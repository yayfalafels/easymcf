# Easy MCF POC Local - API Design

## Purpose

Elaborates REQ-PLAT-01's backend API surface into an implementable specification: which entities are exposed through the generic CRUD shapes unmediated, which use that same shape backed by a per-table write/read hook enforcing an invariant, and which operations fall outside all seven generic shapes as named endpoints — plus the concrete catalog of the latter two categories. This document exists so [010-01-requirements.md](010-01-requirements.md) and [010-architecture.md](010-architecture.md) can state the *principle* (generic CRUD is the default, not a blanket mandate) without carrying the full per-entity enumeration that principle requires. It resolves the gap [010-issues.md](010-issues.md)'s ISS-02 identified between REQ-PLAT-01's literal wording and the lead/apply state-machine's invariants; the run-in-flight concurrency guard it also touches on is already fully specified at `ARCH-RUN-03` and is only referenced here, not re-decided.

## Out of scope

- The Flask blueprint/decorator implementation itself, the schema-validation library choice, and the SQL for each hook — milestone 09-11 (functional builds) implementation detail, not design.
- Re-deciding any `ARCH-*` topology/storage/testing decision — this document only elaborates the endpoint surface `ARCH-RUN-10` already delegates to it.

Decisions carry an `API-*` id (grouped `CAT` classification, `HOOK` per-table hook behavior, `EP` named endpoint), mirroring the `REQ-*`/`ARCH-*` grouping convention.

## 1. Three categories, not a generic/bespoke binary

REQ-PLAT-01's generic CRUD shape (`GET/PUT/DELETE /{table}/{id}`, `POST /{table}`, `POST /{table}/batch`, `GET /{table}/search`, `POST /{table}/delete`) is the default for a table, not a mandate that every table's every write reach the database unmediated. Three categories cover every table and operation in [010-data-model.md](010-data-model.md):

**API-CAT-01 Pure generic** — the table has no invariant beyond schema/type/FK validation; the generic CRUD blueprint serves it with zero table-specific code.

**API-CAT-02 Generic-shaped, hook-backed** — the same URL and verb a caller would expect from the generic shape, but the table registers a hook the blueprint calls before and/or after the write (or before serializing a read) to enforce an invariant or apply a side effect. A caller sees no difference in interaction model from a pure-generic table; the difference is entirely internal.

**API-CAT-03 Named** — the operation spans more than one row-level create/update, triggers a background process, or has no natural single-table CRUD shape at all. These get a purpose-specific endpoint that internally calls the same persistence primitives the generic blueprint uses, rather than duplicating them.

## 2. Per-entity classification

| entity           | category       |
| ---------------- | -------------- |
| `role`           | CAT-01 generic |
| `track`          | CAT-01 generic |
| `search_profile` | CAT-01 generic |
| `cv`             | CAT-01 generic |
| `post_track`     | CAT-01 generic |
| `post`           | CAT-02 hook    |
| `lead`           | CAT-02 hook    |
| `application`    | CAT-02 hook    |
| `run_log`        | CAT-02 hook    |
| `session`        | CAT-02 hook    |

- `role` — plain catalog.
- `track` — `is_active` archive/unarchive is a plain field `PUT`, not a named action; no invariant beyond visibility filtering, which is a read-time query concern elsewhere, not a write concern.
- `search_profile` — 1:1 extension of `track`, no invariant beyond schema validation.
- `cv` — delete-while-referenced (UI page 2) is enforced by the FK from `track.default_cv_id`/`application.cv_id`; the generic `DELETE` handler translates the resulting FK-constraint failure into a `409` naming the referencing rows — a generic error-translation rule, not a named endpoint.
- `post_track` — add/edit/remove a track association is a plain join-row write; auto-population by search/scoring/manual-entry happens via internal service calls into this same layer, not a second implementation.
- `post` (see `API-HOOK-03`) — `GET`/`search` generic; `PUT`/`DELETE` are not exposed at the API surface at all; `POST` (manual entry) is named (`API-EP-01`), not generic, because it must also create scored `post_track` rows (REQ-SRCH-07).
- `lead` (see `API-HOOK-01`) — every write, including a routine `notes`/`deadline` edit, must also write a `lead_event` row (REQ-CRM-08), so no field on `lead` is reachable through pure unmediated generic CRUD.
- `application` (see `API-HOOK-02`) — `GET`/`search` generic; created only via `API-EP-02` (queue), status set only by the apply-run service, removed only via `API-EP-03` (dequeue).
- `run_log` (see `API-HOOK-04`) — `GET`/`search` generic (Automation Runs tab reads it this way); no client `PUT`/`POST`/`DELETE` — rows are created/updated only by `API-EP-04`/`API-EP-05` and the background run thread.
- `session` (see `API-HOOK-04`) — `GET` generic (session-status badge reads it this way); `PUT`/`POST` blocked in favor of `API-EP-06` — a raw field write could claim `status='valid'` without an actual validated cookie ever being uploaded.

Named endpoints (`API-EP-*`) are cataloged in full in section 4; they are the only way to create a `lead`/`application` row, trigger a run, or write a session.

## 3. The write/read hook mechanism (API-CAT-02)

**API-HOOK-01 `lead`.** Before any write reaches the row: if the payload changes `stage`, it must be a legal transition per [010-workflows.md](010-workflows.md) Workflow 5's state diagram, and `close_reason` is required (and validated against the seven-value enum) whenever `stage` becomes `CLOSED`; any other field (`notes`, `deadline`, `title_override`, etc.) is unrestricted. After every accepted write, regardless of which fields changed, the hook writes one `lead_event` row (`event_type` inferred from what changed — `stage_change`, `note_edited`, `deadline_changed`, or `contact_logged` for `last_contact_date`) and refreshes `lead.updated_at` from that event's timestamp — this is the single code path REQ-CRM-08 depends on; there is no second, unmediated way to write a lead. On read (`GET`/`search`), the hook evaluates auto-expiry (REQ-CRM-05) against the injectable clock (`ARCH-STO-05`) before serializing: a `lead` open at any stage whose latest `lead_event` is more than 28 days old is closed (`stage=CLOSED`, `close_reason=expired`) as a write-on-read side effect, writing the closing `lead_event` itself, so the persisted state and every subsequent read agree — this is what "evaluated on each backend list call" ([010-workflows.md](010-workflows.md) Workflow 5) means concretely, and why it does not need to be a separate scheduled job.

**API-HOOK-02 `application`.** No hook logic runs on read. On write: the generic surface accepts `GET` only; the row is created exclusively by `API-EP-02`, and its `status`/`error_detail`/`attempted_at` are written exclusively by the apply-run service — internally, via the same persistence call the generic blueprint would use, not a second write path — as each queued application is processed, applying section 5's lead-side-effect rules as it goes.

**API-HOOK-03 `post`.** `GET`/`search` only; no hook logic beyond that restriction. The search/detail-pass service and `API-EP-01` are the only writers.

**API-HOOK-04 `run_log`, `session`.** `GET`/`search` only for both, for the reasons in the classification table above; write access is restricted to the named endpoints and their background processing.

## 4. Named endpoint catalog (API-CAT-03)

All paths below sit under the `/api` prefix per `ARCH-RUN-10` and are the complete set of exceptions to the seven generic shapes — an endpoint that is neither one of the seven generic shapes nor in this table is a design gap to raise with the architect, not a drift to build around silently.

| id        | method + path                            |
| --------- | ---------------------------------------- |
| API-EP-01 | `POST /api/posts/manual`                 |
| API-EP-02 | `POST /api/applications/queue`           |
| API-EP-03 | `POST /api/applications/{id}/dequeue`    |
| API-EP-04 | `POST /api/runs/search`                  |
| API-EP-05 | `POST /api/runs/apply`                   |
| API-EP-06 | `POST /api/session/upload`               |
| API-EP-07 | `GET /api/health`                        |

- **API-EP-01** (REQ-SRCH-07) — creates a `post` (`src_method='manual'`), runs match-scoring against every track, creates the resulting `post_track` rows (`search_match=false`).
- **API-EP-02** (REQ-APPLY-01) — given `lead_ids[]`: each must be at stage `PROSPECT`; transitions each to `TOAPPLY` and creates one `application(status='queued')` row per lead.
- **API-EP-03** (REQ-APPLY-11) — deletes a `queued` (not yet attempted) `application` row and closes its owning lead with `close_reason='withdrawn'` — not a revert to `PROSPECT`.
- **API-EP-04** (REQ-SRCH-02, `ARCH-RUN-02/03`) — creates a `run_log(run_type='search', status='running')` row and starts the background search thread for the given `track_id`; returns the `run_log.id`. Concurrency guard already fixed at `ARCH-RUN-03`'s `UNIQUE` partial index — not re-specified here.
- **API-EP-05** (REQ-APPLY-03, `ARCH-RUN-02/03`) — creates a `run_log(run_type='apply', status='running')` row and starts the background apply thread over every `queued` application; returns the `run_log.id`. Same `ARCH-RUN-03` guard; retry timing per `ARCH-BOT-05`'s env-var overrides.
- **API-EP-06** (REQ-APPLY-06) — validates the uploaded cookie payload's domain match, writes `.secrets/mcf_session.json` (`ARCH-BOT-03`), and updates the `session` row's `status`/`uploaded_at`/`cookie_ref`.
- **API-EP-07** (`ARCH-TEST-04`) — readiness probe the mock-e2e test harness polls before driving the UI — no domain effect.

A manual stage transition or close action (the Lead Detail panel's "move to next stage" / close-with-reason controls) is **not** a named endpoint — it's a plain `PUT /api/lead/{id}` carrying the new `stage`/`close_reason`, validated and logged by `API-HOOK-01`. Keeping it generic-shaped rather than adding `API-EP-08`, `-09`, ... for every transition is what REQ-PLAT-01's "no bespoke endpoint per feature" intent actually buys once the hook mechanism exists.

## 5. Apply-outcome → lead propagation (implementation note for API-HOOK-02)

Restates [010-workflows.md](010-workflows.md) Workflow 7 as the exact write sequence the apply-run service performs per queued application, so it's unambiguous this happens inside `API-HOOK-02`'s internal write path and never as a client-visible endpoint: on `status='applied'`, transition the lead to `APPLIED` (REQ-APPLY-09); on `status` in (`post_closed`, `post_unavailable`), close the lead with `close_reason='apply_failed'` (REQ-APPLY-10); on any other status, leave the lead at `TOAPPLY`. Each of these is a call into `API-HOOK-01`'s same write path (so the resulting `lead_event` row is written), not a second lead-mutation code path.
