 ## Scope

Build out the real database schema and seed dataset this release has been running against a placeholder for since milestone 07, namely `easymcf/db/schema.sql`'s `meta`-only table and `seed/seed.sql`'s no-op stub. Two deliverables:

- **schema**: extend `easymcf/db/schema.sql` from `meta`-only to the full DDL for all entities the **data model** fixes, `role`, `user`, `track`, `search_profile`, `cv`, `post`, `post_track`, `match_score`, `lead`, `lead_note`, `lead_event`, `application`, `run_log`, and `session`, with foreign keys and the constraints the model calls out, for example `lead.post_id` uniqueness, since a post promotes into at most one lead, and bump `meta.schema_version`, per `ARCH-STO-03`, since this is a schema change
- **seed data**: build `scripts/gen_test_data.py`, plus a thin `scripts/gen_test_data.sh` wrapper per `TESTDATA-GEN-02`, that reads the hand-downloaded `test-data/*.csv` source export, gitignored and never committed per `TESTDATA-GEN-05`, applies the **test data spec**'s section 4 per-table mapping and cleaning rules, and emits `seed/*.sql`. This is the small, deterministic, using `--rand-seed`, committed enumeration `ARCH-STO-04` requires:
  01. two tracks with one archived
  02. CV labels
  03. posts in both `scraped` and `manual` `src_method`
  04. posts matching multiple tracks
  05. leads at every stage including `CLOSED` with several close reasons
  06. applications covering all eight REQ-APPLY-04 outcome codes
  07. `run_log` rows in every status

  It replaces the milestone-07 placeholder `seed/seed.sql` outright.

## Design

### Table creation order and types

`easymcf/db/schema.sql` stays one hand-maintained file, per `ARCH-STO-02`. This milestone only appends to it. Tables are created in FK-dependency order so every `FOREIGN KEY` references an already-declared table, even though SQLite itself doesn't enforce declaration order at `CREATE TABLE` time. Doing it anyway makes the file readable top-to-bottom as its own dependency graph:

`meta` (07) → `role` → `user` → `cv` (→ `user`) → `track` (→ `user`, `role`, `cv`) → `search_profile` (→ `track`) → `run_log` (→ `track`, nullable) → `post` (→ `run_log`, nullable) → `post_track` (→ `post`, `track`) → `match_score` (→ `post_track`) → `lead` (→ `post`, `track`) → `lead_note` (→ `lead`) → `lead_event` (→ `lead`) → `application` (→ `lead`, `cv`, `run_log`) → `session` (→ `user`)

the **data model**'s field lists are conceptual. Concrete SQLite types are resolved here: `id` columns are `INTEGER PRIMARY KEY`, a SQLite rowid alias, except `post.id`, which is `TEXT PRIMARY KEY` per its documented `source + posting_reference + posted_date` composite scheme. `search_profile.track_id`, `post_track`'s `(post_id, track_id)`, and `match_score`'s `(post_id, track_id)` are their own primary keys rather than separate surrogate ids, matching the model's stated 1:1 / many-to-many shape. `match_score` additionally carries a composite `FOREIGN KEY (post_id, track_id) REFERENCES post_track(post_id, track_id)`, so a `match_score` row cannot exist without its owning `post_track` pairing. Boolean fields, `track.is_active`, `post.is_open`, and `post_track.search_match`, are `INTEGER` with `CHECK (col IN (0,1))`. Date/timestamp fields are `TEXT` in ISO-8601, `YYYY-MM-DD` or `YYYY-MM-DD HH:MM:SS`, matching `ARCH-STO-05`'s clock-indirection convention and SQLite's own date functions. `run_log.outcome_counts` is `TEXT` holding a JSON-encoded string. SQLite has no native JSON column type, so marshaling via `json.dumps`/`loads` is an application-layer concern for milestone 09's `run_log` writer, not this schema's.

Indexes beyond the primary/foreign keys: `post(is_open)`, `post(run_id)`, `post_track(track_id)`, `lead(track_id)`, `lead(status, stage)`, `application(lead_id)`, `application(run_id)`, `lead_event(lead_id)`, `run_log(run_type, status)`. These support the query patterns the **workflows** and **user interface** docs describe, such as active-post filtering, per-track pipeline views, and per-lead activity/attempt history. They are not exhaustive coverage of every possible query.

### Closed-vocabulary enforcement

Every closed enumeration the **requirements** doc fixes is additionally enforced as a `CHECK` constraint at the schema layer, transcribed verbatim from the requirements table each comes from. It is not transcribed from the generator's own code, so the two don't share a source of truth for what's "valid".

**implementation decision**: neither the **architecture** doc nor the **data model** mandates DB-level `CHECK` constraints. Application-layer validation via the generic-CRUD JSON-schema envelope, `REQ-PLAT-01`, is milestone 09's job. Adding them here anyway gives a second, DB-native enforcement layer, redundant by design with the future app-layer validation. `TESTDATA-GEN-04` already requires the generator to validate its own output by loading it into a scratch database before writing final output, and a `CHECK` constraint is exactly what turns "the generator silently emitted an invalid enum value" into a loud `sqlite3.IntegrityError` at that validation step, with the offending row identified, instead of a UI rendering bug discovered much later in milestone 09-11.

### Seed-data generator pipeline

`scripts/gen_test_data.py`, plus a thin `scripts/gen_test_data.sh` wrapper, `TESTDATA-GEN-02`, is one linear pipeline, run once per invocation. Per `TESTDATA-GEN-03` it is idempotent and non-incremental, with no merge with a prior run's output:

1. **read**: `test-data/*.csv`, using a positional `csv.reader` rather than `DictReader` for `screened.csv`, per `TESTDATA-SRC-01`'s duplicate-header trap
2. **clean**: section 3's column-level rules, percent→float, boolean normalization, blank-row skip, redacted-URL synthesis
3. **map**: section 4's per-table rules, one function per target table, each returning a list of row-dicts
4. **synthesize gaps**: `TESTDATA-GAP-01..04`'s fabricated rows, such as below-threshold posts, missing apply-outcome codes, pre-apply lead stages, and `cancelled`/`apply_failed` close reasons, each tagged with a SQL comment naming which gap it fills
5. **shift dates**: the single `TESTDATA-MAP-08` anchor delta applied uniformly across every date/timestamp field, in every table, computed once per run
6. **sanitize**: `TESTDATA-GEN-05`'s privacy pass. Any `notes`/`lead_event.detail` value sourced from a real row is replaced with a genericized placeholder before it ever reaches `seed` mode's output. The uncommitted `sample` mode output is exempt, sharing the same trust boundary as `test-data/` itself
7. **validate**: `TESTDATA-GEN-04`. Apply the fully-generated SQL against a scratch temp database, reusing `easymcf/db/schema.sql` and `scripts/db_util.py`'s connection handling, and confirm it loads cleanly before anything is written to `--out`
8. **write**: `seed/*.sql` for mode `seed`, or a single file path for mode `sample`

`ARCH-STO-04` requires seed to diff and review like code, `seed/*.sql`, plural, and `TESTDATA-GEN-02` fixes `--out` as a directory of one file per table for `seed` mode. `scripts/resetdb.py`, built in the **prior milestone** per `EL.12`, already applies every `seed/*.sql` file via `sorted(glob.glob(...))`, one file at a time, using a plain lexicographic sort that isn't FK-aware. Per-table seed files are therefore named with a **zero-padded two-digit numeric prefix matching the table creation order above**: `01_role.sql`, `02_user.sql`, `03_cv.sql`, `04_track.sql`, `05_search_profile.sql`, `06_run_log.sql`, `07_post.sql`, `08_post_track.sql`, `09_match_score.sql`, `10_lead.sql`, `11_lead_note.sql`, `12_lead_event.sql`, `13_application.sql`, `14_session.sql`. This means `sorted()`'s plain string order is already FK-safe load order without any change to `resetdb.py` itself. This replaces milestone 07's single placeholder `seed/seed.sql` outright. The old filename is deleted rather than merely superseded, so no stale no-op file lingers alongside the real set.

### Independent seed verification

`REQ-DEV-03`, backend-only automated tests against seed/fixture data with no browser, and this milestone's own closure condition, `08.CK.03`, both need something that checks the *loaded* database against the design's stated minimum enumeration, independent of the generator's own `TESTDATA-GEN-04` self-check. 

a new pytest module under the existing `backend` marker tier, `tests/backend/`, milestone 07's scaffold, whose expected value sets are transcribed directly from this Design section's own tables above, and transitively from the **requirements**/**architecture** docs, rather than imported from `scripts/gen_test_data.py`'s constants. This way a bug that makes the generator emit the wrong enumeration and a check that only re-reads the generator's own idea of "correct" don't share the same blind spot. 

This operationalizes `STRAT-CASE-05`, closed-vocabulary enumeration completeness, as a concrete, re-runnable test rather than introducing a new testing mechanism.

## Test cases

_test strategy_: four independent layers, per the tracker-pattern skill, since no layer grades its own homework, chosen specifically so the seed dataset's *shape, row counts, and enumeration content* are checked against the design above rather than against whatever the generator happens to believe it produced:

1. **self-report**: `scripts/gen_test_data.py`'s own `[PASS]`/`[FAIL]` log line, exit code, and its internal `TESTDATA-GEN-04` scratch-db validation result. Weakest alone, it proves the generator ran and its own check passed, but not that the design's stated minimum enumeration is actually met
2. **process boundary**: `scripts/initdb.py`/`scripts/resetdb.py` invoked as separate CLI subprocesses, per their `ENV-SCRIPT-01/02` contracts, checking exit code and stdout only. This is exactly what a human or an unattended agent runs, independent of importing the generator's or resetdb's Python functions directly
3. **direct inspection**: `scripts/db_util.py`, or raw `sqlite3`, queries against the resulting `data/easymcf.db` file directly, bypassing both the generator's and `resetdb.py`'s own success claims entirely. This is the layer that actually answers "does the loaded data match the design," rather than merely "did the loading step exit 0"
4. **oracle**: the independent seed-verification pytest module described in Design above. Expected enumeration values are hard-coded from the requirements/architecture docs' own text, rather than read from the generator's source. This confirms the seed satisfies the *design's* stated minimum, rather than merely the generator's internal idea of it

Every case below is read-only against a freshly reset database or a side-effect-free subprocess invocation, so re-running the full table twice in a row is safe and produces the same verdicts, meaning it is idempotent. No case here mutates state that a later case in the table depends on.

### 08.EL.01 `easymcf/db/schema.sql`

Original implementation appended thirteen tables to the existing `meta` table, in the creation order Design fixes, and bumped `schema_version` from 1 to 2 per `ARCH-STO-03`. A later revision, driven by the manual-validation findings below, added `user`, `match_score`, and `lead_note`, an explicit `user_id` on `track`/`cv`/`session`, and dropped `post_track.match_score`/`score_method` and `lead.notes`, bumping `schema_version` again, 2 to 3. The block below is the current file, not a historical snapshot:

```sql
-- Easy MCF POC local - schema (ARCH-STO-02, single hand-maintained file, no migrations).
-- schema_version 2 adds the release-010 data model to the milestone-07 base.
-- schema_version 3 adds `user`, `match_score`, `lead_note`, and explicit `user_id`
-- ownership columns on `track`/`cv`/`session` (see docs/releases/010/design/010-data-model.md).

CREATE TABLE meta (
    schema_version INTEGER NOT NULL
);

INSERT INTO meta (schema_version) VALUES (3);

CREATE TABLE role (
    id INTEGER PRIMARY KEY,
    name TEXT NOT NULL,
    description TEXT
);

CREATE TABLE user (
    id INTEGER PRIMARY KEY,
    name TEXT NOT NULL,
    email TEXT NOT NULL,
    status TEXT NOT NULL
);

CREATE TABLE cv (
```

### 08.EL.02 `scripts/gen_test_data.py`

One module implementing the 8-stage pipeline Design fixes. The skeleton below names every function the pipeline calls. The per-table `_map_*` functions shown are representative, covering the duplicate-header trap, the status and stage translation table, and the enumeration-completeness fabrication.
```python
#!/usr/bin/env python3
"""TESTDATA-GEN-01/02 — seed and sample data generator, one pipeline, two output modes.

    python scripts/gen_test_data.py --mode seed --out seed/ --rand-seed 42
    python scripts/gen_test_data.py --mode sample --out test-data/sample.sql --rand-seed 42

Reads test-data/*.csv (gitignored, never committed), applies the mapping and
cleaning rules in docs/releases/010/design/010-test-data.md section 4, and
writes seed/*.sql (one file per table, numbered for FK-safe load order) or a
single sample SQL file. Idempotent and non-incremental (TESTDATA-GEN-03):
every run regenerates its full output from the source CSVs and the anchor
date, with no merge against a prior run's output.
"""
from __future__ import annotations

import argparse
import csv

_REPO_ROOT = os.path.dirname(os.path.dirname(os.path.abspath(__file__)))

_SCHEMA_PATH = os.path.join(_REPO_ROOT, "easymcf", "db", "schema.sql")

    "role", "user", "cv", "track", "search_profile", "run_log", "post",
    "post_track", "match_score", "lead", "lead_note", "lead_event", "application", "session",
]

def clean_screened_rows(raw_rows: list[list[str]]) -> list[dict]:
    """TESTDATA-SRC-01 — screened.csv's header has two duplicated column names
    (posted_date, open/closed), so DictReader silently drops the first
    occurrence of each. Read positionally instead, by column index."""
    header = raw_rows[0]
    out = []
    for row in raw_rows[1:]:
        if not row or not row[header.index("jobid")]:
            continue  # blank-jobid rows are sheet export artifacts
        out.append({
            "jobid": row[4],
            "position_title": row[13] or row[2],  # position_title, else deranked_title
            "company_name": row[3],
            "url": row[5],
            "posted_date": row[10],       # first occurrence, not the duplicated 2nd
            "closing_date": row[11],
            "salary_high": row[6],
            "src_methodid": row[15],
        })
    return out


_STAGE_MAP = {
    # source value, source column -> (lead.stage, lead.close_reason)
    ("1.1 resume screening dark", "open.stage"): ("APPLIED", None),
    ("02 interview preparation", "open.stage"): ("INTERVIEW", None),
    ("offer accepted", "status"): ("CLOSED", "offer_accepted"),
    ("rejected", "status"): ("CLOSED", "rejected"),
    ("expired", "status"): ("CLOSED", "expired"),
    ("withdrawal", "status"): ("CLOSED", "withdrawn"),
    # full table: TESTDATA-MAP-04 in the test data spec
}

_STAGE_RANK = ["PROSPECT", "TOAPPLY", "APPLIED", "CALLBACK", "INTERVIEW", "OFFER", "CLOSED"]


def resolve_lead_stage(signals: list[tuple[str, str]]) -> tuple[str, str | None]:
    """TESTDATA-MAP-04 multi-signal precedence — take the highest-progress
    mapped stage across every available source signal for one lead."""
    mapped = [_STAGE_MAP[s] for s in signals if s in _STAGE_MAP]
    if not mapped:
        return "PROSPECT", None
    return max(mapped, key=lambda sc: _STAGE_RANK.index(sc[0]))


_APPLY_STATUS_CODES = [
    "applied", "questionnaire_required", "cv_selector_error", "unable_to_apply",
    "post_unavailable", "cv_not_found", "post_closed", "invalid_input",
]


def fabricate_missing_apply_outcomes(rand: random.Random, next_post_id) -> list[dict]:
    """TESTDATA-GAP-02 — real data only ever produces 'applied'. Fabricate one
    small synthetic post/lead/application triple per remaining status code so
    every one of REQ-APPLY-04's eight codes is reachable from seed data."""
    rows = []
    for code in _APPLY_STATUS_CODES[1:]:  # 'applied' already comes from real leads
        post_id = next_post_id()
        close_reason = "apply_failed" if code in ("post_closed", "post_unavailable") else None
        rows.append({"post_id": post_id, "status": code, "close_reason": close_reason, "synthetic": True})
    return rows


def compute_anchor_shift(all_dates: list[date], anchor: date) -> timedelta:
    """TESTDATA-MAP-08 — one shift delta for the whole run, preserving every
    real day-count gap between dates rather than shifting columns independently."""
    return anchor - max(all_dates)


def sanitize_note(raw_note: str | None, is_sample_mode: bool) -> str | None:
    """TESTDATA-GEN-05 — seed mode never carries a real note verbatim.
    Sample mode is uncommitted and gitignored, the same trust boundary as
    test-data/ itself, so it is exempt."""
    if raw_note is None or is_sample_mode:
        return raw_note
    return "Interview scheduled with hiring manager" if raw_note.strip() else raw_note


def validate_against_scratch_db(sql_by_table: dict[str, str]) -> None:
    """TESTDATA-GEN-04 — load the fully generated SQL into a scratch temp
    database before writing --out, so a FK or uniqueness violation surfaces
    here, with the offending row identified, not the next resetdb.py --seed."""
    scratch_path = "/tmp/gen_test_data_scratch.db"
    if os.path.exists(scratch_path):
        os.remove(scratch_path)
    conn = sqlite3.connect(scratch_path)
    try:
        conn.execute("PRAGMA foreign_keys = ON")
        with open(_SCHEMA_PATH, encoding="utf-8") as f:
            conn.executescript(f.read())
        for table in _TABLE_ORDER:
            conn.executescript(sql_by_table[table])
        conn.commit()
    finally:
        conn.close()
        os.remove(scratch_path)


def write_seed_files(sql_by_table: dict[str, str], out_dir: str) -> None:
    """ARCH-STO-04/TESTDATA-GEN-02 — one file per table, zero-padded numeric
    prefix matching _TABLE_ORDER, so resetdb.py's plain sorted(glob(...))
    already loads them in FK-safe order."""
    os.makedirs(out_dir, exist_ok=True)
    for old in os.listdir(out_dir):
        if old.endswith(".sql"):
            os.remove(os.path.join(out_dir, old))  # non-incremental, TESTDATA-GEN-03
    for i, table in enumerate(_TABLE_ORDER, start=1):
        path = os.path.join(out_dir, f"{i:02d}_{table}.sql")
        with open(path, "w", encoding="utf-8") as f:
            f.write(sql_by_table[table])


def main() -> int:
    parser = argparse.ArgumentParser(description=__doc__)
    parser.add_argument("--mode", choices=["seed", "sample"], required=True)
    parser.add_argument("--out", required=True)
    parser.add_argument("--rand-seed", type=int, required=True)
    parser.add_argument("--anchor", default=None, help="YYYY-MM-DD, defaults to today")
    args = parser.parse_args()

    rand = random.Random(args.rand_seed)
    anchor = date.fromisoformat(args.anchor) if args.anchor else date.today()

    # 1. read, 2. clean, 3. map, 4. synthesize gaps, 5. shift dates, 6. sanitize
    # ... builds sql_by_table: dict[str, str], one INSERT-statement string per table

    validate_against_scratch_db(sql_by_table)  # 7. validate

    if args.mode == "seed":                    # 8. write
        write_seed_files(sql_by_table, args.out)
    else:
        with open(args.out, "w", encoding="utf-8") as f:
            for table in _TABLE_ORDER:
                f.write(sql_by_table[table])

    print(f"[PASS] {args.mode} generated — {args.out}")
    return 0


if __name__ == "__main__":
    raise SystemExit(main())
```
