# Search By Keywords - Feature tracker
>Review the guidelines before performing any actions including edits on the document

## 010.10 (open) search by keywords

Implements the **requirements** doc's Search by keywords section (REQ-SRCH-01..11) and the search-facing half of REQ-FE-01/02: configuring a track and its search profile, triggering a search run on demand or on a user-configured schedule, executing the scrape → incremental-persist → dedup → detail-pass → score pipeline against MCF, folding manually-entered posts into that same pipeline, and giving the user the Posts/results screen to review, filter, and act on what a run produced. Builds on the schema and seed data milestone 08 delivered for `track`/`search_profile`/`post`/`post_track`/`match_score`/`run_log`, and carries the data model update the **data model** doc specifies for REQ-SRCH-11's `search_schedule` table.

## Scope

Build the search-by-keywords feature end to end on top of milestone 08's schema and seed data: the track/search-profile configuration the whole release hangs off, both ways a search run starts, the run pipeline itself, and the AngularJS screens (**user interface** pages 1, 1b, 3, and the page 4 manual-entry dialog) that let a user configure, trigger, review, and act on what a run produced. A triggered run, manual or scheduled, performs a fresh MCF search from the configured search profile and upserts the unique posts it finds incrementally across repeated runs.

In scope:

- **backend — track, search profile, and search schedule CRUD** (REQ-SRCH-01, REQ-SRCH-10, REQ-SRCH-11): `track`, `search_profile`, and `search_schedule` as `API-CAT-01` pure generic resources per the **api design**, each keyed on `track_id`, with track archive/unarchive as a plain `PUT {"is_active": false}`. `search_schedule` carries the three schedule columns (`schedule_enabled`, `schedule_interval_hours`, `next_run_at`) the **data model** defines for REQ-SRCH-11, so configuring a schedule is a plain generic write on its own resource. This milestone's routes ride on the generic CRUD blueprint the **api design** defines.
- **backend — data model update** (`ARCH-STO-02/03`, **data model** Schema versions table): edit `easymcf/db/schema.sql` to add the new `search_schedule` table and `run_log.trigger_source`, bump `meta.schema_version` to whatever value is next per the **data model**'s Schema versions table at implementation time, and the matching `easymcf/__init__.py` constant, extend `scripts/gen_test_data.py` to emit `search_schedule` seed rows, and re-run `scripts/resetdb.py --seed`. Recreate-don't-migrate stays in force, per `ARCH-STO-02`. Revising the `search_schedule`/`run_log.trigger_source` shape, if implementation surfaces a need to, is in scope here too. This milestone keeps the **data model** and **architecture** docs current with whatever ships, rather than treating a design-doc update as a separate step outside its own scope.
- **backend — run trigger** (REQ-SRCH-02): `API-EP-04 POST /api/v1/runs/search`, which inserts the `running` `run_log` row (`trigger_source='manual'`), starts the background thread per `ARCH-RUN-02`, and returns the `run_log.id` immediately. A second trigger while a search run is in flight returns `409` with the in-flight id, enforced directly by `ARCH-RUN-03`'s partial unique index at insert time.
- **backend — scheduler** (REQ-SRCH-11, `ARCH-SCHED-01..06`): the in-process tick thread that reads due `search_schedule` rows through `clock.py::now()`, calls the same run-trigger service function `API-EP-04` calls, writes `trigger_source='scheduled'`, advances `next_run_at` in whole interval multiples so missed windows coalesce into one run, and skips and logs the collision when it meets a run already in flight, retrying on the next tick. Started by `__main__.py` at app startup, and governed by `SCHEDULER_ENABLED`/`SCHEDULER_TICK_S`.
- **backend — search run pipeline** (REQ-SRCH-03..06, REQ-SRCH-09): a fresh MCF search per the configured profile's keyword(s)/salary/age, paginating until a page returns no results, parsing title/company/reference/posted date/salary from each card, persisting posts **as they are found** (REQ-SRCH-04), deduplicating on the `source + posting_reference + posted_date` post id so a re-run upserts existing posts (REQ-SRCH-05), running the detail pass as a distinct second sweep over undetailed posts and dropping a post found closed out of the active set (REQ-SRCH-06), and scoring each post against every matching track with the title-keyword method recorded as `score_method` (REQ-SRCH-09). All MCF interaction goes through `ARCH-BOT-02`'s `MCFBrowser` seam, so the same code path runs in `fixture` and `live` mode.
- **live-tier validation of the search-run pipeline** (REQ-DEV-05, `ARCH-TEST-06`): this milestone is the first to populate milestone 07's empty `tests/live/` scaffold with a real case, a `pytest -m live --run-live` search run against the real MCF site using a valid `.secrets/mcf_session.json`. It runs only after the fixture-tier and mock-e2e-tier cases for the pipeline pass, per the **test strategy**'s STRAT-02 ordering, backend-only first, mock e2e second, live third. Its job is confirming MCF's real markup still matches the fixture corpus it was captured from, not discovering pipeline logic defects, which the fixture-tier cases already own. No agent triggers this tier on its own initiative, per `ARCH-TEST-06`, and a human runs it deliberately once the earlier tiers are green.
- **backend — manual post entry** (REQ-SRCH-07): `API-EP-01 POST /api/v1/posts/manual`, which creates the `post` row with `src_method='manual'`, auto-assigns matching tracks with the same scoring logic a run uses, writes the `post_track` (`search_match=false`) plus `match_score` pairs in the same request, and exempts the post from the min-score screen.
- **backend — track assignment and rescoring** (REQ-SRCH-07/08): generic `post_track`/`match_score` writes so a post matching multiple tracks can have an association added or removed and its score reviewed and updated by the user, keeping the association's `search_match` provenance flag intact through a score change.
- **backend — run status read** (REQ-PLAT-03, REQ-FE-02): `run_log` `GET`/`search` as the polling surface for a running search, including `trigger_source` so the run history answers whether last night's schedule actually fired.
- **frontend — Tracks page** (**user interface** page 1): list/create/edit a track's identity, role and seniority, the default-CV picker, and the archive/unarchive action plus the show-archived toggle (REQ-SRCH-10), with a "Configure search" link per track into Search Profiles (page 1b). This page owns track identity and lifecycle. Search configuration lives on Search Profiles (page 1b), and the run trigger lives on Posts (page 3).
- **frontend — Search Profiles page** (**user interface** page 1b): one form per track, reached from Tracks, presenting the keyword/salary/age/min-score/employment-type search criteria (REQ-SRCH-01) and the three schedule fields (REQ-SRCH-11) together, backed by the `search_profile` and `search_schedule` resources for that track. This page owns search configuration only. Track identity lives on Tracks (page 1), and the run trigger lives on Posts (page 3).
- **frontend — Posts page** (**user interface** page 3): track selector, "Run search" with the async running/polling state and error banner, the results table sorted by score descending, the filter set (min score defaulting to the profile's `min_match_score`, max age, include-below-threshold toggle), the `manual` tag, and the `already promoted` indicator.
- **frontend — promote-to-lead trigger** (**user interface** page 3 row action): the control that opens the track picker when a post matches more than one track and calls milestone 09's lead-creation endpoint, then flips the row to `already promoted`. This milestone owns the control and its result handling.
- **frontend — Manual Post Entry dialog** (**user interface** page 4) and the inline track-assignment editor it returns to.
- **run-status/error surfacing** (REQ-FE-02): a failed run, a rejected `409` trigger, or a rejected profile write surfaces in the UI through the **user interface** design's cross-cutting error-surfacing pattern.

Out of scope:

- the `lead`/`lead_note`/`lead_event` write path, the promote endpoint's own hook logic, the Leads page (**user interface** page 5), and the Lead Detail panel (page 6) — milestone 09, job leads tracking. This milestone calls `POST /api/v1/lead` from the Posts row action. Milestone 09 owns that endpoint, its invariants, and every screen that exists once a lead exists.
- apply automation, the apply state machine, CV assignment to a track's default, the apply-queue/results screens (page 7), and the Automation/session screen (page 8) — milestone 11. Track's `default_cv_id` picker renders on page 1 as part of that form, but the apply-time behavior behind it is milestone 11's.
- an OS-level scheduler of any kind — cron entry, systemd timer, APScheduler, Celery beat, or a second process. Explicitly refused by the **architecture**'s out-of-scope list and `ARCH-SCHED-01`'s rejected alternatives. REQ-SRCH-11 is satisfied only by schedule state the UI edits and the app reads.
- `track`/`search_profile`/`search_schedule`/`post`/`post_track`/`match_score`/`run_log` schema and seed-data generation beyond this milestone's own data model update above — delivered by milestone 08. This milestone reuses that seed set, extending it only where Design finds a concrete gap (e.g. a profile with a schedule already due, needed to exercise the tick path).
- NLP/semantic match scoring and salary-percentile scoring — release-wide exclusions (**requirements** Out of scope); `010` ships only the primitive title-keyword method, recorded with its `score_method` so `020` can add another scoring method against the same schema.
- any analytics/BI/reporting pipeline — ETL, warehouse, cross-run dashboards — explicitly out of scope release-wide. "Run reporting" for this milestone means only the run-status polling and `run_log` reads already specified above.
- multi-user support/ownership beyond the single seeded user — out of scope release-wide.
- any request against the live MCF site, and any read of a real session cookie export, run automatically or on an agent's own initiative (**project boundaries**, REQ-DEV-03/04, `ARCH-TEST-06`). Development, automated tests, and every agent-run validation loop use `MCF_MODE=fixture` against the fixture corpus and seed data by default. The live-tier case above is the one deliberate exception, and it is always a human-triggered action, never automatic.

**closure**

- **10.CK.01** every one of REQ-SRCH-01..11 is implemented and independently verified by the Test cases section this milestone writes.
- **10.CK.02** a triggered run, manual or scheduled, performs a fresh MCF search against the configured search profile, persists posts as it finds them, and upserts on the `source + posting_reference + posted_date` id, so running the same search twice keeps `post`, `post_track`, and `match_score` rows unique per id.
- **10.CK.03** a run interrupted partway through keeps every post already captured in that run (REQ-SRCH-04), and the detail pass drops a post found closed from the active set (REQ-SRCH-06).
- **10.CK.04** a user can create, edit, and archive a track and its search profile from the UI, including its schedule configuration, the change persists to the database, and the next run reflects it — an edited keyword changes what is searched, and an archived track disappears from every active track selector while its history stays readable.
- **10.CK.05** a user can trigger a run on demand from the Posts screen, and separately configure a schedule that later fires a run entirely on its own, recorded in `run_log` with `trigger_source='scheduled'`.
- **10.CK.06** a schedule falling due while a search run is already in flight defers: the tick skips, logs the collision, leaves `next_run_at` untouched, and fires on a later tick once the in-flight run ends (`ARCH-SCHED-04`). A schedule whose window was missed while the app was closed produces exactly one catch-up run (`ARCH-SCHED-03`).
- **10.CK.07** the Posts screen lists results with working score/age/below-threshold filters, score-descending default sort, and the `manual` and `already promoted` indicators, all populated live from the real backend API.
- **10.CK.08** the "Promote to lead" row action on the Posts screen successfully calls milestone 09's `POST /api/v1/lead` with the user-selected track, and the row flips to `already promoted` on success; a rejected promote surfaces its error in the UI (REQ-FE-02).
- **10.CK.09** a manually entered post is created with `src_method='manual'`, auto-assigned its matching tracks with scores, exempt from the min-score screen, and visible and promotable in the same results list as a scraped post (REQ-SRCH-07).
- **10.CK.10** a post matching more than one track shows a per-track score the user can review, and the user can update that track assignment from the UI, keeping the pairing's `search_match` provenance intact (REQ-SRCH-07/08).
- **10.CK.11** `schema.sql` carries the `search_schedule` table and `run_log.trigger_source`, `meta.schema_version` matches the **data model**'s Schema versions table, `scripts/resetdb.py --seed` loads cleanly against it, and a version mismatch refuses startup with the `ARCH-STO-03` message.
- **10.CK.12** milestone 07's, 08's, and 09's own closing commands still pass unmodified against this milestone's changes — no regression.
- **10.CK.13** with every fixture-tier and mock-e2e-tier case for the search-run pipeline passing, a human-triggered `pytest -m live --run-live` run against the real MCF site completes and confirms the pipeline still parses real MCF markup, per REQ-DEV-05 and `ARCH-TEST-06`. This case is never run by an agent on its own initiative and is never part of the automated closing loop.
