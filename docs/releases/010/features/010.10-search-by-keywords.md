# Search By Keywords - Feature tracker
>Review the guidelines before performing any actions including edits on the document

## 010.10 (open) search by keywords

Implements the **requirements** doc's Search by keywords section (REQ-SRCH-01..11) and the search-facing half of REQ-FE-01/02: configuring a track and its search profile, triggering a search run on demand or on a user-configured schedule, executing the scrape → incremental-persist → dedup → detail-pass → score pipeline against MCF, folding manually-entered posts into that same pipeline, and giving the user the Posts/results screen to review, filter, and act on what a run produced. Builds on the schema and seed data milestone 08 delivered for `track`/`search_profile`/`post`/`post_track`/`match_score`/`run_log`, and carries the data model update for run provenance and the keyword library.

## Scope

Build the search-by-keywords feature end to end on top of milestone 08's schema and seed data: the track/search-profile configuration the whole release hangs off, both ways a search run starts, the run pipeline itself, and the AngularJS screens (**user interface** pages 1, 1b, 3, and the page 4 manual-entry dialog) that let a user configure, trigger, review, and act on what a run produced. A triggered run, manual or scheduled, performs a fresh MCF search from the configured search profile and upserts the unique posts it finds incrementally across repeated runs.

In scope:

- **backend — track, search profile, and search schedule CRUD** (REQ-SRCH-01, REQ-SRCH-10, REQ-SRCH-11): `track`, `search_profile`, and `search_schedule` as `API-CAT-01` pure generic resources per the **api design**, each keyed on `track_id`, with track archive/unarchive as a plain `PUT {"is_active": false}`. `search_schedule` carries the three schedule columns (`schedule_enabled`, `schedule_interval_hours`, `next_run_at`) the **data model** defines for REQ-SRCH-11, so configuring a schedule is a plain generic write on its own resource. This milestone's routes ride on the generic CRUD blueprint the **api design** defines.
- **backend — data model update** (`ARCH-STO-02/03`, **data model** Schema versions table): edit `easymcf/db/schema.sql` to add `run_log.trigger_source` and the `title_tag` and `keyword_tag` reference tables, after checking that the `search_schedule` table and the per-user `run_log` columns are already present. Bump `meta.schema_version` to the next value per the **data model**'s Schema versions table and the matching `easymcf/__init__.py` constant, extend `scripts/gen_test_data.py` to emit the new column's values and to load the keyword library, and re-run `scripts/resetdb.py --seed`. Recreate-don't-migrate stays in force, per `ARCH-STO-02`. Revising these shapes, if implementation surfaces a need to, is in scope here too. This feature keeps the **data model** and **architecture** docs current with whatever ships.
- **backend — run trigger** (REQ-SRCH-02): `API-EP-04 POST /api/v1/runs/search`, which inserts the `running` `run_log` row for the signed-in user (`trigger_source='manual'`), starts the background thread per `ARCH-RUN-02`, and returns the `run_log.id` immediately. A second trigger by the same user while that user's search run is in flight returns `409` with the in-flight id, enforced directly by `ARCH-RUN-03`'s partial unique index on the user and run type at insert time. A track owned by another user answers `404`.
- **backend — scheduler** (REQ-SRCH-11, `ARCH-SCHED-01..06`): the in-process tick thread that reads due `search_schedule` rows through `clock.py::now()`, calls the same run-trigger service function `API-EP-04` calls, writes `trigger_source='scheduled'`, advances `next_run_at` in whole interval multiples so missed windows coalesce into one run, and skips and logs the collision when it meets a run of the same user already in flight, retrying on the next tick, while the due schedules of other users proceed. Started by `__main__.py` at app startup, and governed by `SCHEDULER_ENABLED`/`SCHEDULER_TICK_S`.
- **backend — search run pipeline** (REQ-SRCH-03..06, REQ-SRCH-09): a fresh MCF search
    - All MCF interaction goes through `ARCH-BOT-02`'s `MCFBrowser` seam, so the same code path runs in `fixture` and `live` mode.
    - per the configured profile's keyword(s)/salary/age
    - paginating until a page returns no results
    - parse url/title/company/reference/posted date/salary from each card
    - persist posts **as they are found** (REQ-SRCH-04)
    - deduplicate on the `source + posting_reference + posted_date` post id so a re-run upserts existing posts (REQ-SRCH-05)
    - run the detail pass, one page load per posting's own detail-page URL, as a distinct second sweep over posts without detail yet, per the **prototype extraction**'s `mcf_profile.py::get_profileRecord()`. That page carries `closing_date`/`applicants`/`industry_classification`/`mcf_ref`/`description`, none of which the search-results card exposes.
    - check that page's open/closed state first, before scraping its other fields, the same short-circuit the **prototype extraction** uses: a closed posting skips the rest of the detail scrape entirely, since those fields are meaningless for a listing no longer live.
    - a post found closed there gets its `post.is_open` flag flipped to `false` (REQ-SRCH-06); the row itself stays. This is a deliberate deviation from the **prototype extraction**'s `db.remove_jobs()`, which hard-deletes a closed posting from its `job` table. `010`'s soft flip, the same shape the **data model** already uses for `track.is_active`, keeps the row and its description readable for any lead already promoted from it. Only its membership in the active set, filtered `WHERE is_open = 1`, changes.
    - a posting whose detail fetch errors is left undetailed, so the next run's set-difference naturally retries it, per the **prototype extraction**'s `failed` list.
    - score each title against the run user's active tracks with the keyword library, method `title_keyword_v1`, recorded as `score_method` (REQ-SRCH-09).
- **live-tier validation of the search-run pipeline** (REQ-DEV-05, `ARCH-TEST-06`): this milestone is the first to populate milestone 07's empty `tests/live/` scaffold with a real case, a `pytest -m live --run-live` search run against the real MCF site using a valid `.secrets/mcf_session.json`. It runs only after the fixture-tier and mock-e2e-tier cases for the pipeline pass, per the **test strategy**'s STRAT-02 ordering, backend-only first, mock e2e second, live third. Its job is confirming MCF's real markup still matches the fixture corpus it was captured from, not discovering pipeline logic defects, which the fixture-tier cases already own. No agent triggers this tier on its own initiative, per `ARCH-TEST-06`, and a human runs it deliberately once the earlier tiers are green.
- **backend — manual post entry** (REQ-SRCH-07): `API-EP-01 POST /api/v1/posts/manual`, which creates the `post` row with `src_method='manual'`, reusing an existing shared post the user cannot yet see and answering `409` for one the user already sees. It auto-assigns the user's matching tracks with the same scoring logic a run uses, writes the `post_track` (`search_match=false`) plus `match_score` pairs in the same request, and exempts the post from the min-score screen. The service then promotes the post to a lead at `TOAPPLY` under its highest-scoring assigned track, or under the user's lowest-id active track when no track scores above 0.
- **backend — track assignment and rescoring** (REQ-SRCH-07/08): generic `post_track`/`match_score` writes so a post matching multiple tracks can have an association added or removed and its score reviewed and updated by the user, keeping the association's `search_match` provenance flag intact through a score change.
- **backend — run status read** (REQ-PLAT-03, REQ-FE-02): `run_log` `GET`/`search` as the polling surface for a running search, including `trigger_source` so the run history answers whether last night's schedule actually fired.
- **backend — validation utility extension** (`STRAT-TOOL-01/04`): extend `scripts/api_tester.py` in place with a poll step, so a case can trigger `POST /api/v1/runs/search`, poll `GET /api/v1/run_log/{id}` until a terminal status or a timeout, and assert on the final body. Milestone 12 built `api_tester.py` as single-request exact-equality replay, and a search run is asynchronous (`ARCH-RUN-02`), returning a `run_log.id` before any post exists, so a run's outcome has no standalone check today. This milestone is the first consumer of that gap and owns the extension. Existing case-file fields, the `PASS`/`FAIL`/`ERROR` classes and the log format stay as they are.
- **frontend — Tracks page** (**user interface** page 1): list/create/edit a track's identity, role and seniority, the default-CV picker, and the archive/unarchive action plus the show-archived toggle (REQ-SRCH-10), with a "Configure search" link per track into Search Profiles (page 1b). This page owns track identity and lifecycle. Search configuration lives on Search Profiles (page 1b), and the run trigger lives on Posts (page 3).
- **frontend — Search Profiles page** (**user interface** page 1b): one form per track, reached from Tracks, presenting the keyword/salary/age/min-score/employment-type search criteria (REQ-SRCH-01) and the three schedule fields (REQ-SRCH-11) together, backed by the `search_profile` and `search_schedule` resources for that track. This page owns search configuration only. Track identity lives on Tracks (page 1), and the run trigger lives on Posts (page 3).
- **frontend — Posts page** (**user interface** page 3): track selector, "Run search" with the async running/polling state and error banner, the results table sorted by score descending, the filter set (min score defaulting to the profile's `min_match_score`, max age, include-below-threshold toggle), the `manual` tag, and the `already a lead` indicator.
- **backend — keyword library** (REQ-SRCH-09): five tables hold the title word-pair scores, the role keyword scores, and the junk, seniority and keep lists that clean a title, all from the files under `reference/`. The seed generator loads them into every database. `title_keyword_v1` scores a title from those tables and the track's search keywords in pure Python, and needs neither nltk nor scikit-learn.
- **backend — system promotion** (REQ-CRM-01, Workflow 4): at the end of a search run, the service promotes each post found by the run's track that is open, has its detail, passes the track's screen (score at or above `min_match_score`, age within `max_age_weeks`) and has no lead for the user, by calling the lead service's `promote` function, the write path behind `POST /api/v1/lead`, with the run's `track_id`. The lead starts at `TOAPPLY` with the profile's `min_salary` as its `expected_salary_sgd`, and a post promoted by an earlier run is skipped. The Posts page offers no promote control.
- **frontend — Manual Post Entry dialog** (**user interface** page 4) and the inline track-assignment editor it returns to.
- **run-status/error surfacing** (REQ-FE-02): a failed run, a rejected `409` trigger, or a rejected profile write surfaces in the UI through the **user interface** design's cross-cutting error-surfacing pattern.

Out of scope:

- the `lead`/`lead_note`/`lead_event` write path, the promote endpoint's own hook logic, the Leads page (**user interface** page 5), and the Lead Detail panel (page 6) — milestone 09, job leads tracking. This milestone's search run calls that write path for each qualifying post. Milestone 09 owns that endpoint, its invariants, and every screen that exists once a lead exists.
- apply automation, the apply state machine, CV assignment to a track's default, the apply-queue/results screens (page 7), and the Automation/session screen (page 8) — milestone 11. Track's `default_cv_id` picker renders on page 1 as part of that form, but the apply-time behavior behind it is milestone 11's.
- an OS-level scheduler of any kind — cron entry, systemd timer, APScheduler, Celery beat, or a second process. Explicitly refused by the **architecture**'s out-of-scope list and `ARCH-SCHED-01`'s rejected alternatives. REQ-SRCH-11 is satisfied only by schedule state the UI edits and the app reads.
- `track`/`search_profile`/`search_schedule`/`post`/`post_track`/`match_score`/`run_log` schema and seed-data generation beyond this milestone's own data model update above — delivered by milestone 08. This milestone reuses that seed set, extending it only where Design finds a concrete gap (e.g. a profile with a schedule already due, needed to exercise the tick path).
- NLP/semantic match scoring and salary-percentile scoring — release-wide exclusions (**requirements** Out of scope); `010` ships only the primitive title-keyword method, recorded with its `score_method` so `020` can add another scoring method against the same schema.
- any analytics/BI/reporting pipeline — ETL, warehouse, cross-run dashboards — explicitly out of scope release-wide. "Run reporting" for this milestone means only the run-status polling and `run_log` reads already specified above.
- accounts, sign-in, and the ownership layer itself — feature 13. This milestone's services take the owning user id explicitly and its routes rely on the ownership layer feature 13 delivers, per `ARCH-AUTH-04` and `ARCH-AUTH-08`.
- any request against the live MCF site, and any read of a real session cookie export, run automatically or on an agent's own initiative (**project boundaries**, REQ-DEV-03/04, `ARCH-TEST-06`). Development, automated tests, and every agent-run validation loop use `MCF_MODE=fixture` against the fixture corpus and seed data by default. The live-tier case above is the one deliberate exception, and it is always a human-triggered action, never automatic.

## Test strategy

Five independent-verification layers. Each layer follows a release-level strategy id.

- `STRAT-TOOL-01..04` the `api_tester.py`/`ui_tester.py` standalone utilities milestone 12 built, one per silo
- `STRAT-SILO-05/06` component-silo, service-layer proof of the search-run pipeline against the fixture corpus, before mock e2e
- `STRAT-02` backend-only, mock e2e, then live, human-gated
- `STRAT-HUMAN-01/02` a human's secondary UI pass, last, once every automated layer is green

01. **self-report, one utility per silo** — case-config replay against a running instance, each case a `PASS`/`FAIL`/`ERROR` verdict. The backend API silo uses `api_tester.py` and the frontend silo uses `ui_tester.py`, per `STRAT-TOOL-01`. Weakest alone, since a verdict proves a response shape or a rendered element, not that a write persisted correctly or that scoring and dedup logic is right.
02. **direct inspection** — `db_util.py` queried against the same database a case just wrote to, bypassing the API/UI response entirely. This is what proves dedup, the closed-post flag, and the scheduler's own column state, instead of trusting a response body.
03. **oracle** — hard-coded-expectation pytest, mostly at the service layer per `STRAT-SILO-05` (`easymcf/services/search.py` called directly against the fixture browser, `easymcf/automation/fixture.py`), for the pipeline logic no HTTP-shape check can prove: dedup id computation, the detail pass's open-check short-circuit, per-track scoring, and the scheduler's collision and coalescing arithmetic against a controlled clock. Expected values are hard-coded from this milestone's own Scope/closure text and the fixture corpus, never imported from the code under test.
04. **live-tier** — a human-triggered `pytest -m live --run-live` run against the real MCF site, per REQ-DEV-05/`ARCH-TEST-06`, run only after every layer above passes. It confirms real MCF markup still matches the fixture corpus. The layers above already own pipeline logic.
05. **human validation** — per `STRAT-HUMAN-01`, the last step: a person clicks through the real running app once every automated layer, including the live tier, is green, following a short checklist derived from this milestone's own closure criteria. It catches what an automated assertion was not written to check, such as a layout issue, a confusing error message, or an awkward control.

**backend validation utility gap**: `api_tester.py` replays one request per case and compares exact status and body equality. A search run is asynchronous, so `POST /api/v1/runs/search` returns a `run_log.id` while the run thread is still working, and the run's outcome (posts persisted, terminal status, counts) appears only later. Cases 10.TC.04, .05 and .07 need a poll step: trigger, poll `GET /api/v1/run_log/{id}` until a terminal status or a timeout, then assert on the final body. Per `STRAT-TOOL-04`'s reuse-first rule this extends `api_tester.py` in place, scoped in this milestone's Scope, and the extension's own classification is checked by oracle case 10.TC.23. Cases 10.TC.11..16 read the resulting rows with `db_util.py` once a poll returns.

## Design

The design fixes search behavior tightly enough that every case in Test cases has one expected result. It runs from workflow, through the algorithms that decide outcomes, to storage, structure, the API surface, the screens and the validation utility. Every request and thread acts for one signed-in user, so ownership is part of each section. The closing table maps each design element to its cases. Per-file detail belongs to Edit locations.

**Design docs this feature updates**, so each states the same design:

01. **workflows**: Workflow 2 scores each card when its page is persisted and ends with the promotion step. Workflow 3 states the filing rule for manual posts.
02. **data model**: the `run_log.trigger_source` column, the `outcome_counts` key set, the five keyword library reference tables, and the `post_track` and `match_score` write rules.
03. **architecture**: orphaned-run reconciliation for every user next to `ARCH-RUN-03`, the two new variables in `ARCH-RUN-07`, the two `MCFBrowser` methods in `ARCH-BOT-02`, and the fixture scenarios in `ARCH-TEST-04`.
04. **api design**: the joined `post` read, the `post_track` write hook, the manual entry response, and the `run_log` poll shape.
05. **user interface**: page 1's description of a new track's default search profile, and the `already a lead` indicator on page 3.
06. **frontend app**: the Posts row of the screen-to-service table.
07. **test data**: the five keyword reference files and the generator rows that load them.

### Workflow

**Search run** (Workflow 2, REQ-SRCH-02..06, REQ-SRCH-08/09).

01. **Trigger.** `POST /api/v1/runs/search {track_id}` and the scheduler both call one service function, `start_run(uid, track_id, trigger_source)`. It checks that the track is visible to `uid`, is active and has a search profile. It then inserts a `run_log` row with `user_id`, `status='running'` and the caller's `trigger_source`. The insert is the concurrency guard. `ARCH-RUN-03`'s partial unique index on `(user_id, run_type)` rejects a second running search by the same user, and `start_run` raises `RunInFlight(run_id)` for the endpoint to return as `409` and for the scheduler to log and skip. On success a background thread takes over with its own connection and its own browser context, per `ARCH-RUN-02` and `ARCH-RUN-04`. Runs of different users proceed side by side.
02. **Sweep.** For each keyword in the search profile the thread requests search pages 0, 1, 2 and so on, until a page has no cards. Each page is parsed, persisted and committed before the next page is requested (REQ-SRCH-04).
03. **Persist and score.** Within a page's transaction each card becomes a `post` row when its id is new. The card's title is scored against the run user's active tracks. The searched track always receives a pairing, and any other active track receives one when its score is above 0. Each pairing is a `post_track` row with its `match_score` row. When the searched track's own search returns a post that already has a pairing for it, that pairing's `search_match` becomes true. `run_log.outcome_counts` is updated in the same transaction, so a poll after any commit shows real progress.
04. **Detail pass.** After the last keyword, every open scraped post that has no detail yet and is visible to the run user is fetched from its own detail-page URL, newest first, one commit per post. Posts are shared, so a fetched detail serves every user who sees the post.
05. **Promote.** The run promotes every qualifying post under the run's track
06. **Close.** The run ends with a terminal status, `ended_at` and the final `outcome_counts`.

Scoring reads only the card's title, so it happens at persist time. A run interrupted before its detail pass still leaves scored pairings, and the next run's detail pass and promotion complete them.

**Promotion** (Workflow 4, REQ-CRM-01). Promotion is a system action and the Posts page offers no control for it. The last step of a run calls the lead service's promote function once for each qualifying pairing, highest score first, each call in its own transaction. A pairing qualifies when all of these hold.

01. the run user has no lead on the post, whichever stage the lead has reached.
02. it belongs to the run's track and has `search_match` true.
03. its post is open and detailed, meaning `mcf_ref` is set. A post whose detail fetch failed waits for a later run, so its deadline is computed from a real closing date.
04. it passes the screening rule.

The promote function 

01. create the lead at `TOAPPLY` under the run's track
02. copy the post's title, company and URL
03. compute the deadline
04. copy the profile's `min_salary` as the expected salary
05. write the first activity event. 

A post that two of a user's tracks both found is filed under whichever run promotes it first. A promotion that raises an exception is counted, ends the run as `partial`, and leaves the other posts unaffected.

**Interrupted runs.** A process that dies mid-run leaves its `run_log` row at `running`, and the partial unique index would then refuse every later search by that user. Startup therefore reconciles. Before the server accepts requests and before the scheduler starts, every `running` row of every user becomes `failed`, with `ended_at` set and `error_detail='interrupted: process stopped before the run finished'`. Posts committed before the stop remain (REQ-SRCH-04).

**Scheduled run** (REQ-SRCH-11, `ARCH-SCHED-01..06`). The tick thread wakes every `SCHEDULER_TICK_S` seconds and calls `tick(conn, now)`. The tick selects schedules that are enabled, belong to an active track, and have `next_run_at` null or at or before `now`, oldest first, across all users. For each it calls `start_run` with the track owner's id and `'scheduled'`. On success it advances `next_run_at`. On `RunInFlight` it logs one line naming the track and the in-flight run, leaves `next_run_at` untouched and skips the remaining due schedules of that user for this tick, because each of them would collide too. Schedules of other users continue in the same tick. A skipped schedule is retried on the next tick and fires once that user's running search ends. Two tracks of one user due at the same instant run one after the other, and tracks of different users run concurrently.

**Manual post entry** (Workflow 3, REQ-SRCH-07). `POST /api/v1/posts/manual` derives the post id with the same rule as a scraped post. The service writes the post on the server, since users never write a `post` row directly.

01. A post whose id exists and is visible to the user answers `409` naming the existing post. A post whose id exists but is not visible is reused, and only the user's own rows are written.
02. A new post is inserted with `src_method='manual'`.
03. The title is scored against every active track of the user. Each track that scores above 0 receives a `post_track` (`search_match=false`) and `match_score` pair.
04. The post is promoted on save, whatever its score, under the assigned track with the highest score. When no track scores above 0, the lead goes under the user's active track with the lowest id and that track receives a pairing as well. A user with no active track receives `409`.
05. The response lists the assigned tracks with their scores and the new lead's id, so the dialog opens its track-assignment editor without a second request.

Screening lets a manual post through for its assigned tracks, since a lead already exists for it.

**Track assignment and rescoring** (REQ-SRCH-07/08). The editor on a post adds a track, removes a track, or edits a score.

01. Adding a track creates a `post_track` row with `search_match=false` and scores the pairing with the function a run uses. The post and the track must both be visible to the user.
02. Removing a track deletes the `match_score` row and then the `post_track` row. An existing lead is unaffected.
03. Editing a score writes `match_score` and `score_method='manual'` on the existing row. `search_match` is written only by the sweep, when the track's own search returns the post, and by an added track, as false. Every existing pairing keeps its provenance through each edit.

**Track and search configuration** (Workflow 1, REQ-SRCH-01/10/11). Creating a track also creates its `search_profile` row, with `keywords` set to the role name and the default values for the other columns, and its `search_schedule` row with `schedule_enabled=0`. Both rows are written in the track's transaction, so the data model's exactly-one-per-track holds from the first moment. Page 1b then edits both rows with plain updates. Archiving is `PUT {is_active: false}`. A run request for an archived track answers `409`, and the scheduler skips its schedule.

**Ownership.** The ownership layer scopes every generic read and write. Each service function that a request or thread calls takes the user id and confirms visibility of each id it receives. The joined `post` read composes the ownership layer's `post` predicate, so a user sees a post through their own tracks or leads. `post`, `title_tag` and `keyword_tag` are shared, and no user writes them. Another user's row answers `404`.

### Algorithms

**Post identity and card parsing** (REQ-SRCH-03/05). A card yields `urlid`, the link path after `/job/` without its query string, plus title, company, salary and posted text. The stored `url_ref` is the full posting URL. Relative posted text resolves against `clock.today()`: "today" is the date itself, "yesterday" is one day earlier and "N days ago" is N days earlier. The post id is `source-urlid[-32:]-posted_date`, for example `MyCareerFutures-0123456789abcdef0123456789abcdef-2026-09-16`. Relative text shifts by one day as calendar days pass, so a posting keeps one posted date and one id across runs. A manual post takes its source and reference from an MCF job URL when one is given, so it matches the scraped copy of the same posting. Otherwise its source is `Manual` and its reference is the first 32 hex characters of a SHA-1 over title and company.

**Sweep termination and errors** (REQ-SRCH-03). A keyword's sweep ends at the first page with no cards. The salary filter is the profile's `min_salary` when set, and the employment type is the profile's value. A page fetch that raises is retried twice with an explicit bounded wait. A third failure ends that keyword's sweep, records `error_detail`, and lets the next keyword proceed.

**Detail pass** (REQ-SRCH-06). Candidates are visible posts with `src_method='scraped'`, `is_open=1` and `mcf_ref IS NULL`. For each, the detail page is parsed in this order.

01. read the open or closed marker first. A closed marker sets `is_open=0` and stops. The card columns stay as they are and the detail columns stay null.
02. read `mcf_ref`, `closing_date`, `applicants`, `industry_classification` and `description`, then commit.
03. a page whose marker is absent raises a parse error. The post stays a candidate for the next run and the run counts a `detail_errors`.

A fetch failure follows the same path as a parse error. Manual posts skip the detail pass because their fields come from the user. Two users' runs may fetch the same post, and the update is idempotent. A lead keeps the title, company, URL and deadline it copied at promotion, so a later detail pass never rewrites a lead.

**Scoring, `title_keyword_v1`** (REQ-SRCH-09). The score is a pure function of a post title, a track and the keyword library, in the range 0 to 1, rounded to two places. It reads no salary or industry value and needs neither nltk nor scikit-learn. Three signals add to a net count, and each distinct tag or phrase counts once however often it occurs.

01. **title tags.** Every adjacent word pair of the cleaned title that appears in `title_tag` adds that tag's score of -1, 0 or 1.
02. **keyword tags.** Every keyword phrase of the track's groups that appears in the cleaned title as adjacent words adds that phrase's score. A track's groups are `others` plus every `keyword_tag` group whose name appears as a whole phrase in the lowercased role name. The role Sustainability Consultant takes the `sustainability` and `consultant` groups, and Data Scientist takes `data scientist`. A role that names no group takes `others` alone.
03. **search keywords.** Every phrase of the track's search profile `keywords`, split on commas, that appears in the cleaned title as adjacent words adds 1.

```python
def score_title(title, track, lib):
    words = clean(title)
    net = sum(lib.title_score(pair) for pair in distinct_pairs(words))
    net += sum(s for phrase, s in lib.keyword_phrases(track.groups) if contains_run(words, phrase))
    net += sum(1 for phrase in track.search_phrases if contains_run(words, phrase))
    return round(net / (net + 1), 2) if net > 0 else 0.0
```

A net count of 0 or less scores 0. Net counts of 1, 2, 3 and 4 score 0.5, 0.67, 0.75 and 0.8, so more matching evidence ranks higher and the score never reaches 1. With the reference files as delivered, a Data Scientist track searching "Data Scientist, Machine Learning" scores the title "Data Scientist" at 0.5, "Machine Learning Engineer" at 0.8 and "Warehouse Management Officer" at 0. The default `min_match_score` of 0.3 therefore admits any title with a positive net count.

`clean` runs four steps in order. It lowercases the text and replaces every run of characters other than letters and digits with one space. It drops the English stopwords, except any word listed in `keep_tag`. It removes every phrase listed in `junk_tag`, longest phrase first, as whole words. It removes every word listed in `rank_tag`. The stopword set is a fixed constant in the scoring module that holds the common English stopwords. Tag and phrase text goes through the same cleaning, so a tag such as `wire-bonding` matches the words wire bonding. The source titles behind the title library went through this same cleaning, so it must precede every lookup. Cleaning turns "Senior Data Scientist (AI), Asia Pacific" into the words data, scientist and ai.

**implementation decision**: the title library stores the word pairs the prototype's vectorizer extracted, with the user's score for each, so scoring looks them up directly. The prototype took its stopwords from nltk. The scoring module holds a constant list of the same kind, so scoring imports neither nltk nor scikit-learn. `rank_tag.weight_score` is stored with the library and scoring never reads it. The scoring method name leaves room for a `020` replacement.

**Screening** (REQ-SRCH-09). A pairing is visible on Posts when its post is open and one of these holds.

01. the post is manual.
02. the post's age in days is at most 7 times the track's `max_age_weeks`, and its score is at least the track's `min_match_score`. A null `max_age_weeks` removes the age limit.

The include-below-threshold toggle drops the second condition and keeps the open check. Results sort by score descending, then posted date descending.

**Schedule advance** (`ARCH-SCHED-03`). After a scheduled run starts, `next_run_at` becomes the first whole-interval step strictly after `now`, so missed windows collapse into one run.

```python
def next_run_after(next_run_at, interval_hours, now):
    step = timedelta(hours=interval_hours)
    if next_run_at is None:
        return now + step
    return next_run_at + step * ((now - next_run_at) // step + 1)
```

With a 24-hour interval, `next_run_at` of 2026-09-16 08:00 and `now` of 2026-09-19 10:00, three whole intervals have passed, one run starts, and the next value is 2026-09-20 08:00. Only a started run calls this function.

**Run status and counts.** A run finishes `success` when every keyword's sweep, every detail fetch and every promotion completed. It finishes `partial` when at least one keyword ended on a fetch failure, at least one detail fetch errored, or at least one promotion raised, and posts were still persisted. It finishes `failed` when an unhandled exception ended it, or when every keyword failed. `outcome_counts` is a JSON object with these keys: `mcf_mode`, `keywords`, `pages`, `cards`, `new_posts`, `existing_posts`, `detailed`, `closed`, `detail_errors`, `promoted`, `promote_errors`. `mcf_mode` records `fixture` or `live`, per `ARCH-BOT-04`. The Posts running state renders "{cards} postings found, page {pages}" from two of them.

### Data model

The data model update adds a run provenance column and the keyword library, which is five tables. The current schema already carries the `search_schedule` table and the per-user `run_log` columns and running index, so the update checks that they are present and adds only what is missing. Version numbers follow the Schema versions table at implementation time.

01. `run_log.trigger_source`: `TEXT NOT NULL DEFAULT 'manual' CHECK (trigger_source IN ('manual', 'scheduled'))`.
02. `title_tag`: `tag TEXT PRIMARY KEY`, `industry TEXT`, `count REAL`, `score INTEGER NOT NULL CHECK (score IN (-1, 0, 1))` and `note TEXT`. A row is a cleaned word pair with the user's score for it. The reference file holds 935 rows.
03. `keyword_tag`: `group_name TEXT NOT NULL`, `tag TEXT NOT NULL`, `score INTEGER NOT NULL CHECK (score IN (-1, 0, 1))` and `PRIMARY KEY (group_name, tag)`. A row is a keyword phrase of one role group with the user's score for it. The reference file holds 1,023 rows in 18 groups.
04. `junk_tag`: `tag TEXT PRIMARY KEY`. A row is a word or phrase removed from titles and phrases before scoring. The reference file holds 73 rows.
05. `rank_tag`: `tag TEXT PRIMARY KEY` and `weight_score REAL NOT NULL`. A row is a seniority word removed before scoring, with a weight that scoring does not read. The reference file holds 23 rows.
06. `keep_tag`: `tag TEXT PRIMARY KEY`. A row is a word that stays although it is an English stopword. The reference file holds 1 row.
07. `post`, `post_track` and `match_score` keep their shape. `post.mcf_ref` doubles as the detail-done marker. The existing indexes cover the joined read.
08. The `run_log` closed vocabularies keep their values. A skipped scheduler tick writes no row, per `ARCH-SCHED-05`.

A score of 1 marks a target signal, 0 a neutral one and -1 an off-target one. The five library tables are shared reference tables like `role`. They carry no owner column, no API resource exposes them, and only the scoring service reads them, once per run, into memory. Neither table needs a declaration in the ownership layer. An empty library leaves scoring to the track's search keywords alone.

### Seed data

The keyword library loads through the seed generator. The five reference files sit in the committed `reference/` directory, since they hold no personal data.

01. `scripts/gen_test_data.py` gains `_map_title_tag`, `_map_keyword_tag`, `_map_junk_tag`, `_map_rank_tag` and `_map_keep_tag`. Each reads its file, strips a byte order mark, Windows line endings and surrounding whitespace, lowercases the `tag` column, and emits one `INSERT` per row in file order, so regeneration is byte-stable. `_TABLE_ORDER` places both tables after `role`, and the seed files take their numbers from that order.
02. `group` in the source file maps to `group_name`, since `group` is an SQL keyword. Every other column maps by name.
03. The generator validates the output against a scratch database as it does for every table. Row counts equal the source files' data rows, so a file whose last line has no line ending loads completely.
04. Both generator modes emit the tables, since scoring needs them in every database.
05. A change to a reference file reaches a database through regeneration and a reset.

The rest of the seed set keeps its shape and gains three things. Each existing `run_log` row carries `trigger_source='manual'` by default. At least one seeded search `run_log` row carries `trigger_source='scheduled'`, on a track that the scheduled-run case does not schedule, so both values appear and the seed oracle's enumeration check extends to the new column (`STRAT-CASE-05`). The seeded posts keep the manual, multi-track, closed and already-a-lead rows the frontend cases assert against. With two seeded users, each user's posts, pairings and leads stay distinct, and one post is paired to a track of each.

**Modules.** Pure functions sit apart from the code that does I/O, so the oracle cases reach them directly.

01. `easymcf/automation/parsing.py` holds `parse_cards(html, today)` and `parse_detail(html)`. Both are pure, built on BeautifulSoup with html5lib.
02. `easymcf/services/scoring.py` holds `clean`, `TagLibrary`, which loads the five library tables from a connection, and `score_title`.
03. `easymcf/services/search.py` holds `post_id`, `start_run`, `run_sweep`, `run_detail_pass`, `promote_qualifying`, `screened_posts`, `add_manual_post`, `assign_track`, `remove_track` and `reconcile_orphaned_runs`.
04. `easymcf/services/scheduler.py` holds `next_run_after`, `tick` and the loop that `__main__.py` starts.
05. `easymcf/automation/browser.py` gains two `MCFBrowser` methods, `search_page(keyword, min_salary, page)` and `detail_page(url_ref)`, each returning page HTML after an explicit wait on a card, the empty-results marker, or the detail marker. `live.py` and `fixture.py` implement them behind the same interface, per `ARCH-BOT-02`. **Threading and connections.** Each run thread and the tick thread open their own SQLite connection per `ARCH-STO-07`. A run thread carries its user id from the track row for its whole life. It commits after every page and every detail post, so a kill loses at most the page in flight. All current-time reads go through `clock.now()`. `create_app()` starts no thread, per `ARCH-SCHED-06`.

**Fixture corpus.** `ARCH-TEST-04`'s layout gains what the cases need. ### API endpoints

All routes require a signed-in user and answer `401` otherwise.

| id | endpoint                                  | classification            | responsibility                                          |
| -- | ----------------------------------------- | ------------------------- | ------------------------------------------------------- |
| 01 | `POST`/`PUT /api/v1/track`                | CAT-02 hook, create only  | create also writes the default profile and schedule     |
| 02 | `PUT /api/v1/search_profile/{track_id}`   | CAT-01 generic            | edit search criteria                                    |
| 03 | `PUT /api/v1/search_schedule/{track_id}`  | CAT-01 generic            | edit schedule, with `schedule_interval_hours` of at least 1 |
| 04 | `POST /api/v1/runs/search`                | CAT-03 named, `API-EP-04` | start a run, `201`, or `409` with the in-flight id      |
| 05 | `GET`/`search /api/v1/run_log`            | CAT-02 hook, read-only    | poll a run, `outcome_counts` returned as an object      |
| 06 | `GET`/`search /api/v1/post`               | CAT-02 hook, read-only    | joined and screened read for a track                    |
| 07 | `POST /api/v1/posts/manual`               | CAT-03 named, `API-EP-01` | manual entry, track assignment and promotion            |
| 08 | `POST`/`DELETE /api/v1/post_track`        | CAT-02 hook               | assign and remove a track, scoring on assign            |
| 09 | `PUT /api/v1/match_score`                 | CAT-01 generic            | edit a score, sent with `score_method: "manual"`        |

**Trigger validation.** A missing `track_id` is `400`. An unknown track, or a track owned by another user, is `404`. An archived track and a run already in flight are `409`. The in-flight body carries the running run's id.

**Joined read** (row 06). With a `track_id`, each returned row carries the post's columns without `description`, plus `match_score`, `score_method`, `search_match` and `lead_id`. `lead_id` is the id of the caller's own lead on the post, or null. Optional parameters `min_match_score`, `max_age_weeks` and `include_below_threshold` override the profile's defaults. `GET /api/v1/post/{id}` returns the full row with its description. The `post` resource offers reads only.

**implementation decision**: the joined read gives screening one server-side implementation, which the cases test without a browser. It also keeps list payloads small, since a track's posts carry full descriptions and the source data holds over 3,500 track-post pairings. `post_track` writes go through a hook so that assigning a track always scores the pairing, and a pairing never exists without its `match_score` row. The `track` create hook gives every new track its profile and schedule rows.

### Validation utility extension

`api_tester.py` gains one optional `poll` block on a case, so a case can trigger asynchronous work and assert on where it ends. The request and `expected_status` behave as they do today. After a matching response the tester polls the given path once a second until the `until` condition holds or `timeout_s` passes, then compares the final body to `expected_final` as a subset. Polling requests use the case's signed-in session, so a case that runs as a named seeded user polls as that user.

```json
{"name": "trigger search and wait", "as_user": "user1", "method": "POST", "path": "/api/v1/runs/search",
 "body": {"track_id": 1}, "expected_status": 201,
 "poll": {"path": "/api/v1/run_log/{id}", "until": {"status": ["success", "partial", "failed"]}, "timeout_s": 60},
 "expected_final": {"status": "success"}}
```

`{id}` takes the `id` from the response body. When the polled body is a list, the condition holds once any element satisfies it, and that element becomes the final body. A poll that reaches `timeout_s` classifies `ERROR`, a final body that misses `expected_final` classifies `FAIL`, and a match classifies `PASS`. Existing case files, the three outcome classes and the log format keep their current behavior.
