# Search By Keywords - Feature tracker
>Review the guidelines before performing any actions including edits on the document

## 010.10 (open) search by keywords

Implements the **requirements** doc's Search by keywords section (REQ-SRCH-01..07, REQ-SRCH-10/11) and the search-facing half of REQ-FE-01/02: configuring a track and its search profile, triggering a search run on demand or on a user-configured schedule, executing the scrape → incremental-persist → dedup → detail-pass → promote pipeline against MCF, folding manually-entered posts into that same pipeline, and giving the user the Posts/results screen to review what a run produced. Builds on the schema and seed data milestone 08 delivered for `track`/`search_profile`/`post`/`post_track`/`match_score`/`run_log`, and carries the data model update for run provenance and the `lead.close_reason` addition below.

Every post a track's own search finds is a fixed, unweighted match: `match_score` is a constant `1.0` for every card the search returns, recorded with `score_method='search_match_v1'` so the value's provenance is explicit rather than implied. A post found this way promotes straight to a lead at `TOAPPLY` once its detail pass completes, with no relevance screen in between — the track's own keywords already decided relevance by producing the result in the first place. A lead that turns out not to actually fit the track it was promoted under is dropped with `close_reason='track_not_matched'`, a distinct value from `withdrawn`, so the pipeline/CRM history can tell "the track's keywords over-matched this one" apart from "this was a real fit and the user changed their mind." Differentiated relevance scoring — a model that ranks one match above another rather than treating every result alike — is milestone 16's own deliverable ([010.16-position-title-score-model.md](010.16-position-title-score-model.md)), built and evaluated independently of this milestone and swapped in later purely by adding a new `score_method` value; this milestone's schema and workflow already carry that value on every scored row for exactly that reason.

## Scope

Build the search-by-keywords feature end to end both ways a search run starts, the run pipeline itself, and the AngularJS screens (**user interface** pages 1, 1b, 3, and the page 4 manual-entry dialog) that let a user configure, trigger, and review what a run produced. A triggered run, manual or scheduled, performs a fresh MCF search from the configured search profile and upserts the unique posts it finds incrementally across repeated runs, and every post it finds becomes a lead — the track's own search keywords are the only relevance filter this milestone applies.

In scope:

- **backend — track, search profile, and search schedule CRUD** (REQ-SRCH-01, REQ-SRCH-10, REQ-SRCH-11): `track`, `search_profile`, and `search_schedule` as `API-CAT-01` pure generic resources per the **api design**, each keyed on `track_id`, with track archive/unarchive as a plain `PUT {"is_active": false}`. `search_schedule` carries the three schedule columns (`schedule_enabled`, `schedule_interval_hours`, `next_run_at`) the **data model** defines for REQ-SRCH-11, so configuring a schedule is a plain generic write on its own resource. This milestone's routes ride on the generic CRUD blueprint the **api design** defines.
- **backend — data model update** (`ARCH-STO-02/03`, **data model** Schema versions table): edit `easymcf/db/schema.sql` to add `run_log.trigger_source` and the `track_not_matched` value to `lead.close_reason`'s check constraint, after checking that the `search_schedule` table and the per-user `run_log` columns are already present. Bump `meta.schema_version` to the next value per the **data model**'s Schema versions table and the matching `easymcf/__init__.py` constant, extend `scripts/gen_test_data.py` to emit the new column's values, and re-run `scripts/resetdb.py --seed`. Recreate-don't-migrate stays in force, per `ARCH-STO-02`. Revising this feature's own shapes, if implementation surfaces a need to, is in scope here too. This feature keeps the **data model** and **architecture** docs current with whatever ships.
- **backend — run trigger** (REQ-SRCH-02): `API-EP-04 POST /api/v1/runs/search`, which inserts the `running` `run_log` row for the signed-in user (`trigger_source='manual'`), starts the background thread per `ARCH-RUN-02`, and returns the `run_log.id` immediately. A second trigger by the same user while that user's search run is in flight returns `409` with the in-flight id, enforced directly by `ARCH-RUN-03`'s partial unique index on the user and run type at insert time. A track owned by another user answers `404`.
- **backend — scheduler** (REQ-SRCH-11, `ARCH-SCHED-01..06`): the in-process tick thread that reads due `search_schedule` rows through `clock.py::now()`, calls the same run-trigger service function `API-EP-04` calls, writes `trigger_source='scheduled'`, advances `next_run_at` in whole interval multiples so missed windows coalesce into one run, and skips and logs the collision when it meets a run of the same user already in flight, retrying on the next tick, while the due schedules of other users proceed. Started by `__main__.py` at app startup, and governed by `SCHEDULER_ENABLED`/`SCHEDULER_TICK_S`.
- **backend — search run pipeline** (REQ-SRCH-03..06): a fresh MCF search
    - All MCF interaction goes through `ARCH-BOT-02`'s `MCFBrowser` seam, so the same code path runs in `fixture` and `live` mode.
    - per the configured profile's keyword(s)/salary/age
    - paginating until a page returns no results
    - parse url/title/company/reference/posted date/salary from each card
    - persist posts **as they are found** (REQ-SRCH-04)
    - deduplicate on the `source + posting_reference + posted_date` post id so a re-run upserts existing posts (REQ-SRCH-05)
    - run the detail pass, one page load per posting's own detail-page URL, as a distinct second sweep over posts without detail yet, per the **prototype extraction**'s `mcf_profile.py::get_profileRecord()`. That page carries `closing_date`/`applicants`/`industry_classification`/`mcf_ref`/`description`, none of which the search-results card exposes.
    - check that page's open/closed state first, before scraping its other fields, the same short-circuit the **prototype extraction** uses: a closed posting skips the rest of the detail scrape entirely, since those fields are meaningless for a listing no longer live.
    - a post found closed there gets its `post.is_open` flag flipped to `false` (REQ-SRCH-06); the row itself stays. This is a deliberate deviation from the **prototype extraction**'s `db.remove_jobs()`, which hard-deletes a closed posting from its `job` table. `010`'s soft flip, the same shape the **data model** already uses for `track.is_active`, keeps the row and its description readable for any lead already promoted from it. Only its membership in the active set, filtered `WHERE is_open = 1`, changes.
    - a posting whose detail fetch errors is left undetailed, so the next run's set-difference naturally retries it, per the **prototype extraction**'s `failed` list.
    - record every matched card's `post_track`/`match_score` pair with the fixed score.
- **live-tier validation of the search-run pipeline** (REQ-DEV-05, `ARCH-TEST-06`): this milestone is the first to populate milestone 07's empty `tests/live/` scaffold with a real case, a `pytest -m live --run-live` search run against the real MCF site using a valid `.secrets/mcf_session.json`. It runs only after the fixture-tier and mock-e2e-tier cases for the pipeline pass, per the **test strategy**'s STRAT-02 ordering, backend-only first, mock e2e second, live third. Its job is confirming MCF's real markup still matches the fixture corpus it was captured from, not discovering pipeline logic defects, which the fixture-tier cases already own. No agent triggers this tier on its own initiative, per `ARCH-TEST-06`, and a human runs it deliberately once the earlier tiers are green.
- **backend — manual post entry** (REQ-SRCH-07): `API-EP-01 POST /api/v1/posts/manual`, which creates the `post` row with `src_method='manual'`, reusing an existing shared post the user cannot yet see and answering `409` for one the user already sees. The request names the one track the post belongs to; the service writes that track's `post_track` (`search_match=false`) and `match_score` (fixed `1.0`, `score_method='manual_v1'`) pair in the same request, then promotes the post to a lead at `TOAPPLY` under it. A user with no active track receives `409`.
- **backend — run status read** (REQ-PLAT-03, REQ-FE-02): `run_log` `GET`/`search` as the polling surface for a running search, including `trigger_source` so the run history answers whether last night's schedule actually fired.
- **backend — validation utility extension** (`STRAT-TOOL-01/04`): extend `scripts/api_tester.py` in place with a poll step, so a case can trigger `POST /api/v1/runs/search`, poll `GET /api/v1/run_log/{id}` until a terminal status or a timeout, and assert on the final body. Milestone 12 built `api_tester.py` as single-request exact-equality replay, and a search run is asynchronous (`ARCH-RUN-02`), returning a `run_log.id` before any post exists, so a run's outcome has no standalone check today. This milestone is the first consumer of that gap and owns the extension. Existing case-file fields, the `PASS`/`FAIL`/`ERROR` classes and the log format stay as they are.
- **frontend — Tracks page** (**user interface** page 1): list/create/edit a track's identity, role and seniority, the default-CV picker, and the archive/unarchive action plus the show-archived toggle (REQ-SRCH-10), with a "Configure search" link per track into Search Profiles (page 1b). This page owns track identity and lifecycle. Search configuration lives on Search Profiles (page 1b), and the run trigger lives on Posts (page 3).
- **frontend — Search Profiles page** (**user interface** page 1b): one form per track, reached from Tracks, presenting the keyword/salary/age/employment-type search criteria (REQ-SRCH-01) and the three schedule fields (REQ-SRCH-11) together, backed by the `search_profile` and `search_schedule` resources for that track. This page owns search configuration only. Track identity lives on Tracks (page 1), and the run trigger lives on Posts (page 3).
- **frontend — Posts page** (**user interface** page 3): track selector, "Run search" with the async running/polling state and error banner, the results table sorted by posted date descending, an age filter, the `manual` tag, and the `already a lead` indicator (true for every row this milestone writes, since every result promotes on its own).
- **backend — system promotion** (REQ-CRM-01, Workflow 4): at the end of a search run, the service promotes every post found by the run's track that is open, has its detail, and has no lead for the user yet, by calling the lead service's `promote` function, the write path behind `POST /api/v1/lead`, with the run's `track_id` and the fixed match score. The lead starts at `TOAPPLY` with the profile's `min_salary` as its `expected_salary_sgd`, and a post promoted by an earlier run is skipped. The Posts page offers no promote control, since promotion is unconditional and automatic.
- **frontend — Manual Post Entry dialog** (**user interface** page 4): the track picker described above and the resulting lead, returned in the same response.
- **run-status/error surfacing** (REQ-FE-02): a failed run, a rejected `409` trigger, or a rejected profile write surfaces in the UI through the **user interface** design's cross-cutting error-surfacing pattern.

Out of scope:

- **relevance scoring that differentiates one match from another** assign every matched card the same fixed score
- **matching a post against more than one track**, adding or removing a track association after the fact, and editing a `match_score` value. A post the search finds or a user manually enters carries exactly one `post_track`/`match_score` pair, to the track that found or was given it.
- the `lead`/`lead_note`/`lead_event` write path, the promote endpoint's own hook logic, the Leads page (**user interface** page 5), and the Lead Detail panel (page 6) — milestone 09, job leads tracking. This milestone's search run calls that write path for each found post. Milestone 09 owns that endpoint, its invariants, and every screen that exists once a lead exists, including the drop/close action that records `close_reason`.
- apply automation, the apply state machine, CV assignment to a track's default, the apply-queue/results screens (page 7), and the Automation/session screen (page 8) — milestone 11. Track's `default_cv_id` picker renders on page 1 as part of that form, but the apply-time behavior behind it is milestone 11's.
- an OS-level scheduler of any kind — cron entry, systemd timer, APScheduler, Celery beat, or a second process. Explicitly refused by the **architecture**'s out-of-scope list and `ARCH-SCHED-01`'s rejected alternatives. REQ-SRCH-11 is satisfied only by schedule state the UI edits and the app reads.
- any analytics/BI/reporting pipeline — ETL, warehouse, cross-run dashboards — explicitly out of scope release-wide. "Run reporting" for this milestone means only the run-status polling and `run_log` reads already specified above.
- accounts, sign-in, and the ownership layer itself — feature 13. This milestone's services take the owning user id explicitly and its routes rely on the ownership layer feature 13 delivers, per `ARCH-AUTH-04` and `ARCH-AUTH-08`.
- any request against the live MCF site, and any read of a real session cookie export, run automatically or on an agent's own initiative (**project boundaries**, REQ-DEV-03/04, `ARCH-TEST-06`). Development, automated tests, and every agent-run validation loop use `MCF_MODE=fixture` against the fixture corpus and seed data by default. The live-tier case above is the one deliberate exception, and it is always a human-triggered action, never automatic.

## Test strategy

Five independent-verification layers. Each layer follows a release-level strategy id.

- `STRAT-TOOL-01..04` the `api_tester.py`/`ui_tester.py` standalone utilities milestone 12 built, one per silo
- `STRAT-SILO-05/06` component-silo, service-layer proof of the search-run pipeline against the fixture corpus, before mock e2e
- `STRAT-02` backend-only, mock e2e, then live, human-gated
- `STRAT-HUMAN-01/02` a human's secondary UI pass, last, once every automated layer is green

01. **self-report, one utility per silo** — case-config replay against a running instance, each case a `PASS`/`FAIL`/`ERROR` verdict. The backend API silo uses `api_tester.py` and the frontend silo uses `ui_tester.py`, per `STRAT-TOOL-01`. Weakest alone, since a verdict proves a response shape or a rendered element, not that a write persisted correctly or that scoring and dedup logic is right.
02. **direct inspection** — `db_util.py` queried against the same database a case just wrote to, bypassing the API/UI response entirely. This is what proves dedup, the closed-post flag, and the scheduler's own column state, instead of trusting a response body.
03. **oracle** — hard-coded-expectation pytest, mostly at the service layer per `STRAT-SILO-05` (`easymcf/services/search.py` called directly against the fixture browser, `easymcf/automation/fixture.py`), for the pipeline logic no HTTP-shape check can prove: dedup id computation, the detail pass's open-check short-circuit, the fixed-score write, and the scheduler's collision and coalescing arithmetic against a controlled clock. Expected values are hard-coded from this milestone's own Scope/closure text and the fixture corpus, never imported from the code under test.
04. **live-tier** — a human-triggered `pytest -m live --run-live` run against the real MCF site, per REQ-DEV-05/`ARCH-TEST-06`, run only after every layer above passes. It confirms real MCF markup still matches the fixture corpus. The layers above already own pipeline logic.
05. **human validation** — per `STRAT-HUMAN-01`, the last step: a person clicks through the real running app once every automated layer, including the live tier, is green, following a short checklist derived from this milestone's own closure criteria. It catches what an automated assertion was not written to check, such as a layout issue, a confusing error message, or an awkward control.

**backend validation utility gap**: `api_tester.py` replays one request per case and compares exact status and body equality. A search run is asynchronous, so `POST /api/v1/runs/search` returns a `run_log.id` while the run thread is still working, and the run's outcome (posts persisted, terminal status, counts) appears only later. Cases 10.TC.04, .05 and .07 need a poll step: trigger, poll `GET /api/v1/run_log/{id}` until a terminal status or a timeout, then assert on the final body. Per `STRAT-TOOL-04`'s reuse-first rule this extends `api_tester.py` in place, scoped in this milestone's Scope, and the extension's own classification is checked by oracle case 10.TC.23. Cases 10.TC.11..16 read the resulting rows with `db_util.py` once a poll returns.

## Design

The design fixes search behavior tightly enough that every case in Test cases has one expected result. It runs from workflow, through the algorithms that decide outcomes, to storage, structure, the API surface, the screens and the validation utility. Every request and thread acts for one signed-in user, so ownership is part of each section. The closing table maps each design element to its cases. Per-file detail belongs to Edit locations.

**Design docs this feature updates**, so each states the same design:

01. **workflows**: Workflow 2 writes the fixed match score when its page is persisted and ends with the promotion step. Workflow 3 states the filing rule for manual posts.
02. **data model**: the `run_log.trigger_source` column, the `outcome_counts` key set, and the `post_track` and `match_score` write rules. The keyword library's own table shapes are milestone 16's to add.
03. **architecture**: orphaned-run reconciliation for every user next to `ARCH-RUN-03`, the two new variables in `ARCH-RUN-07`, the two `MCFBrowser` methods in `ARCH-BOT-02`, and the fixture scenarios in `ARCH-TEST-04`.
04. **api design**: the joined `post` read, the `post_track` write hook, the manual entry response, and the `run_log` poll shape.
05. **user interface**: page 1's description of a new track's default search profile, and the `already a lead` indicator on page 3.
06. **frontend app**: the Posts row of the screen-to-service table.
07. **test data**: the seed generator rows this milestone's own schema change (`run_log.trigger_source`) needs; the keyword reference files and the generator rows that load them are milestone 16's.

### Workflow

**Search run** (Workflow 2, REQ-SRCH-02..06).

01. **Trigger.** `POST /api/v1/runs/search {track_id}` and the scheduler both call one service function, `start_run(uid, track_id, trigger_source)`. It checks that the track is visible to `uid`, is active and has a search profile. It then inserts a `run_log` row with `user_id`, `status='running'` and the caller's `trigger_source`. The insert is the concurrency guard. `ARCH-RUN-03`'s partial unique index on `(user_id, run_type)` rejects a second running search by the same user, and `start_run` raises `RunInFlight(run_id)` for the endpoint to return as `409` and for the scheduler to log and skip. On success a background thread takes over with its own connection and its own browser context, per `ARCH-RUN-02` and `ARCH-RUN-04`. Runs of different users proceed side by side.
02. **Sweep.** For each keyword in the search profile the thread requests search pages 0, 1, 2 and so on, until a page has no cards. Each page is parsed, persisted and committed before the next page is requested (REQ-SRCH-04).
03. **Persist and record.** Within a page's transaction each card becomes a `post` row when its id is new. The searched track receives a `post_track` row (`search_match=true`) with a `match_score` row fixed at `1.0`, `score_method='search_match_v1'`. `run_log.outcome_counts` is updated in the same transaction, so a poll after any commit shows real progress.
04. **Detail pass.** After the last keyword, every open scraped post that has no detail yet and is visible to the run user is fetched from its own detail-page URL, newest first, one commit per post. Posts are shared, so a fetched detail serves every user who sees the post.
05. **Promote.** The run promotes every qualifying post under the run's track
06. **Close.** The run ends with a terminal status, `ended_at` and the final `outcome_counts`.

The fixed score needs no title analysis, so it is written at persist time alongside the post itself. A run interrupted before its detail pass still leaves its pairing written, and the next run's detail pass and promotion complete it.

**Promotion** (Workflow 4, REQ-CRM-01). Promotion is a system action and the Posts page offers no control for it. The last step of a run calls the lead service's promote function once for each qualifying pairing, oldest match first, each call in its own transaction. A pairing qualifies when all of these hold.

01. the run user has no lead on the post, whichever stage the lead has reached.
02. it belongs to the run's track and has `search_match` true.
03. its post is open and detailed, meaning `mcf_ref` is set. A post whose detail fetch failed waits for a later run, so its deadline is computed from a real closing date.

The promote function 

01. create the lead at `TOAPPLY` under the run's track
02. copy the post's title, company and URL
03. compute the deadline
04. copy the profile's `min_salary` as the expected salary
05. write the first activity event. 

A post that two of a user's tracks each independently found is filed under whichever track's run promotes it first; the one-lead-per-user-per-post constraint blocks the second. A promotion that raises an exception is counted, ends the run as `partial`, and leaves the other posts unaffected.

**Interrupted runs.** A process that dies mid-run leaves its `run_log` row at `running`, and the partial unique index would then refuse every later search by that user. Startup therefore reconciles. Before the server accepts requests and before the scheduler starts, every `running` row of every user becomes `failed`, with `ended_at` set and `error_detail='interrupted: process stopped before the run finished'`. Posts committed before the stop remain (REQ-SRCH-04).

**Scheduled run** (REQ-SRCH-11, `ARCH-SCHED-01..06`). The tick thread wakes every `SCHEDULER_TICK_S` seconds and calls `tick(conn, now)`. The tick selects schedules that are enabled, belong to an active track, and have `next_run_at` null or at or before `now`, oldest first, across all users. For each it calls `start_run` with the track owner's id and `'scheduled'`. On success it advances `next_run_at`. On `RunInFlight` it logs one line naming the track and the in-flight run, leaves `next_run_at` untouched and skips the remaining due schedules of that user for this tick, because each of them would collide too. Schedules of other users continue in the same tick. A skipped schedule is retried on the next tick and fires once that user's running search ends. Two tracks of one user due at the same instant run one after the other, and tracks of different users run concurrently.

**Manual post entry** (Workflow 3, REQ-SRCH-07). `POST /api/v1/posts/manual` derives the post id with the same rule as a scraped post, and takes the target `track_id` as a required field. The service writes the post on the server, since users never write a `post` row directly.

01. A post whose id exists and is visible to the user answers `409` naming the existing post. A post whose id exists but is not visible is reused, and only the user's own rows are written.
02. A new post is inserted with `src_method='manual'`.
03. The named track receives a `post_track` row (`search_match=false`) with a `match_score` row fixed at `1.0`, `score_method='manual_v1'`.
04. The post is promoted on save under the named track. A track not visible to the user, or an archived one, answers `404`/`409` the same way the run trigger does.
05. The response includes the new post, its one pairing, and the new lead's id, so the dialog can show them without a second request.

**Track and search configuration** (Workflow 1, REQ-SRCH-01/10/11). Creating a track also creates its `search_profile` row, with `keywords` set to the role name and the default values for the other columns, and its `search_schedule` row with `schedule_enabled=0`. Both rows are written in the track's transaction, so the data model's exactly-one-per-track holds from the first moment. Page 1b then edits both rows with plain updates. Archiving is `PUT {is_active: false}`. A run request for an archived track answers `409`, and the scheduler skips its schedule.

**Ownership.** The ownership layer scopes every generic read and write. Each service function that a request or thread calls takes the user id and confirms visibility of each id it receives. The joined `post` read composes the ownership layer's `post` predicate, so a user sees a post through their own tracks or leads. `post` is shared, and no user writes it directly. Another user's row answers `404`.

### Algorithms

**Post identity and card parsing** (REQ-SRCH-03/05). A card yields `urlid`, the link path after `/job/` without its query string, plus title, company, salary and posted text. The stored `url_ref` is the full posting URL. Relative posted text resolves against `clock.today()`: "today" is the date itself, "yesterday" is one day earlier and "N days ago" is N days earlier. The post id is `source-urlid[-32:]-posted_date`, for example `MyCareerFutures-0123456789abcdef0123456789abcdef-2026-09-16`. Relative text shifts by one day as calendar days pass, so a posting keeps one posted date and one id across runs. A manual post takes its source and reference from an MCF job URL when one is given, so it matches the scraped copy of the same posting. Otherwise its source is `Manual` and its reference is the first 32 hex characters of a SHA-1 over title and company.

**Sweep termination and errors** (REQ-SRCH-03). A keyword's sweep ends at the first page with no cards. The salary filter is the profile's `min_salary` when set, and the employment type is the profile's value. A page fetch that raises is retried twice with an explicit bounded wait. A third failure ends that keyword's sweep, records `error_detail`, and lets the next keyword proceed.

**Detail pass** (REQ-SRCH-06). Candidates are visible posts with `src_method='scraped'`, `is_open=1` and `mcf_ref IS NULL`. For each, the detail page is parsed in this order.

01. read the open or closed marker first. A closed marker sets `is_open=0` and stops. The card columns stay as they are and the detail columns stay null.
02. read `mcf_ref`, `closing_date`, `applicants`, `industry_classification` and `description`, then commit.
03. a page whose marker is absent raises a parse error. The post stays a candidate for the next run and the run counts a `detail_errors`.

A fetch failure follows the same path as a parse error. Manual posts skip the detail pass because their fields come from the user. Two users' runs may fetch the same post, and the update is idempotent. A lead keeps the title, company, URL and deadline it copied at promotion, so a later detail pass never rewrites a lead.

**Match score, `search_match_v1`/`manual_v1`** (REQ-SRCH-03). Every card a track's own search returns writes a `match_score` row fixed at `1.0`, `score_method='search_match_v1'`; a manually entered post's chosen-track pairing writes the same fixed value with `score_method='manual_v1'`. Neither reads title text, salary, industry, or any other post field — the track's own search keywords already did the relevant filtering by producing the card at all. 

**Posts display filter.** The Posts screen's age filter hides a row whose post age in days exceeds 7 times the track's `max_age_weeks`; a null `max_age_weeks` removes the limit. It affects only what the screen shows — every post it would otherwise hide is already promoted to a lead, since promotion applies no filter of its own. Results sort by posted date descending.

**Schedule advance** (`ARCH-SCHED-03`). After a scheduled run starts, `next_run_at` becomes the first whole-interval step strictly after `now`, so missed windows collapse into one run.

```python
def next_run_after(next_run_at, interval_hours, now):
    step = timedelta(hours=interval_hours)
    if next_run_at is None:
        return now + step
    return next_run_at + step * ((now - next_run_at) // step + 1)
```

With a 24-hour interval, `next_run_at` of 2026-09-16 08:00 and `now` of 2026-09-19 10:00, three whole intervals have passed, one run starts, and the next value is 2026-09-20 08:00. Only a started run calls this function.

**Run status and counts.** A run finishes `success` when every keyword's sweep, every detail fetch and every promotion completed. It finishes `partial` when at least one keyword ended on a fetch failure, at least one detail fetch errored, or at least one promotion raised, and posts were still persisted. It finishes `failed` when an unhandled exception ended it, or when every keyword failed. `outcome_counts` is a JSON object with these keys: `mcf_mode`, `keywords`, `pages`, `cards`, `new_posts`, `existing_posts`, `detailed`, `closed`, `detail_errors`, `promoted`, `promote_errors`. `mcf_mode` records `fixture` or `live`, per `ARCH-BOT-04`. The Posts running state renders "{cards} postings found, page {pages}" from two of them.

### Data model

The data model update adds a run provenance column and one closed-vocabulary value. The current schema already carries the `search_schedule` table and the per-user `run_log` columns and running index, so the update checks that they are present and adds only what is missing. Version numbers follow the Schema versions table at implementation time.

01. `run_log.trigger_source`: `TEXT NOT NULL DEFAULT 'manual' CHECK (trigger_source IN ('manual', 'scheduled'))`.
02. `lead.close_reason`'s check constraint gains `track_not_matched` alongside its existing values, so a lead dropped because the track's own keywords over-matched it reads distinctly from `withdrawn`.
03. `post`, `post_track` and `match_score` keep their shape. `post.mcf_ref` doubles as the detail-done marker. `match_score.match_score` is written as the constant `1.0` here; the column's existing `CHECK (match_score >= 0 AND match_score <= 1)` already allows any value in range, so milestone 16 can write a differentiated value later under its own `score_method` with no constraint change. The existing indexes cover the joined read.
04. The `run_log` closed vocabularies keep their values. A skipped scheduler tick writes no row, per `ARCH-SCHED-05`.

### Seed data

The rest of the seed set keeps its shape and gains two things beyond the usual per-milestone extension. Each existing `run_log` row carries `trigger_source='manual'` by default, and at least one seeded search `run_log` row carries `trigger_source='scheduled'`, on a track that the scheduled-run case does not schedule, so both values appear and the seed oracle's enumeration check extends to the new column (`STRAT-CASE-05`). The seeded posts keep the manual, closed and already-a-lead rows the frontend cases assert against, each `match_score` row seeded at the fixed `1.0`. With two seeded users, each user's posts, pairings and leads stay distinct, and at least one seeded `lead` row carries `close_reason='track_not_matched'` so the value is exercised from the first reset.

### Architecture

**Modules.** Pure functions sit apart from the code that does I/O, so the oracle cases reach them directly.

01. `easymcf/automation/parsing.py` holds `parse_cards(html, today)` and `parse_detail(html)`. Both are pure, built on BeautifulSoup with html5lib.
02. `easymcf/services/search.py` holds `post_id`, `start_run`, `run_sweep`, `run_detail_pass`, `promote_qualifying`, `posts_for_track`, `add_manual_post` and `reconcile_orphaned_runs`. The fixed `match_score` write lives inline in `run_sweep`/`add_manual_post`; there is no separate scoring module in this milestone.
03. `easymcf/services/scheduler.py` holds `next_run_after`, `tick` and the loop that `__main__.py` starts.
04. `easymcf/automation/browser.py` gains two `MCFBrowser` methods, `search_page(keyword, min_salary, page)` and `detail_page(url_ref)`, each returning page HTML after an explicit wait on a card, the empty-results marker, or the detail marker. `live.py` and `fixture.py` implement them behind the same interface, per `ARCH-BOT-02`. Search needs no MCF session, so neither implementation reads one.

**Service contracts.** These are the seams the cases call, listed test-first. Every function that a request or thread calls takes the user id first.

| id | contract                                                                            | cases               |
| -- | ----------------------------------------------------------------------------------- | ------------------- |
| 01 | `parse_cards(html, today)` returns card dicts or an empty list                      | TC.11, TC.17        |
| 02 | `parse_detail(html)` returns a dict or `{is_open: False}`; raises on missing marker | TC.12, TC.18        |
| 03 | `start_run(uid, track_id, trigger_source)` returns run row/raises `RunInFlight`     | TC.04, TC.05, TC.21 |

**Threading and connections.** Each run thread and the tick thread open their own SQLite connection per `ARCH-STO-07`. A run thread carries its user id from the track row for its whole life. It commits after every page and every detail post, so a kill loses at most the page in flight. All current-time reads go through `clock.now()`. `create_app()` starts no thread, per `ARCH-SCHED-06`.

**Configuration.** Two variables join `ARCH-RUN-07`'s table. `SEARCH_PAGE_DELAY_S`, default 1, is the pause between search page loads in live mode, so the sweep is polite without fixed sleeps. Fixture-mode tests set it to 0. `MCF_FIXTURE_SCENARIO`, default `default`, selects a named scenario from the fixture corpus's `routes.json` in fixture mode.

**Fixture corpus.** `ARCH-TEST-04`'s layout gains what the cases need. The `default` scenario serves captured search pages with a final empty page, overlapping cards across keywords, one closed detail page, and one card that two seeded tracks' own separate searches each independently return. The `slow` scenario adds a `delay_ms` on chosen routes, so a run stays in flight long enough to collide with a second trigger or to be killed after its first page. Cards adjusted for those cases are derived from captured pages, with only the title text changed.

All routes require a signed-in user and answer `401` otherwise.

| id | endpoint                                 | classification            | responsibility                  |
| -- | ---------------------------------------- | ------------------------- | ------------------------------- |
| 01 | `POST`/`PUT /api/v1/track`               | CAT-02 hook, create only  | also creates profile + schedule |
| 02 | `PUT /api/v1/search_profile/{track_id}`  | CAT-01 generic            | edit search criteria            |
| 03 | `PUT /api/v1/search_schedule/{track_id}` | CAT-01 generic            | edit schedule, interval >= 1    |
| 04 | `POST /api/v1/runs/search`               | CAT-03 named, `API-EP-04` | start a run, `201`/`409`        |
| 05 | `GET`/`search /api/v1/run_log`           | CAT-02 hook, read-only    | poll a run's `outcome_counts`   |

**Trigger validation.** A missing `track_id` is `400`. An unknown track, or a track owned by another user, is `404`. An archived track and a run already in flight are `409`. The in-flight body carries the running run's id.

**Joined read** (row 06). With a `track_id`, each returned row carries the post's columns without `description`, plus `match_score`, `score_method`, `search_match` and `lead_id`. `lead_id` is the id of the caller's own lead on the post, or null — every row this milestone writes carries one, since promotion is unconditional. An optional `max_age_weeks` parameter overrides the profile's default for display only. `GET /api/v1/post/{id}` returns the full row with its description. The `post` resource offers reads only.

the joined read keeps list payloads small, since a track's posts carry full descriptions and the source data holds over 3,500 track-post pairings. The `track` create hook gives every new track its profile and schedule rows.

### Validation utility extension

`api_tester.py` gains one optional `poll` block on a case, so a case can trigger asynchronous work and assert on where it ends. The request and `expected_status` behave as they do today. After a matching response the tester polls the given path once a second until the `until` condition holds or `timeout_s` passes, then compares the final body to `expected_final` as a subset. Polling requests use the case's signed-in session, so a case that runs as a named seeded user polls as that user.

```json
{"name": "trigger search and wait", "as_user": "user1", "method": "POST", "path": "/api/v1/runs/search",
 "body": {"track_id": 1}, "expected_status": 201,
 "poll": {"path": "/api/v1/run_log/{id}", "until": {"status": ["success", "partial", "failed"]}, "timeout_s": 60},
 "expected_final": {"status": "success"}}
```

`{id}` takes the `id` from the response body. When the polled body is a list, the condition holds once any element satisfies it, and that element becomes the final body. A poll that reaches `timeout_s` classifies `ERROR`, a final body that misses `expected_final` classifies `FAIL`, and a match classifies `PASS`. Existing case files, the three outcome classes and the log format keep their current behavior.

```python
def _poll(session, base_url: str, case: dict, first_body: dict) -> tuple[str, object, object, str | None]:
    spec = case["poll"]
    path = spec["path"].format(**first_body)
    deadline = time.monotonic() + spec["timeout_s"]
    while time.monotonic() < deadline:
        resp = session.get(base_url + path, timeout=10)
        body = resp.json()
        candidates = body if isinstance(body, list) else [body]
        for row in candidates:
            if all(row.get(k) in v for k, v in spec["until"].items()):
                expected_final = case.get("expected_final", {})
                if all(row.get(k) == v for k, v in expected_final.items()):
                    return "PASS", expected_final, row, None
                return "FAIL", expected_final, row, None
        time.sleep(1)
    return "ERROR", spec["until"], None, f"poll of {path} timed out after {spec['timeout_s']}s"
```

```python
def next_run_after(next_run_at, interval_hours: int, now: datetime) -> datetime:
    step = timedelta(hours=interval_hours)
    if next_run_at is None:
        return now + step
    return next_run_at + step * ((now - next_run_at) // step + 1)


def tick(db, now: datetime) -> None:
    due = db.execute(
        "SELECT ss.track_id, t.user_id, ss.schedule_interval_hours, ss.next_run_at FROM search_schedule ss "
        "JOIN track t ON t.id = ss.track_id WHERE ss.schedule_enabled = 1 AND t.is_active = 1 "
        "AND (ss.next_run_at IS NULL OR ss.next_run_at <= ?) ORDER BY ss.next_run_at", (now.isoformat(),),
    ).fetchall()
    skipped_users = set()
    for row in due:
        if row["user_id"] in skipped_users:
            continue
        try:
            search.start_run(db, row["user_id"], row["track_id"], trigger_source="scheduled")
            next_at = next_run_after(
                datetime.fromisoformat(row["next_run_at"]) if row["next_run_at"] else None,
                row["schedule_interval_hours"], now,
            )
            db.execute("UPDATE search_schedule SET next_run_at = ? WHERE track_id = ?", (next_at.isoformat(), row["track_id"]))
        except RunInFlight as exc:
            logging.info("scheduler: skipping track %s, run %s already in flight", row["track_id"], exc.extra["run_id"])
            skipped_users.add(row["user_id"])


def run_forever(get_db_fn, tick_s: float, stop_event: threading.Event) -> None:
    while not stop_event.wait(tick_s):
        db = get_db_fn()
        try:
            tick(db, clock.now())
        finally:
            db.close()
```
