# Apply Automation - Feature tracker
>Review the guidelines before performing any actions including edits on the document

## 010.11 (pending) apply automation

Implements the **requirements** Automated apply section, REQ-APPLY-01..11, and the apply half of REQ-FE-01/02. The feature lets a user establish the MCF session, work through the `TOAPPLY` apply queue as a batch, run the apply state machine, receive each outcome on the lead lifecycle milestone 09 owns, and drive and repair the whole cycle from the CVs, Applications, and Automation screens. It builds on the schema and seed data milestone 08 delivered for `cv`, `application`, and `session`.

## Scope

Build the apply-automation feature end to end on top of milestone 08's schema and seed data and milestone 09's lead lifecycle. The feature covers the CV catalog CRUD, the apply queue (the open `TOAPPLY` leads), the run, and the drop flow, the browser-driven per-lead apply state machine, the MCF session upload and status mechanism, the apply-outcome effects on the lead, and the AngularJS screens that let a user drive, monitor, and manually repair the whole cycle. Those screens are **user interface** pages 2, 7, and 8.

In scope:

01. **backend CV catalog CRUD.** `API-CAT-01` generic resource per REQ-APPLY-02. A user creates and edits `cv` labels. `DELETE /api/v1/cv/{id}` on a label still referenced by `track.default_cv_id` or `application.cv_id` fails the FK constraint. The generic handler translates that failure into a descriptive `409`, per the **api design**.
02. **apply queue.** The apply queue is the set of open leads at `TOAPPLY` (`09.IS.46` of milestone 09), so no queue endpoint exists and `API-EP-02` is retired. The Applications page reads the `TOAPPLY` leads, and the run attempts the same set.
03. **queued status resolved.** The `application.status` `CHECK` constraint in the **schema** keeps its eight apply-run outcome codes and needs no `queued` value, because the queue is the set of `TOAPPLY` leads and an `application` row exists for each attempt only. This item needs no schema or seed change.
04. **drop from the queue.** REQ-APPLY-11 is served by `POST /api/v1/lead/batch` with `stage: "CLOSED"` and `close_reason: "dropped"`, which milestone 09 builds, and the per-row drop on the Applications page uses `PUT /api/v1/lead/{id}` with the same values. No dequeue endpoint exists, `API-EP-03` is retired, and a dropped lead stays out of every future run.
05. **backend application read.** `API-HOOK-02` hook with generic `GET` and `search`. Only the apply-run service writes `status`, `error_detail`, and `attempted_at`, through the same persistence call the generic blueprint uses. `POST`, `PUT`, and `DELETE` are unexposed.
06. **backend apply run trigger.** `API-EP-05 POST /api/v1/runs/apply` implements REQ-APPLY-03, 06, 07, and 08. It takes no request body and attempts every open lead of the signed-in user at `TOAPPLY`, writing one `application` row per attempt. It aborts the whole run up front if the user's `mcf_session` row is not `valid`. REQ-APPLY-06 evaluates this once for the entire batch at the start of the run. The one-run-at-a-time guard is the same one the search run uses, the `ARCH-RUN-03` partial unique index on `run_log` per user and run type, and a collision for the same user returns `409` with the in-flight `run_log.id`.
07. **backend apply automation engine.** The per-lead state machine implements REQ-APPLY-03, 04, 05, 07, and 08. It loads the post URL, polls the apply button up to `APPLY_POLL_RETRIES` times at `APPLY_POLL_DELAY_S` intervals per `ARCH-BOT-05`, clicks, selects the assigned CV by substring match against the resume options, advances, and submits the final review. It reaches the full outcome vocabulary: `applied`, `questionnaire_required`, `cv_selector_error`, `unable_to_apply`, `post_unavailable`, `cv_not_found`, `post_closed`, and `invalid_input`. All MCF interaction goes through the `ARCH-BOT-02` `MCFBrowser` seam, so one code path serves `fixture` and `live` mode. A failure on one queued application lets the batch continue. Results merge back keyed by lead id, following the prototype's `combine_first()` pattern, so every application keeps its own recorded outcome.
08. **backend session management.** `API-HOOK-04` hook per REQ-APPLY-06. `GET /api/v1/mcf_session/search` is the generic read behind the status badge and returns the signed-in user's single row. `PUT` and `POST /api/v1/mcf_session` are blocked, since a raw field write could claim `status='valid'` without a validated cookie ever being uploaded. `API-EP-06 POST /api/v1/mcf_session/upload` validates that at least one loaded cookie matches the MCF domain and writes the user's session file `mcf_session_<user_id>.json` per `ARCH-BOT-03` with `0600` file and `0700` directory permissions. It then updates the user's `mcf_session` row's `status`, `uploaded_at`, and `cookie_ref`. `cookie_ref` holds the filename only, which keeps the raw cookie value out of the database.
09. **backend apply-outcome propagation.** Workflow 7 implements REQ-APPLY-09 and 10 inside the apply-run service, and no client-visible endpoint exists for it. The rules are:
    1. `applied` transitions the lead to `APPLIED`.
    2. `post_closed` and `post_unavailable` close the lead with `close_reason='apply_failed'`.
    3. `questionnaire_required`, `cv_not_found`, `cv_selector_error`, `unable_to_apply`, and `invalid_input` leave the lead at `TOAPPLY` for the user to repair and retry.

    This milestone owns writing these effects. The stage machine and close-reason vocabulary they write into belong to milestone 09.
10. **backend run status read.** REQ-PLAT-03 and REQ-FE-02 reuse milestone 10's `run_log` `GET` and `search` surface for `run_type='apply'` rows. Those rows carry a null `track_id` and `trigger_source='manual'`, since nothing schedules an apply run in `010`.
11. **frontend CVs page.** **User interface** page 2 lists, creates, and edits CV labels. Users reach it from the "Manage CVs" link on Tracks and from the CV override control on Applications. It has no standalone nav entry, per the **user interface** information architecture.
12. **frontend Applications page.** **User interface** page 7 provides:
    1. the apply queue list, the open `TOAPPLY` leads, with a per-row CV override that defaults to the track's default CV, plus an inline "manage CVs" link.
    2. visual flagging and next-run blocking for a lead left with an unresolved `cv_not_found`.
    3. drop-from-queue, which closes the lead as `dropped`, behind the confirmation-modal pattern.
    4. inline session status that disables "Run" with an explanation when the session is invalid.
    5. "Run apply batch" behind the confirmation modal, leading into the async running state with per-application progress.
    6. the post-run results view with a per-outcome next action per Workflow 7's table.
13. **frontend Leads page queue actions.** Milestone 09 (task 09.13) builds the `TOAPPLY` column's batch `Apply` and `Drop` on `POST /api/v1/lead/batch`, so this milestone adds no queue action to the Leads page. It feeds the `TOAPPLY` leads to the Applications page and the run.
14. **queue selection.** No queue selection step exists. Leads enter the queue at `TOAPPLY` by system promotion, and the Leads page's batch `Apply` and `Drop` prune it (`09.IS.39`).
15. **frontend Automation page.** **User interface** page 8 has two tabs. The Runs tab shows a reverse-chronological `run_log` list with type, track if applicable, start and end time, status, and outcome counts. Rows expand to error detail, and apply-run rows link to their resulting applications. The Session tab shows current status and last-uploaded-at, a "Log in to MCF" external-browser link, an upload control with an inline validation-failure error, and a confirmation-modal-gated overwrite of an existing valid session. The global session-status badge opens this same Session component as an overlay from any page.
16. **manual repair path.** REQ-APPLY-05 leaves a lead at `TOAPPLY` after `questionnaire_required` or any other retryable outcome. The existing surfaces support two repairs. The user completes the application directly on MCF and then advances the lead to `APPLIED` from the Lead Detail panel that milestone 09 owns. Alternatively the user fixes the underlying problem, such as the CV assignment or missing input, and the next apply run attempts the lead again.
17. **run-status and error surfacing.** REQ-FE-02 applies. A failed or rejected `application` or `mcf_session` write surfaces in the UI through the **user interface** cross-cutting error-surfacing pattern.

Out of scope:

01. the Tracks page, the Posts and results screen, the Manual Post Entry dialog, and the search and scoring pipeline behind them, which are **user interface** pages 1, 3, and 4 and belong to milestone 10. This milestone reads `track.default_cv_id` as a read-only default.
02. the Leads page stage tabs, the Lead Detail panel, the lead stage state machine, the close-reason vocabulary, and auto-expiry, which belong to milestone 09. This milestone writes the `APPLIED` transition and the `apply_failed` close into that machine and wires one existing control, as items 09 and 13 describe.
03. automating the Singpass login, MFA, or CAPTCHA step, which REQ-APPLY-06 excludes release-wide. The "Log in to MCF" action opens an ordinary external browser context, and login is a manual human action outside `MCFBrowser` per `ARCH-NET-03`.
04. automating multi-step questionnaire completion, which REQ-APPLY-05 excludes. This milestone detects and records `questionnaire_required` and leaves completion to the user on MCF.
05. `cv`, `application`, and `mcf_session` schema and seed generation. Milestone 08 delivered them in the **schema** and the **application seed** and **session seed** files, and feature 13 gives the session table one row per user. This milestone reuses that set and extends it where Design finds a concrete gap.
06. any scheduler for apply runs. Apply runs are always user-triggered per `ARCH-RUN-02`, with `trigger_source='manual'` on every `run_type='apply'` row. Milestone 10's in-process scheduler covers search runs only.
07. any analytics, BI, or reporting pipeline, which the **requirements** Out of scope section excludes release-wide. The Automation Runs tab exists to diagnose a run without re-running it.
08. accounts, sign-in, and the ownership layer itself, which feature 13 delivers. This milestone's queue, run, and session code takes the owning user id explicitly, per `ARCH-AUTH-04` and `ARCH-AUTH-08`.
09. any request against the live MCF site and any read or commit of a real session cookie export in an automated or unattended context, per the **project boundaries** and REQ-DEV-03 and 04. A bug in this milestone submits real job applications, so it carries the highest blast radius in the release. Development, tests, and every agent-run validation loop use `MCF_MODE=fixture` against the `apply/{scenario}/` fixture corpus of `ARCH-TEST-04`, which covers all eight outcome codes. `MCF_MODE=live` and a genuine session file are deliberate per-invocation human actions. An agent satisfies neither, per `ARCH-TEST-06`.

**closure**

01. **11.CK.01** every one of REQ-APPLY-01..11 is implemented and independently verified by the Test cases section this milestone writes.
02. **11.CK.02** the open `TOAPPLY` leads form the apply queue: the Applications page lists them, and the run attempts each of them. A lead moved to `APPLIED` or dropped on the Leads page is out of the queue and is not attempted.
03. **11.CK.03** a user reviews the queue on the Applications page, overrides the CV per lead, and drops a lead before running. The drop closes the lead as `dropped`, and the lead stays out of every later run.
04. **11.CK.04** triggering "Run apply batch" aborts the entire run up front with zero per-application attempts when the session is not `valid`. Otherwise every open `TOAPPLY` lead is attempted, and every one of the eight outcome codes is reachable deterministically against the fixture corpus.
05. **11.CK.05** a failure on one lead's attempt lets the run attempt the rest of the batch and leaves every other application's recorded outcome intact, verified against a mixed-outcome batch per REQ-APPLY-08.
06. **11.CK.06** each apply outcome reaches its lead exactly per Workflow 7's table. `applied` moves the lead to `APPLIED`, `post_closed` and `post_unavailable` close it with `apply_failed`, and every other code leaves it at `TOAPPLY`. Milestone 09's stage machine and its unconditional-overwrite regression guard keep passing.
07. **11.CK.07** a user establishes or refreshes the MCF session through the in-app upload dialog. A cookie that fails the MCF domain match is rejected with an inline error. Session status, `valid`, `expired`, or `missing`, is visible from the global badge and the Automation Session tab on every page.
08. **11.CK.08** a lead left at `TOAPPLY` after `questionnaire_required`, `cv_not_found`, `cv_selector_error`, `unable_to_apply`, or `invalid_input` is manually repairable. The user completes it directly on MCF and advances it to `APPLIED` from the Lead Detail panel, or fixes the cause and the next run attempts it again. The system treats manual completion as a first-class route to `APPLIED`.
09. **11.CK.09** the Applications page and the Automation page with its Runs and Session tabs are reachable and populated from seed and fixture data. Every action, whether queue review, CV override, drop, run, or session upload, round-trips through the real backend API.
10. **11.CK.10** the CVs page supports create, edit, and delete of CV labels and is reachable from Tracks and from the Applications CV override control. Deleting a label still referenced by a track default or an application override returns a descriptive `409`.
11. **11.CK.11** a rejected or failed `application` or `mcf_session` write surfaces its error in the UI per REQ-FE-02.
12. **11.CK.12** milestone 07's, 08's, 09's, and 10's own closing commands still pass unmodified against this milestone's changes.
