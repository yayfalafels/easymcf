# Apply Automation - Feature tracker
>Review the guidelines before performing any actions including edits on the document

## 010.11 (pending) apply automation

Implements the **requirements** Automated apply section, REQ-APPLY-01..11, and the apply half of REQ-FE-01/02. The feature works through the `TOAPPLY` apply queue as a batch, runs the apply state machine against an already-established MCF session, receives each outcome on the lead lifecycle milestone 09 owns, and drives and repairs the whole cycle from the CVs, Applications, and Automation screens. It builds on the schema and seed data milestone 08 delivered for `cv`, `application`, and `session`.

## Scope

Build the apply-automation feature end to end. The feature covers

- CV catalog CRUD
- apply queue (the open `TOAPPLY` leads)
- run, and drop flow
- browser-driven per-lead apply state machine
- MCF session consumption and reauthentication detection
- apply-outcome effects on the lead
- AngularJS screens that let a user drive, monitor, and manually repair the whole cycle.

In scope:

01. **backend CV catalog CRUD.** `API-CAT-01` generic resource per REQ-APPLY-02. A user creates and edits `cv` labels. `DELETE /api/v1/cv/{id}` on a label referenced by `track.default_cv_id` or `application.cv_id` fails the FK constraint. The generic handler translates that failure into a descriptive `409`, per the **api design**.
02. **apply queue.** The apply queue derives from open leads at `TOAPPLY`. `API-EP-02` is retired. The Applications page reads the `TOAPPLY` leads, and the run attempts the same set.
03. **queued status resolved.** The `application.status` `CHECK` constraint in the **schema** contains the eight apply-run outcome codes. Queue membership comes from `TOAPPLY` leads, and each application row represents an attempt. This item preserves the existing schema and seed data.
04. **drop from the queue.** REQ-APPLY-11 uses `POST /api/v1/lead/batch` with `stage: "CLOSED"` and `close_reason: "dropped"`, and the per-row drop on the Applications page uses `PUT /api/v1/lead/{id}` with the same values. The existing lead endpoints provide the drop flow. `API-EP-03` is retired, and a dropped lead stays out of every future run.
05. **backend application read.** `API-HOOK-02` provides generic `GET` and `search`. The apply-run service owns writes to `status`, `error_detail`, and `attempted_at` through the same persistence call the generic blueprint uses. The API exposes reads for applications.
06. **backend apply run trigger.** `API-EP-05 POST /api/v1/runs/apply` implements REQ-APPLY-03, 06, 07, and 08. It accepts an empty request body and attempts every open lead of the signed-in user at `TOAPPLY`, writing one `application` row per attempt. An invalid user's `mcf_session` row aborts the whole run up front and raises an exception with an error message prompting the user to log in and authenticate a new session. REQ-APPLY-06 evaluates this once for the entire batch at the start of the run. The one-run-at-a-time guard is the same one the search run uses, the `ARCH-RUN-03` partial unique index on `run_log` per user and run type, and a collision for the same user returns `409` with the in-flight `run_log.id`.
07. **backend apply automation engine.** The per-lead state machine implements REQ-APPLY-03, 04, 05, 07, and 08. It loads the post URL, polls the apply button up to `APPLY_POLL_RETRIES` times at `APPLY_POLL_DELAY_S` intervals per `ARCH-BOT-05`, clicks, selects the assigned CV by substring match against the resume options, advances, and submits the final review. It reaches the full outcome vocabulary: `applied`, `questionnaire_required`, `cv_selector_error`, `unable_to_apply`, `post_unavailable`, `cv_not_found`, `post_closed`, and `invalid_input`. All MCF interaction goes through the `ARCH-BOT-02` `MCFBrowser` seam, so one code path serves `fixture` and `live` mode. A failure on one queued application lets the batch continue. Results merge back keyed by lead id, following the prototype's `combine_first()` pattern, so every application keeps its own recorded outcome.
08. **backend session handling.** The apply-run service opens its browser context from the storage state that the signed-in user's `mcf_session.cookie_ref` names, per `ARCH-BOT-03`, restoring the saved cookies into a fresh Chromium context for each run that needs one. A run whose page banner shows "Login" in place of the signed-in user's initials records `mcf_session.status='expired'` and moves the owning `mcf_attempt` row to `reauthentication_required`.
09. **backend apply-outcome propagation.** Workflow 7 implements REQ-APPLY-09 and 10 inside the apply-run service. The rules are:
    1. `applied` transitions the lead to `APPLIED`.
    2. `post_closed` and `post_unavailable` close the lead with `close_reason='apply_failed'`.
    3. `questionnaire_required`, `cv_not_found`, `cv_selector_error`, `unable_to_apply`, and `invalid_input` leave the lead at `TOAPPLY` for the user to repair and retry.

    This milestone owns writing these effects. The stage machine and close-reason vocabulary they write into belong to milestone 09.
10. **backend run status read.** REQ-PLAT-03 and REQ-FE-02 reuse milestone 10's `run_log` `GET` and `search` surface for `run_type='apply'` rows. Those rows carry a null `track_id` and `trigger_source='manual'`, since apply runs are always triggered manually in `010`.
11. **frontend CVs page.** **User interface** page 2 lists, creates, and edits CV labels. Users reach it from the "Manage CVs" link on Tracks and from the CV override control on Applications. Navigation follows the **user interface** information architecture through those entry points.
12. **frontend Applications page.** **User interface** page 7 provides:
    1. the apply queue list, the open `TOAPPLY` leads, with a per-row CV override that defaults to the track's default CV, plus an inline "manage CVs" link.
    2. visual flagging and next-run blocking for a lead left with an unresolved `cv_not_found`.
    3. drop-from-queue, which closes the lead as `dropped`, behind the confirmation-modal pattern.
    4. inline session status that disables "Run" with an explanation when the session is invalid.
    5. "Run apply batch" behind the confirmation modal, leading into the async running state with per-application progress.
    6. the post-run results view with a per-outcome next action per Workflow 7's table.
13. **frontend Leads page queue actions.** feed the `TOAPPLY` leads to the Applications page and the run.
14. **queue selection.** System promotion places leads in the queue at `TOAPPLY`. The Leads page's batch `Apply` and `Drop` prune the queue.
15. **frontend Automation page.** **User interface** page 8 has one tab, Runs, which this milestone extends to `run_type='apply'` rows. It shows a reverse-chronological `run_log` list with type, track if applicable, start and end time, status, and outcome counts. Rows expand to error detail, and apply-run rows link to their resulting applications. Session status has no tab of its own. It surfaces through the global MCF connection pop-up feature 17 already built, which this milestone feeds by writing `mcf_session` and `mcf_attempt` but does not itself build.
16. **manual repair path.** REQ-APPLY-05 leaves a lead at `TOAPPLY` after `questionnaire_required` or any other retryable outcome. The existing surfaces support two repairs. The user opens the posting through Feature 17's reusable authenticated MCF link, completes the application directly on MCF, and then advances the lead to `APPLIED` from the Lead Detail panel that milestone 09 owns. The link uses Feature 17's authenticated version when a valid session exists, and the ordinary URL otherwise. Alternatively the user fixes the underlying problem, such as the CV assignment or missing input, and the next apply run attempts the lead again.
17. **run-status and error surfacing.** REQ-FE-02 applies. A failed or rejected `application` or `mcf_session` write surfaces in the UI through the **user interface** cross-cutting error-surfacing pattern.

Out of scope:

01. the Tracks page, the Posts and results screen, the Manual Post Entry dialog, and the search and scoring pipeline behind them. This milestone reads `track.default_cv_id` as a read-only default.
02. the Leads page stage tabs, the Lead Detail panel, the lead stage state machine, the close-reason vocabulary, and auto-expiry, which belong to milestone 09. This milestone writes the `APPLIED` transition and the `apply_failed` close into that machine and wires one existing control, as items 09 and 13 describe.
03. automating the Singpass login, MFA which REQ-APPLY-06 excludes release-wide. Feature 17 establishes and restores the session. Any required Singpass approval remains a manual human action outside `MCFBrowser` per `ARCH-NET-03`.
04. automating multi-step questionnaire completion, which REQ-APPLY-05 excludes. This milestone detects and records `questionnaire_required` and leaves completion to the user on MCF.
05. `cv`, `application`, and `mcf_session` schema and seed generation. Extends the existing features where Design finds a concrete gap.
06. any scheduler for apply runs. Apply runs are always user-triggered per `ARCH-RUN-02`, with `trigger_source='manual'` on every `run_type='apply'` row. Milestone 10's in-process scheduler covers search runs. Apply runs use manual triggers.
07. analytics, BI, and reporting pipelines. The **requirements** Out of scope section excludes these release-wide. The Automation Runs tab diagnoses a run from its recorded data.
08. accounts, sign-in, and the ownership layer itself, which feature 13 delivers. This milestone's queue, run, and session code takes the owning user id explicitly, per `ARCH-AUTH-04` and `ARCH-AUTH-08`.
09. establishing, uploading, or refreshing the MCF session, the QR and Singpass connection-attempt flow behind it, and the `mcf_attempt` table, which feature 17 delivers. This milestone consumes the `mcf_session` row that flow populates and writes the `expired` transition described in item 08.
10. any request against the live MCF site and any read or commit of a real session cookie export in an automated or unattended context, per the **project boundaries** and REQ-DEV-03 and 04. A bug in this milestone submits real job applications, so it carries the highest blast radius in the release. Development, tests, and every agent-run validation loop use `MCF_MODE=fixture` against the `apply/{scenario}/` fixture corpus of `ARCH-TEST-04`, which covers all eight outcome codes. `MCF_MODE=live` and a genuine session file are deliberate per-invocation human actions. Only a human satisfies both, per `ARCH-TEST-06`.

## Test strategy

Six independent-verification layers, each following the release-level strategy ids the **test strategy doc** already defines. The layers run in this order, and each layer checks independently of the layers before it, per `STRAT-TOOL-04`.

01. **self-report, one utility per silo.** Case-config replay against a running instance, per `STRAT-TOOL-01/02`: `api_tester.py` for the backend routes, `ui_tester.py` for the CVs, Applications, and Automation screens. Each case is a `PASS`, `FAIL`, or `ERROR` verdict. A verdict proves a status code or a rendered element. Direct inspection supplies persistence and batch-isolation evidence.
02. **direct inspection.** `db_util.py` queries the same database a case just wrote to, per `STRAT-SILO-02`. The queries prove queue membership, the propagation effect on each lead, and the reauthentication write from persisted state.
03. **oracle.** Hard-coded-expectation pytest at the service layer, per `STRAT-SILO-05`, calling the apply-run service directly against `easymcf/automation/fixture.py`'s `MCFBrowser`. Expected values come from this tracker's Scope and closure text. This layer verifies the logic behind the full eight-code outcome vocabulary (`STRAT-SILO-06`), the `APPLY_POLL_RETRIES` boundary, and the REQ-APPLY-08 merge-by-lead-id guarantee.
04. **mock end to end.** Playwright against the real backend, the real database, and the fixture `MCFBrowser`, per `ARCH-TEST-04`/`STRAT-02`. This layer exists specifically for the run-trigger-and-poll wiring across the Applications page's async progress state and the backend run thread, the same class of cross-component risk `STRAT-CASE-07` names for REQ-FE-02's search-run case.
05. **live-tier.** A human-triggered run against the real MCF site, per `ARCH-TEST-06`. This layer submits a real application. It requires the standard `--run-live` marker and the second explicit submission flag named by Design. Human invocation controls this tier.
06. **human validation.** Per `STRAT-HUMAN-01/02`, the last step. A person clicks through the real running app once every automated layer and the live tier are green, following a checklist derived from this tracker's own closure items.

Strategy rules applied to this feature:

01. **enumeration completeness.** Per `STRAT-CASE-05` and `STRAT-SILO-06`, the oracle layer reaches all eight REQ-APPLY-04 outcome codes as named fixture scenarios. Mock end to end adds wiring coverage.
02. **boundary values.** Per `STRAT-CASE-03`, `APPLY_POLL_RETRIES` gets a case one attempt short of exhaustion, finding the button, and a second case at exhaustion, reaching `unable_to_apply`.
03. **batch isolation as a named case.** REQ-APPLY-08's merge-by-lead-id rule gets its own dedicated case, following `STRAT-CASE-04`'s pattern of protecting a specific correctness guarantee directly. The happy-path batch case provides complementary coverage.
04. **determinism.** Per `STRAT-CASE-06`, every apply-automation case runs with `APPLY_POLL_RETRIES` and `APPLY_POLL_DELAY_S` overridden small, per `ARCH-BOT-05`, so the retry loop executes in full with deterministic timing.
05. **ownership.** Per `STRAT-SILO-08` and `STRAT-CASE-08`, the apply queue, the run trigger's one-in-flight guard, the application rows, and the `mcf_session`/`mcf_attempt` rows are all scoped to the signed-in user. Each seeded user's request returns and affects that user's rows.
06. **branch observability.** Each browser-state branch asserts both its returned application outcome and the browser interaction boundary it controls. Preflight input failures assert zero browser actions. Load failures assert zero button polls. Questionnaire outcomes assert that the batch advances to the next lead.

## Design

The automated apply feature develops the existing lead, schema, run-log, authentication, session, and AngularJS contracts into one apply workflow. The queue is derived from open `TOAPPLY` leads, each run creates append-only application attempt records, and each outcome updates the lead through Feature 09's stage service.

The design includes end-to-end **Workflow** and the **State-machine contract**. These sections define 

01. queue review
02. run preflight
03. browser actions, all  outcomes
04. batch continuation
05. lead propagation. 

**Data model** assigns ownership and persistence responsibilities across `cv`, `application`, `mcf_session`, `mcf_attempt`, and `run_log`.

**Seed data and fixture corpus** defines deterministic database and MCF page inputs for every branch. 

**Architecture and session handling** specifies the `MCFBrowser` seam, background worker, browser context, authentication expiry, and one-run guard. 

**API backend** translates those decisions into endpoint contracts and write boundaries.

**Frontend** defines the Applications and Automation states, including queue review, CV repair, run progress, results, session status, and error surfacing. **Error handling and observability** defines per-lead outcomes, run-level failures, diagnostics, and secret-free logging. **Design traceability** maps each design area to its scope requirement and independent verification case.

### Workflow

The apply workflow has the following phases: queue review, run preflight, per-lead attempt, and run finalization.

01. **queue review.** The Applications page queries the signed-in user's open `TOAPPLY` leads. Each row resolves its effective CV from an application override or the lead's track default. A user may change the override, drop the lead with `close_reason='dropped'`, or start the batch.
02. **run preflight.** `POST /api/v1/runs/apply` confirm checks, then create a `run_log` row.
    - confirm checks:
        01. user's session is `valid`
        02. user has no running apply row
        03. queue can be read
    - The session check applies to the whole batch
    - An invalid session returns the session error and produces zero application attempts.
03. **per-lead input validation.** Each queued lead must have a job identifier, posting URL, and effective CV identifier. Invalid input records `invalid_input` for that lead before browser navigation. The batch proceeds to the next lead.
04. **posting load.** The browser loads the posting URL and reads the page banner's account control. A load failure records `post_unavailable` and proceeds to the next lead. A banner reading "Login" instead of the signed-in user's initials signals a lapsed session, per the session-expiry handling below, and ends the batch.
05. **apply-button resolution.** The browser polls for the apply button using `APPLY_POLL_RETRIES` and `APPLY_POLL_DELAY_S`. A found button is clicked. An already-applied page signal follows the success branch. A closed-post signal records `post_closed`. An exhausted poll with no terminal signal records `unable_to_apply`.
06. **CV selection.** The browser reads resume options and matches the effective CV identifier as a substring of the option text. A matching option is selected and the flow advances. A missing match records `cv_not_found`. A selector or DOM failure records `cv_selector_error`.
07. **final review.** The browser submits the final review. A successful submission records `applied`. A failed one-click submission records `questionnaire_required` and returns control to the user for manual completion.
08. **outcome persistence.** The service inserts the application attempt with `status`, `error_detail`, `attempted_at`, and the effective CV. It then applies Workflow 7 to the lead in the same logical operation. The batch continues after every per-lead outcome.
09. **run finalization.** The service closes the `run_log` with terminal status, outcome counts, and aggregate error detail. The Applications page polls the run and then reads the persisted application rows and lead states.

### State-machine contract

The automation engine exposes one operation for one lead and returns a structured result containing `lead_id`, `status`, `error_detail`, `cv_id`, and browser diagnostics needed for the run log. The result vocabulary is exactly the eight values in REQ-APPLY-04.

| id | branch         | result                   | lead effect              |
| -- | -------------- | ------------------------ | ------------------------ |
| 01 | applied        | `applied`                | `APPLIED`                |
| 02 | questionnaire  | `questionnaire_required` | `TOAPPLY`                |
| 03 | selector error | `cv_selector_error`      | `TOAPPLY`                |
| 04 | poll exhausted | `unable_to_apply`        | `TOAPPLY`                |
| 05 | load failure   | `post_unavailable`       | `CLOSED`, `apply_failed` |
| 06 | CV missing     | `cv_not_found`           | `TOAPPLY`                |
| 07 | post closed    | `post_closed`            | `CLOSED`, `apply_failed` |
| 08 | invalid input  | `invalid_input`          | `TOAPPLY`                |

- **01 applied** — entry condition: submit succeeds, or the page reports already applied. Browser action: click or acknowledge, select the CV, advance, submit.
- **02 questionnaire** — entry condition: the final one-click submit fails. Browser action: stop after the failed submit.
- **03 selector error** — entry condition: resume-card lookup raises a selector or DOM error. Browser action: stop at CV selection.
- **04 poll exhausted** — entry condition: the apply button stays unresolved through the configured retries. Browser action: poll to exhaustion.
- **05 load failure** — entry condition: posting navigation fails. Browser action: the engine proceeds directly to the next lead.
- **06 CV missing** — entry condition: no resume option matches the configured CV. Browser action: inspect the options.
- **07 post closed** — entry condition: the page signals a closed or unavailable posting. Browser action: inspect the page signal.
- **08 invalid input** — entry condition: the job id, URL, or CV assignment is missing. Browser action: the engine skips browser interaction and proceeds to the next lead.

The engine distinguishes `post_unavailable` from `post_closed` by the stage at which the signal occurs. Navigation failure produces `post_unavailable`. A loaded page that reports a closed posting produces `post_closed`. It distinguishes `cv_not_found` from `cv_selector_error` by whether option lookup succeeds and returns a non-matching set or raises an interaction error.

### Data model

The design uses the existing tables schema version <##> and adds the write/read behavior needed by the apply run.

01. **`cv`.** A user-owned label catalog. The label is the matching identifier used against MCF resume options, and the actual file lives on MCF's own profile.
02. **`track.default_cv_id`.** The track-level fallback CV. The apply queue reads it through the lead's track relationship.
03. **`application`.** A user-owned attempt history row linked to one lead and one effective CV. The apply service writes `status`, `error_detail`, and `attempted_at`. A lead may have many rows, ordered by attempt time.
04. **`mcf_session`.** One user-owned session record with `status` and opaque `cookie_ref`. The apply run reads it during preflight and updates it to `expired` when the page banner shows "Login" instead of the signed-in user's account initials.
05. **`mcf_attempt`.** Feature 17 owns the connection attempt. Feature 11 updates the owning row to `reauthentication_required` when session expiry is detected.
06. **`run_log`.** Feature 10 owns the common run record. Apply rows use `run_type='apply'`, `track_id=NULL`, and `trigger_source='manual'`. `outcome_counts` contains counts by apply status.

Application writes are append-only from the feature's service contract. A retry creates a new row. The lead effect and application insert share the service operation's transaction boundary, so a persisted outcome always has its corresponding Workflow 7 mutation or a recorded run error.

### Seed data and fixture corpus

Seed data supplies deterministic queue, CV, application-history, session, and run-log records for API and UI checks. The seeded `mcf_session` row for the standard fixture user is `valid` and points to a fixture storage state. A second seeded user supplies tenancy checks. Invalid-session seeds cover `missing` and `expired` states.

The MCF fixture corpus is separate from SQLite seed data. `tests/fixtures/mcf/apply/{scenario}/` contains one named scenario for each state-machine branch, including `success`, `already_applied`, `questionnaire`, `selector_error`, `poll_exhausted`, `post_unavailable`, `cv_not_found`, `post_closed`, `invalid_input`, `signed_out`, and `slow`. `routes.json` maps the selected scenario to the page responses used by the fixture browser. The fixtures contain public page markup and no session material.

The fixture manifest also records the expected interaction markers used by oracle tests. A test can therefore assert that load failure performs zero polls, invalid input performs zero browser actions, questionnaire handling stops after submit, and poll exhaustion performs the configured number of polls.

### Architecture and session handling

The API route creates the apply `run_log` and starts the existing in-process background-run pattern. The background worker reads a stable queue snapshot for the signed-in user, opens one fixture or live browser context from the session storage state, and processes leads in deterministic order. Each run owns its browser context and closes it during finalization.

The `MCFBrowser` interface provides 

01. navigation
02. page-state inspection
03. sign-in-status detection
04. apply-button polling
05. CV-option selection
06. advance, final submit
07. browser diagnostics. 

The service uses the interface and remains independent of the concrete browser implementation.

`fixture.py` implements these operations through route-intercepted local HTML. `live.py` implements the same interface for a deliberate human-triggered run. 

**rerun guard**

The one-run guard uses the existing partial unique index for a running row per user and run type. A second apply trigger returns `409` with the existing run id. A completed, partial, or failed row releases the guard and remains available for the Automation Runs view.

**Session validity** is checked before the worker opens a browser, from the `mcf_session` row a prior run or Feature 17's connection flow last wrote. A session can also lapse mid-batch on MCF's own side. 

The service scopes this authentication failure to the whole run rather than to one lead.

The service checks for this on each posting page load
    - reading the page banner's account control: a signed-in session shows the user's initials there
    - and an expired one shows "Login" in their place. 
    - The same lapse also replaces the posting page's apply button with a "Login to Apply" prompt, a corroborating signal rather than a separate check. 

The session inactive signal triggers a session closed event:

01. mark `mcf_session.status='expired'`
02. updates the related `mcf_attempt.status='reauthentication_required'`
03. records the run error
04. ends the browser work for the batch.

| -- | ---------------------------- | ---------------- | ------------------------------------------------- |
| 01 | `/api/v1/cv`                 | GET, POST        | list and create CV labels                         |
| 02 | `/api/v1/cv/{id}`            | GET, PUT, DELETE | edit or delete; a referenced delete returns `409` |
| 03 | `/api/v1/lead/search`        | GET              | list the queue, `stage=TOAPPLY`                   |
| 04 | `/api/v1/lead/{id}`          | PUT              | edit a CV, or close a lead as `dropped`           |
| 05 | `/api/v1/lead/batch`         | POST             | batch drop, or manual `APPLIED` promotion         |

The generic resource layer enforces tenancy, field validation, and FK errors. Application mutation routes remain internal to the apply service. Run and application writes include enough error detail for the UI and direct database inspection to explain a failed outcome.

### Frontend

The Applications page is the primary apply surface. It has explicit loading, empty, invalid-session, running, completed, partial, and error states.

01. **queue state.** Show open `TOAPPLY` leads, effective CV, CV override, last attempt outcome, and drop action. Disable Run for an invalid session and show the session repair action.
02. **CV management.** The override control links to the CV catalog. A saved override updates the lead's effective CV used by the next run.
03. **confirmation state.** Drop and Run use the existing confirmation-modal service. The Run confirmation names the queue count and effective session state.
04. **running state.** Poll the returned run id and show per-application progress, current lead, processed count, and accumulated outcome counts. Preserve the page's queue context while the worker runs.
05. **results state.** Read application rows after terminal status and show each outcome with the Workflow 7 next action. `applied` links to the updated lead, retryable outcomes identify the repair, and closed outcomes identify the close reason.
06. **error state.** Surface rejected CV, application, session, and run writes through the shared error service. Preserve the user's unsaved queue context when a refresh or retry is possible.

The Automation page's Runs tab reads apply `run_log` rows and links each run to its applications. Feature 17's global MCF connection pop-up already reads `mcf_session` and shows `valid`, `missing`, or `expired`, together with the reauthentication state; this milestone feeds that display by writing those columns and builds no session UI of its own. The Leads page keeps its existing stage controls and supplies the Applications queue through the shared lead query.

### Error handling and observability

Every per-lead failure becomes one of the eight application statuses and carries a diagnostic `error_detail`, per the table below. A run-level failure never becomes one of those eight codes. It stays in `run_log.error_detail` instead, per the numbered list further down.

| id | status                   | error_detail content                                        |
| -- | ------------------------ | ----------------------------------------------------------- |
| 01 | `applied`                | null                                                        |
| 02 | `questionnaire_required` | the final submit's failure reason from the review page      |
| 03 | `cv_selector_error`      | the resume-card lookup's exception type and message         |
| 04 | `unable_to_apply`        | apply button unresolved after `APPLY_POLL_RETRIES` attempts |
| 05 | `post_unavailable`       | the posting-load exception's type and message               |
| 06 | `cv_not_found`           | the configured CV label that matched no resume option       |
| 07 | `post_closed`            | the closed or unavailable text the posting page reported    |
| 08 | `invalid_input`          | the missing field: job id, posting URL, or CV assignment    |

an exception the automation engine raises that no named branch already catches is caught at the per-lead boundary, recorded as `unable_to_apply` with the exception's type name and message appended to `error_detail`, and the batch proceeds to the next lead. REQ-APPLY-04's vocabulary stays at exactly eight codes. `unable_to_apply` already means the automation could not resolve the apply button, and an unrecognized exception is exactly that from the caller's own perspective.

**Run-level failures.** Five conditions abort a run, or one lead's remaining share of it, without ever becoming a per-lead outcome.

01. **invalid session at preflight.** A `mcf_session.status` other than `valid` aborts the whole run before any application row is written. The trigger answers under the platform's existing `conflict` code, per the **api design**'s error table.

    ```json
    409 { "error": "conflict", "message": "mcf_session is not valid: sign in through the MCF nav page before running apply" }
    ```

02. **in-flight collision.** `ARCH-RUN-03`'s partial unique index rejects a second running row for the same user and run type, the same guard `API-EP-04` already uses for search runs.

    ```json
    409 { "error": "conflict", "message": "an apply run is already in progress", "run_id": 501 }
    ```

03. **session lapse mid-batch.** The signed-out banner detected during a later lead's posting load ends the batch. `run_log.error_detail` names the lead the batch stopped at and how many leads it had already attempted. Every application row already inserted for that run keeps its recorded outcome.
04. **interrupted run.** A process that dies mid-batch leaves its `run_log` row at `running`, blocking every later apply trigger by that user under the same index. Startup reconciliation, already scoped generically by milestone 10, extends unchanged to `run_type='apply'`. Every `running` row of every user becomes `failed` with `error_detail='interrupted: process stopped before the run finished'` before the server accepts requests, and application rows already committed before the crash keep their recorded outcomes.
05. **unexpected run-level exception.** A database, concurrency, or worker-thread failure outside any single lead's processing ends the run as `failed`. `run_log.error_detail` records the exception's type name and message, following feature 17's `error_code` convention for an unrecognized failure. Application rows already written keep their outcomes.

**Observability.** The service logs the run id, user id, lead id, application id, scenario or mode, outcome, and elapsed time, one line per lead attempt. It omits cookie contents, storage-state payloads, and other session secrets, per `ARCH-BOT-03`. Fixture runs identify their scenario in diagnostics so a failing oracle case can be reproduced without a live request.

```python
"""REQ-APPLY-01..11 — the apply-run trigger and per-lead state machine."""

from __future__ import annotations

from .. import clock
from ..errors import Conflict, RunInFlight
from . import leads
from .apply_outcomes import OUTCOME_EFFECTS  # Workflow 7's table, one entry per status

_INSERT_RUN = (
    "INSERT INTO run_log (run_type, user_id, track_id, started_at, status, trigger_source) "
    "VALUES ('apply', ?, NULL, ?, 'running', 'manual')"
)


def start_run(db, uid: int, browser_factory) -> dict:
    session = db.execute("SELECT status FROM mcf_session WHERE user_id = ?", (uid,)).fetchone()
    if session is None or session["status"] != "valid":
        raise Conflict("mcf_session is not valid: sign in through the MCF nav page before running apply")
    with db:
        try:
            cur = db.execute(_INSERT_RUN, (uid, clock.stamp()))
        except db.IntegrityError:
            in_flight = db.execute(
                "SELECT id FROM run_log WHERE user_id = ? AND run_type = 'apply' AND status = 'running'", (uid,)
            ).fetchone()
            raise RunInFlight("apply", in_flight["id"])
        run_id = cur.lastrowid
    _run_apply(db, uid, run_id, browser_factory)
    return dict(db.execute("SELECT * FROM run_log WHERE id = ?", (run_id,)).fetchone())


def _run_apply(db, uid: int, run_id: int, browser_factory) -> None:
    leads_to_attempt = db.execute(
        "SELECT id, url_ref, position_title, company_name, "
        "COALESCE((SELECT cv_id FROM application WHERE lead_id = lead.id ORDER BY id DESC LIMIT 1), "
        "(SELECT default_cv_id FROM track WHERE track.id = lead.track_id)) AS effective_cv_id "
        "FROM lead WHERE user_id = ? AND stage = 'TOAPPLY'",
        (uid,),
    ).fetchall()
    browser = browser_factory()
    counts: dict[str, int] = {}
    try:
        for lead in leads_to_attempt:
            result = _attempt_one(db, browser, lead)
            if result == "session_expired":
                break  # run-level failure: stop the batch, per Error handling's Run-level failures
            counts[result] = counts.get(result, 0) + 1
    finally:
        browser.close()
        with db:
            db.execute(
                "UPDATE run_log SET status = ?, ended_at = ?, outcome_counts = ? WHERE id = ?",
                ("partial" if "session_expired" in locals() else "success", clock.stamp(), str(counts), run_id),
            )
```

```python
"""ARCH-BOT-02 — the ApplyBrowser seam, parallel to MCFBrowser and SingpassBrowser.

from __future__ import annotations

from ..config import Config


class ApplyBrowser(Protocol):
```

```javascript
angular.module('easymcfApp').factory('RunPoller', ['$interval', 'ApiClient', function ($interval, ApiClient) {
  var active = null; // FE-RUN-03: service-level singleton, readable by nav-bar from any page
  function start(runId, onUpdate) {
    function poll() {
      ApiClient.get('run_log', runId).then(function (run) {
        if (onUpdate) { onUpdate(run); }
        if (run.status !== 'running') { stop(); }
      });
    }
    stop();
    active = { runId: runId, timer: $interval(poll, 2000) };
    poll();
    return { stop: stop };
  }
  function stop() { if (active) { $interval.cancel(active.timer); active = null; } }
  return { start: start, isActive: function () { return !!active; } };
}]);
```
