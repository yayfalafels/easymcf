# Apply Automation - Feature tracker
>Review the guidelines before performing any actions including edits on the document

## 010.11 (pending) apply automation

Implements the **requirements** doc's Automated apply section (REQ-APPLY-01..11) and the apply-facing half of REQ-FE-01/02: establishing the MCF session the whole feature depends on, queuing `PROSPECT` leads into a batch, running the apply state machine against them, propagating each outcome back into the lead lifecycle milestone 09 already owns, and giving the user the CVs, Applications, and Automation screens to drive and repair all of that without touching the database directly. Builds on the schema and seed data milestone 08 already delivered for `cv`/`application`/`session`, and closes out the last of the four functional-area milestones (07 env, 08 schema, 09 CRM, 10 search) this release's UI depends on.

## Scope

Build the apply-automation feature end to end on top of milestone 08's schema and seed data and milestone 09's lead lifecycle: the CV catalog CRUD, the batch queue/run/remove flow, the browser-driven per-lead apply state machine, the MCF session upload/status mechanism it depends on, the apply-outcome-to-lead propagation effects, and the AngularJS screens (**user interface** pages 2, 7, and 8) that let a user drive, monitor, and manually repair the whole cycle without a database or MCF-site detour.

In scope:

- **backend — CV catalog CRUD** (`API-CAT-01` generic, REQ-APPLY-02): create/edit `cv` labels. `DELETE /api/v1/cv/{id}` on a label still referenced by `track.default_cv_id` or `application.cv_id` fails the FK constraint, translated by the generic handler into a descriptive `409` rather than a bare SQL error, per the **api design**.
- **backend — application queue** (`API-EP-02 POST /api/v1/applications/queue`, REQ-APPLY-01): each `lead_id` must currently be at stage `PROSPECT` (`409` naming the first offending id otherwise), transitions to `TOAPPLY`, and gets one `application` row ready to run. **Unsettled**: `easymcf/db/schema.sql`'s `application.status` `CHECK` constraint currently enumerates only the eight apply-run outcome codes (REQ-APPLY-04) and has no `queued` value, while the **api design** and **workflows** doc both describe this endpoint writing `application(status='queued')`. Design must reconcile this before implementation, either by widening the `CHECK` vocabulary to include `queued` or by modeling the pre-run queue state some other way. Either way this is a schema/seed touch-up on top of milestone 08's delivered set rather than a re-open of its design.
- **backend — application dequeue** (`API-EP-03 POST /api/v1/applications/{id}/dequeue`, REQ-APPLY-11): deletes the `queued` `application` row (`409` if it has already been attempted) and closes its owning lead with `close_reason='withdrawn'` — never a revert to `PROSPECT`, and never eligible to be re-queued later.
- **backend — application read** (`API-HOOK-02` hook, `GET`/`search` generic): `status`/`error_detail`/`attempted_at` are written only by the apply-run service, internally, via the same persistence call the generic blueprint would use, never a second write path. `POST`/`PUT`/`DELETE` beyond `API-EP-02`/`03` are not exposed.
- **backend — apply run trigger** (`API-EP-05 POST /api/v1/runs/apply`, REQ-APPLY-03/06/07/08): no request body, runs every currently-`queued` application. Aborts the whole run up front if the `session` row is not `valid`. REQ-APPLY-06 evaluates this once for the entire batch, at the start of the run. Same one-run-at-a-time concurrency guard as the search run (`ARCH-RUN-03`'s partial unique index on `run_log`), returning `409` with the in-flight `run_log.id` on collision.
- **backend — apply automation engine** (REQ-APPLY-03/04/05/07/08): the per-lead state machine — load post URL, poll the apply button up to `APPLY_POLL_RETRIES`/`APPLY_POLL_DELAY_S` apart (`ARCH-BOT-05`), click, select the assigned CV by substring match against resume options, advance, submit final review — reaching the full outcome vocabulary (`applied`, `questionnaire_required`, `cv_selector_error`, `unable_to_apply`, `post_unavailable`, `cv_not_found`, `post_closed`, `invalid_input`). All MCF interaction goes through `ARCH-BOT-02`'s `MCFBrowser` seam, so the same code path runs in `fixture` and `live` mode. A failure on one queued application never stops the batch and results are merged back keyed by lead id (REQ-APPLY-08), mirroring the prototype's `combine_first()` pattern rather than replacing the whole result set per run.
- **backend — session management** (`API-HOOK-04` hook, REQ-APPLY-06): `GET /api/v1/session/1` generic read for the status badge. `PUT`/`POST /api/v1/session` is blocked, since a raw field write could claim `status='valid'` without an actual validated cookie ever being uploaded. `API-EP-06 POST /api/v1/session/upload` validates at least one loaded cookie matches the MCF domain, writes `.secrets/mcf_session.json` (`ARCH-BOT-03`, `0600`/`0700` permissions), and updates the `session` row's `status`/`uploaded_at`/`cookie_ref` to the filename reference only, keeping the raw cookie value out of the database.
- **backend — apply-outcome to lead propagation** (Workflow 7, REQ-APPLY-09/10): internal to the apply-run service, never a client-visible endpoint. `applied` transitions the lead to `APPLIED`. `post_closed`/`post_unavailable` auto-close the lead with `close_reason='apply_failed'`. Every other outcome, `questionnaire_required`, `cv_not_found`, `cv_selector_error`, `unable_to_apply`, or `invalid_input`, leaves the lead at `TOAPPLY` for the user to repair and retry. This milestone owns writing these effects. The stage machine and close-reason vocabulary they write into belong to milestone 09.
- **backend — run status read** (REQ-PLAT-03, REQ-FE-02): reuses milestone 10's `run_log` `GET`/`search` surface for `run_type='apply'` rows — `track_id` null, `trigger_source` always `'manual'`, since nothing schedules an apply run in `010`.
- **frontend — CVs page** (**user interface** page 2): list/create/edit CV labels, reached from the "Manage CVs" link on Tracks and from the CV override control on Applications. It has no standalone nav entry, per the **user interface** design's information architecture.
- **frontend — Applications page** (**user interface** page 7): the queued-application list with per-row CV override, defaulting to the track's default CV, and an inline "manage CVs" link. Visual flagging and re-queue blocking for an application left with an unresolved `cv_not_found`. Remove-from-queue behind the confirmation-modal pattern. Inline session status that disables "Run" with an explanation when the session is invalid. "Run apply batch" behind the confirmation modal into the async running state with per-application progress. The post-run results view shows a per-outcome next action per Workflow 7's table.
- **frontend — Leads page queue-action wiring** (**user interface** page 5, boundary with milestone 09): milestone 09 already built the Pipeline board's "select for apply queue" bulk-selection control as UI shell. This milestone wires that control's action to `POST /api/v1/applications/queue` now that the endpoint exists. It does not rebuild the Leads page or its stage tabs. **Unsettled**: the **requirements** (REQ-APPLY-01) and Workflow 6 describe selecting leads while still at stage `PROSPECT`, which then advances to `TOAPPLY`. The **user interface** design's page 5 section instead places the checkbox on already-`TOAPPLY` cards. Design must reconcile which stage the selection control actually lives on before this wiring step, in coordination with whoever holds the Leads-page edit locations.
- **frontend — Automation page** (**user interface** page 8): the **Runs tab** shows a reverse-chronological `run_log` list, type, track if applicable, start/end time, status, and outcome counts, with expandable error detail, and apply-run rows link to their resulting applications. The **Session tab** shows current status and last-uploaded-at, a "Log in to MCF" external-browser link, an upload-session control with an inline validation-failure error, and a confirmation-modal-gated overwrite of an existing valid session. This is the same component the global session-status badge opens as an overlay from any page.
- **manual repair path** (REQ-APPLY-05, this milestone's UI, not a new backend mechanism): a lead left at `TOAPPLY` after `questionnaire_required` or any other retryable outcome is repairable two ways, both already covered by existing surfaces rather than new ones — the user completes the application directly on MCF and then manually advances the lead to `APPLIED` from the Lead Detail panel (milestone 09), or fixes the underlying problem (CV assignment, input) and re-queues it through this milestone's queue flow.
- **run-status/error surfacing** (REQ-FE-02): a failed or rejected `application`/`session` write surfaces in the UI through the **user interface** design's cross-cutting error-surfacing pattern, not only in a console or log.

Out of scope:

- the Tracks page (**user interface** page 1), the Posts/results screen (page 3), the Manual Post Entry dialog (page 4), and the search/scoring pipeline behind them — milestone 10. This milestone consumes `track.default_cv_id` as a read-only default and does not touch the Tracks form.
- the Leads page's stage tabs, the Lead Detail panel, the lead stage state machine, close-reason vocabulary, and auto-expiry — milestone 09. This milestone only writes the two specific propagation effects, the `APPLIED` transition and the `apply_failed` close, into that already-built machine, and wires one existing control's action, per the boundary noted above. It does not re-open page 5/6's design.
- automating the Singpass login, MFA, or CAPTCHA step — explicitly out of scope release-wide (REQ-APPLY-06). The "Log in to MCF" action opens an ordinary, un-automated external browser context. Login itself is a manual human action outside `MCFBrowser` (`ARCH-NET-03`).
- automating multi-step questionnaire completion — explicitly out of scope (REQ-APPLY-05). This milestone only detects and records `questionnaire_required`, and leaves completing it to the user on MCF.
- `cv`/`application`/`session` schema and seed-data generation beyond the queued-status reconciliation noted above — delivered by milestone 08 (`easymcf/db/schema.sql`, `seed/13_application.sql`, `seed/14_session.sql`). This milestone reuses that seed set, extending it only where Design finds a concrete gap (the queued-status rows needed to exercise the Applications-page queue view being the known one).
- any OS-level scheduler for apply runs — apply runs are always user-triggered (`ARCH-RUN-02`, `run_log.trigger_source` always `'manual'` for `run_type='apply'`). Milestone 10's in-process scheduler covers only search runs. This milestone adds no scheduling mechanism of its own.
- any analytics/BI/reporting pipeline — release-wide exclusion (**requirements** Out of scope section). Automation's Runs tab (diagnose a run without re-running it) is not a metrics or reporting screen.
- multi-user support/ownership beyond the single seeded user — out of scope release-wide.
- any request against the live MCF site, and any read or commit of a real session cookie export, in an automated or unattended context (**project boundaries**, REQ-DEV-03/04). This is the highest-blast-radius milestone in the release — a bug here submits real job applications — so development, tests, and every agent-run validation loop use `MCF_MODE=fixture` against the `apply/{scenario}/` fixture corpus (`ARCH-TEST-04`) covering all eight outcome codes. `MCF_MODE=live` and a genuine `.secrets/mcf_session.json` are deliberate, per-invocation human actions, never this milestone's default and never something an agent satisfies on its own (`ARCH-TEST-06`).

**closure**

- **11.CK.01** every one of REQ-APPLY-01..11 is implemented and independently verified by the Test cases section this milestone writes.
- **11.CK.02** a user can select one or more `PROSPECT` leads from the Leads page and queue them for apply. Each transitions to `TOAPPLY` and gets exactly one `application` row ready to run, and queuing an already-non-`PROSPECT` lead is rejected with `409`.
- **11.CK.03** a user can review the queue on the Applications page, override the CV per application, and remove a queued application before running — removal closes the owning lead as `withdrawn`, never reverting it to `PROSPECT`, and it is never re-queued later.
- **11.CK.04** triggering "Run apply batch" aborts the entire run up front, with no per-application attempts made, if the session is not `valid`. Otherwise every queued application is attempted, and every one of the eight outcome codes is reachable deterministically against the fixture corpus.
- **11.CK.05** a failure on one queued application in a batch never stops the run from attempting the rest, and never overwrites another application's already-recorded outcome (REQ-APPLY-08), verified against a run containing a mixed-outcome batch.
- **11.CK.06** each apply outcome propagates to its lead exactly per Workflow 7's table — `applied` to `APPLIED`, `post_closed`/`post_unavailable` to `CLOSED` (`apply_failed`), every other code leaves the lead at `TOAPPLY` — and this does not regress milestone 09's stage machine or its unconditional-overwrite regression guard.
- **11.CK.07** a user can establish or refresh the MCF session through the in-app upload dialog. A cookie not matching the MCF domain is rejected with an inline error rather than a silent no-op. Session status, `valid`, `expired`, or `missing`, is visible from the global badge and the Automation Session tab from every page.
- **11.CK.08** a lead left at `TOAPPLY` after `questionnaire_required`, `cv_not_found`, `cv_selector_error`, `unable_to_apply`, or `invalid_input` can be manually repaired — completed directly on MCF and then manually advanced to `APPLIED` from the Lead Detail panel, or fixed and re-queued — without any code path assuming the automated run is the only way to reach `APPLIED`.
- **11.CK.09** the Applications page and the Automation page (Runs and Session tabs) are reachable, populated from seed/fixture data, and every action (queue review, CV override, remove, run, session upload) round-trips through the real backend API, not a client-side mock.
- **11.CK.10** the CVs page supports create/edit/delete of CV labels, reachable from Tracks and from the Applications CV override control, and deleting a label still referenced by a track default or an application override returns a descriptive `409` rather than a bare SQL error.
- **11.CK.11** a rejected or failed `application`/`session` write surfaces its error in the UI (REQ-FE-02).
- **11.CK.12** milestone 07's, 08's, 09's, and 10's own closing commands still pass unmodified against this milestone's changes — no regression.
