# OAuth Login - Feature tracker
>Review the guidelines before performing any actions including edits on the document

## 010.13 (closed) oauth login

Adds user accounts to easymcf. A visitor creates an account or signs in with Google or with an email and password. Every page then shows a minimal signed-in user section with a profile photo in a circle icon and a log out option, and every screen and API read shows only the signed-in user's own data. The feature uses standard, well-supported building blocks and does not invent its own authentication scheme.

## Scope

Build sign-up, sign-in, sign-out, a per-user profile photo, and per-user data isolation on top of the schema milestone 08 delivered and the screens milestones 09 to 11 deliver. The **data model** already carries a `user` table and a `user_id` column on `track`, `cv`, and the MCF session table, which this feature activates and renames from `session` to `mcf_session`, so it cannot be mistaken for the sign-in session this feature adds. The **architecture** and **requirements** documents currently treat `010` as single user with no authentication, so this feature changes release-wide assumptions and updates those documents as part of its own scope.

In scope:

01. **backend email and password accounts.** A visitor creates an account with an email address and a password. Passwords are stored only as salted hashes produced by a maintained library and never as plain text. Sign-in checks the hash and starts a server-side session carried by a signed, HttpOnly cookie. Sign-out ends that session. A duplicate email, a malformed email, and a password that breaks the strong password policy are rejected with a descriptive error that lists every unmet rule. The policy covers a 12 character minimum, upper and lower case letters, a digit, a symbol, and no use of the account's own email or name. Standard library choices are settled in Design.
02. **backend Google sign-in.** A visitor signs in or creates an account with a Google account through the standard OAuth 2.0 authorization code flow with OpenID Connect. The callback verifies the identity token, then signs the user in. A Google identity whose verified email matches an existing account links to that account. Any other Google identity creates a new account. The client id comes from the untracked `.env` and the client secret from a file under `.secrets/`, and neither is ever in the repository.
03. **backend session and current user.** A current-user endpoint returns the signed-in user's id, display name, email, and photo reference, and returns `401` when nobody is signed in. Every API route except the sign-up, sign-in, Google callback, and health routes requires a signed-in user.
04. **backend per-user data scoping.** Every list, read, and write is filtered to the signed-in user's own rows. `track`, `cv`, and `mcf_session` are owned directly through `user_id`. `search_profile`, `search_schedule`, `lead`, `lead_note`, `lead_event`, `application`, `run_log`, `post_track`, and `match_score` are owned through their track or lead. The shared `post` table stays shared across users and read-only to every user, and a user sees a post through their own tracks. A lead holds its own editable copy of the post's title, company, URL, and deadline, so a user changes a lead and never a post. A request for another user's row returns `404`. Scoping is applied once in the generic CRUD layer and the named endpoints, with no per-route filtering written by hand.
05. **backend per-user runs.** A search run, an apply run, and a scheduled run execute on behalf of one user and touch only that user's tracks, leads, applications, and MCF session. The one-run-at-a-time guard and the scheduler tick account for more than one user.
06. **backend profile and photo.** A signed-in user uploads a profile photo, replaces it, and removes it. The upload accepts common image types, enforces a size limit and content type check, stores the file under a per-user path outside the web root, and serves it only to its owner. A Google account's picture is used as the initial photo until the user uploads their own.
07. **data model update.** Edit `easymcf/db/schema.sql` to add the sign-in fields to `user`, which are a unique email, a password hash that is null for a Google-only account, a Google subject identifier, a display name, and a photo reference. Rename the `session` table to `mcf_session` together with its index and foreign key references, and update its resource, its endpoints, and every reference in code, seed, and documents. Bump `meta.schema_version` to the next value in the **data model** Schema versions table, extend `scripts/gen_test_data.py` to seed more than one user with distinct data, and re-run `scripts/resetdb.py --seed`. Recreate-don't-migrate stays in force per `ARCH-STO-02`. Replace the lead's `title_override` and `company_override` columns with the lead's own `position_title`, `company_name`, and `url_ref`, add `user_id` to `lead` and `run_log`, and make the lead key unique per user and post. The single seeded user becomes a known test account with a known password, and a second seeded user has distinct data.
08. **frontend sign-in and sign-up pages.** A sign-in page and a sign-up page offer email and password forms and a Continue with Google button. The sign-up page shows a live checklist of the password rules. Validation errors and failed sign-in attempts surface through the **user interface** design's cross-cutting error-surfacing pattern. An unauthenticated visit to any other route redirects to sign-in, and a successful sign-in returns the user to the page they asked for.
09. **frontend signed-in user section.** Every page shows a minimal user section in the shared header. It holds a circle icon that displays the user's photo, or their initials when no photo exists, and a menu with Upload photo and Log out. Log out returns the user to the sign-in page and clears client-side state.
10. **frontend per-user screens.** Tracks, Search Profiles, Posts, Leads, CVs, Applications, and Automation render only the signed-in user's data, and a `401` from any call sends the user to sign-in. The Leads cards and the Lead Detail panel read and edit the lead's own title, company, URL, and deadline, and never write to a post.
11. **validation utility extension.** Extend `scripts/api_tester.py` and `scripts/ui_tester.py` in place with per-user sign-in and cookie jars, so a case can authenticate as a named seeded user before its requests and checks, along with redirect, header, cookie, file upload, and URL assertions. Existing case-file fields and the log format stay as they are. Automated tiers exercise Google sign-in against a stubbed identity provider.
12. **live Google sign-in validation.** A live tier case signs in through the real Google identity endpoints with a real Google account and confirms the callback, account creation, account linking on a returning identity, and photo import all work end to end. It follows the human-gated pattern of `ARCH-TEST-06`. It sits behind the `live` marker, which `pytest.ini` deselects by default, runs only with an explicit opt-in flag, and needs an OAuth client id and secret in local environment configuration plus a Google account whose consent only the user can give. The stubbed-provider cases and the mock end to end cases must pass first. An agent never runs this tier on its own initiative and no automated loop invokes it. The user triggers it deliberately, and an agent may prepare the case, the run command, and the evidence capture.
13. **document updates.** Update the **requirements**, **architecture**, **data model**, **api design**, **user interface**, and **workflows** documents so they describe an authenticated, multi-user `010` and no longer say otherwise. The release-wide exclusion of multi-user support in those documents and in the project instructions is revised as part of this feature.

Out of scope:

01. Email verification, password reset by email, and any outbound email. These need a mail service and are deferred.
02. Multi-factor authentication for easymcf accounts, account lockout policies beyond basic rate limiting, and social providers other than Google.
03. Roles, teams, sharing of leads between users, and any admin console.
04. Account deletion and data export.
05. Cloud deployment, a hosted identity provider, and any change to the network binding. The Flask process stays bound to `127.0.0.1:5000` per `ARCH-NET-01`.
06. Automating MCF login. The per-user MCF session upload flow from milestone 11 stays manual per REQ-APPLY-06.

Decisions to settle in Design before implementation:

01. The **requirements**, **architecture**, and project instructions currently exclude multi-user support and authentication from `010`, and `ARCH-NET-03` allows no outbound network calls except to MyCareersFuture. Google sign-in adds outbound calls to Google. Design records these as deviations and names the approving decision.
02. Google sign-in needs an OAuth client registered in a Google Cloud project, which only the user can create. Design defines the redirect URI for a loopback origin, the local configuration variables, the opt-in flag for the live tier, and where the live run's evidence is recorded. Design also decides how the live case keeps the Google account credentials out of the repository and the logs.
03. The choice between a server-side session cookie and a signed token. The recommendation is the server-side session cookie, since the app is a single origin and needs no cross-origin tokens.
04. Ownership of `run_log` rows and the scheduler behavior when several users have due schedules.

## Test strategy

Six verification layers, each following the release-level ids in the **test strategy doc**. The layers run in this order. Every layer checks independently of the layers before it, per `STRAT-TOOL-04`.

01. **self-report, one utility per silo.** Case-config replay through the **api tester** and the **ui tester** against a running instance, per `STRAT-TOOL-01/02`. Each case is a `PASS`, `FAIL`, or `ERROR` verdict. Weakest alone, since a verdict proves a status code or a rendered element and cannot prove that a password was hashed, that a row is really owned by the right user, or that a file landed where it should.
02. **direct inspection.** The **db util** queried against the same database a case just wrote to, plus direct reads of the photo store on disk and a scan of the logs, per `STRAT-SILO-02` and `STRAT-TOOL-03`. This layer proves the password hash, the account linking outcome, the ownership columns, the stored photo path and its permissions, and the absence of secrets.
03. **oracle.** Hard-coded-expectation pytest per `STRAT-SILO-05`, calling the auth service, the tenancy layer, and the scheduler directly. Expected values come from this tracker's Scope and closure text and never from the code under test. This layer owns the logic that no response shape can prove, which is the tenancy matrix, the token validation matrix, the account linking matrix, the password and photo boundaries, session expiry, and rate limiting.
04. **mock end to end.** Playwright against the real backend and a stub identity provider, per `ARCH-TEST-04` and `STRAT-02`. The stub is a local OpenID Connect server that signs its own tokens with a test key, so the full authorization code flow runs with no network call. It confirms wiring across the browser, the backend, and the provider protocol.
05. **live tier.** A human-triggered run against the real Google identity endpoints, per scope item 12 and `ARCH-TEST-06`. It runs only after layers 01 to 04 pass. It confirms that the real provider behaves as the stub assumes, and it owns no application logic.
06. **human validation.** Per `STRAT-HUMAN-01/02`, the last step. A person clicks through the running app once every automated layer and the live tier are green, following the checklist derived from the closure items that have a user-visible surface.

Strategy rules applied to this feature:

01. **tenancy leaks are the named regression.** An unscoped route is the defect this feature is most likely to ship. Per `STRAT-CASE-04` the tenancy matrix is a permanent case. Per `STRAT-CASE-05` it is generated from the resource registry, so a resource added later without scoping fails the matrix until it is scoped.
02. **every boundary gets both sides.** Per `STRAT-CASE-03` the password length minimum, the photo size limit, the session lifetime, and the rate limit window each get a case at the boundary and one unit past it. The threshold values come from Design.
03. **no wall clock, no sleep.** Per `STRAT-CASE-06` session expiry, rate limit windows, and token expiry read time through `clock.py::now()`, and the stub provider issues tokens with explicit timestamps.
04. **no secret is ever a test input from the repository.** Test accounts and the stub provider's signing key are generated fixtures with obviously fake values. The client id and the test account for the live tier live only in the untracked `.env`, and the client secret lives only in `.secrets/gcp_oauth_client_secret`.
05. **isolation.** Every case that writes runs against a freshly reset temp database and a temp photo store, so the full set is idempotent when run twice in a row.

**utility gaps this feature closes.** The **api tester** and the **ui tester** replay unauthenticated requests. The **api tester** carries no cookie jar, cannot assert on headers, cookies, or redirects, cannot send a file part, and neither utility can act as a second user. Task 13.11 extends both in place per `STRAT-TOOL-04`'s reuse-first rule. The Design section specifies the fields.

01. an `as_user` field on a case selects a seeded account from `tests/support/users.json`. The tester keeps one cookie jar per name and signs in on first use, which is what lets one file assert that user B cannot read user A's row.
02. cases without `as_user` share one anonymous jar for the whole file, so a sign-up, sign-in, and sign-out sequence keeps its cookie between cases.
03. `follow_redirects`, `expected_headers`, `expected_cookie`, and `files` fields cover the redirect, header, cookie, and upload assertions.
04. a failed sign-in classifies the case `ERROR` and not `FAIL`, since the assertions never ran.
05. the **ui tester** applies `as_user` to its browser context before the route loads, and gains an `upload` op and a `url_path_equals` expect op.

Existing case-file fields and the log format stay as they are, and a file that uses none of the new fields behaves as before.

**test support this feature adds.**

01. a stub identity provider under `tests/support/`, started by fixtures and by the standalone run command below. It serves discovery, authorize, token, and JWKS endpoints, and each scenario is selectable by the email address entered on its consent page, which covers a valid identity, an unverified email, an expired token, a wrong audience, and a denied consent.
02. a second seeded user with distinct data, delivered through `scripts/gen_test_data.py`.
03. the `--run-live` option and the `tests/live/` directory.

## Design

01. **requirements**: a new Accounts and sign-in section, `REQ-AUTH-01..08`, and the revised Out of scope list and actor description, which drop the single local user statement.
02. **architecture**: `ARCH-NET-01` keeps loopback binding and gains the authentication paragraph. `ARCH-NET-03` gains the Google endpoints as the second permitted outbound destination, used only by the sign-in flow. `ARCH-RUN-03` becomes one run of each type per user. `ARCH-SCHED-04` and its emergent consequence follow. `ARCH-RUN-07` gains the configuration variables below. `ARCH-BOT-03` names the per-user session file. `ARCH-TEST-04` gains the stub identity provider and `ARCH-TEST-06` gains the Google live case.
03. **data model**: the `user`, `auth_session`, `lead`, `run_log`, `cv`, and `mcf_session` changes below, including the rename from `session`, including the lead's own copies of the post's display fields, and schema version 8 in the Schema versions table.
04. **api design**: the `API-EP-08..17` auth endpoints, the ownership rule for every `API-CAT` resource, and the `401` and `404` behavior. The resource is renamed `mcf_session`. It is read through a search filtered to the caller, `GET /api/v1/session/1` is retired, and `POST /api/v1/session/upload` becomes `POST /api/v1/mcf_session/upload`.
05. **workflows**: a new Workflow 10, Accounts, sign-in, and sign-out, and per-user wording in Workflows 1 to 8.
06. **user interface**: pages 9 and 10, Sign in and Sign up, the shared user section, and the `401` behavior in the cross-cutting error-surfacing pattern.
07. **frontend app**: the auth service, the route guard, the HTTP interceptor, and the user section directive.
08. **test data**: the second seeded user and the seeded password hashes.
09. **job leads tracker**: the `lead` columns `title_override` and `company_override` are replaced by `position_title`, `company_name`, and `url_ref`. The promotion service, the lead update schema, the Leads page, and the Lead Detail panel that milestone 09 delivered read and write those columns, and the `post` update path and its Save post URL control are removed.
10. **apply and search features**: the apply feature uses the `mcf_session` table name and endpoint paths in place of `session`. Search and apply features implement their run and MCF session endpoints with the caller's user id passed explicitly. This design fixes that contract so their edit locations account for it.

### Workflow

**Sign up** (Workflow 10). `POST /api/v1/auth/signup {name, email, password}`.

01. The body is validated. Name is 1 to 80 characters after trimming. Email is at most 254 characters, matches `^[^@\s]+@[^@\s]+\.[^@\s]+$`, and is stored lowercased. The password must satisfy the password policy. Sign in only requires a password of 1 to 128 characters, so the policy never blocks an existing account from signing in.
02. A duplicate email answers `409` with `field: "email"`.
03. In one transaction the service inserts the `user` row with `status='active'` and the password hash, inserts the user's `mcf_session` row with `status='missing'`, and creates an `auth_session`.
04. The response is `201` with the user object and the session cookie. The visitor is signed in.

**Sign in.** `POST /api/v1/auth/signin {email, password}`.

01. The failure counter for the lowercased email is checked first. At the limit the response is `429` with `Retry-After`, and the password is not evaluated.
02. The user row is loaded. The service always performs one hash verification. A missing user, a user without a password hash, and a user whose status is not `active` are verified against a fixed dummy hash, so the timing and the response match a wrong password.
03. A failure answers `401 invalid_credentials` with the message `Email or password is incorrect.` in every failing case, and increments the counter.
04. A success clears the counter, deletes expired `auth_session` rows, creates an `auth_session`, and answers `200` with the user object and the cookie.

**Sign out.** `POST /api/v1/auth/signout` deletes the caller's `auth_session` row if one exists, expires the cookie, and answers `204`. The endpoint is idempotent and open, so a stale cookie can always be cleared.

**Every request.** A `before_request` hook on the application runs three steps in order.

01. For `POST`, `PUT`, and `DELETE`, an `Origin` header that is present and names a different host than `Host` answers `403 forbidden_origin`.
02. The session cookie is verified for its signature, hashed, and looked up in `auth_session` joined to an `active` user with `expires_at` after `clock.now()`. A match sets `g.user_id`.
03. A request to any `/api/v1` route outside the public set with no `g.user_id` answers `401 unauthenticated`. The public set is `health`, `auth/signup`, `auth/signin`, `auth/signout`, `auth/config`, `auth/google/start`, and `auth/google/callback`. The SPA static route is public, since it serves code only.

**Google sign-in** (Workflow 10). Start, provider consent, callback, then the linking rules in the third party section below. Every callback outcome is a `302`. Success goes to the validated `next` path and any failure goes to `/signin?error=<code>`.

**Return to the requested page.** A protected route visited while signed out redirects to `/signin?next=<path>`. Sign in, sign up, and the Google callback all end at `next` when it is a same-origin path, meaning it starts with a single `/` and not `//`, and at `/` otherwise.

**Profile photo.** Upload replaces any existing photo. Delete removes it. The signed-in user section shows the photo, or initials when none exists. A Google account's picture is imported once, when the account is created or linked and no photo exists.

**Promotion copy.** `POST /api/v1/lead {post_id, track_id}` requires the post visible and the track owned. In one transaction the service inserts the lead with `user_id` from the track, and copies `position_title`, `company_name`, and `url_ref` from the post. It computes `deadline` with milestone 09's initial deadline rule from the post's `closing_date` and `posted_date`. The copy happens once. Later changes to the post, including a detail pass that fills `closing_date` or closes the post, never rewrite the lead's copies.

**Manual lead.** `POST /api/v1/lead/manual` creates a `post` row with `src_method='manual'` on the server and then promotes it through the same copy rule. Users never write a post row. `POST /api/v1/posts/manual` follows the same rule.

**Lead edit.** A user edits a lead's `position_title`, `company_name`, `url_ref`, and `deadline` with `PUT /api/v1/lead/{id}`. Each accepted change writes `lead_event` rows under milestone 09's existing rules, `deadline_changed` for the deadline and `field_edited` for the other three, and refreshes `updated_at`. The post row is never read for display.

**Per-user execution.** Requests scope by `g.user_id`. Background threads carry the user id explicitly.

01. `start_run(user_id, ...)` inserts `run_log.user_id`. The running-run guard is one search and one apply per user, so two users run concurrently.
02. A search run scores a post against the run user's active tracks only, writes `post_track` and `match_score` rows only for those tracks, and its detail pass fetches only posts visible to that user.
03. An apply run attempts the `TOAPPLY` leads of its user and reads that user's `mcf_session` row and session file.
04. The scheduler tick selects due schedules across all users. On `RunInFlight` for a schedule it logs one line, leaves that `next_run_at` untouched, skips the remaining due schedules of the same user, and continues with other users.
05. Startup reconciliation marks every `running` row of every user `failed`.

### Google identity provider

**Library.** Authlib's Flask client performs discovery, the authorization code flow with PKCE, state and nonce handling, id token signature, issuer, audience, and expiry validation. It is added to the ops env manifest. No other OAuth code is written.

```python
oauth.register(
    "google", server_metadata_url=config.google_discovery_url,
    client_id=config.google_client_id, client_secret=config.google_client_secret,
    client_kwargs={"scope": "openid email profile", "code_challenge_method": "S256"},
)
```

**Configuration.** `GCP_OAUTH_CLIENT_ID` from `.env`, the client secret read from the file named by `GCP_OAUTH_SECRET_FILE`, `GOOGLE_DISCOVERY_URL` defaulting to `https://accounts.google.com/.well-known/openid-configuration`, and `GOOGLE_REDIRECT_URI` defaulting to `http://127.0.0.1:{PORT}/api/v1/auth/google/callback`. The secret file defaults to `<SECRETS_DIR>/gcp_oauth_client_secret`, holds the secret alone, and has mode `0600`. The secret is never an environment variable. When the client id is empty or the secret file is absent or empty, `auth/config` returns `google_enabled: false`, the sign-in page hides the button, and `auth/google/start` answers `404 google_not_configured`. The redirect URI registered in the Google Cloud console must equal `GOOGLE_REDIRECT_URI`, and the app must be opened at that same host so the cookie is sent on return.

**Flow.**

01. `GET /api/v1/auth/google/start?next=<path>` stores `next` in a signed transient cookie `easymcf_oauth`, HttpOnly, `SameSite=Lax`, ten minutes, alongside the state, nonce, and PKCE verifier that Authlib writes there. It redirects to the provider with `prompt=select_account`.
02. The provider redirects to the callback with `code` and `state`, or with `error=access_denied`.
03. `access_denied` redirects to `/signin?error=google_denied`. A state mismatch, a token validation failure of any kind, or a nonce mismatch redirects to `/signin?error=google_invalid`. A network failure reaching the provider redirects to `/signin?error=google_unavailable`. A missing email or `email_verified` not true redirects to `/signin?error=google_email_unverified`. None of these creates a user or a session.
04. A validated identity applies the linking rules, creates the `auth_session`, deletes the transient cookie, and redirects to `next`.

**Linking rules.** Evaluated in order, first match wins.

| id | condition                                             | result                                  |
| -- | ----------------------------------------------------- | --------------------------------------- |
| 01 | a user has this `google_sub`                          | sign in to that user                    |
| 02 | a user has this email and the identity is verified    | set `google_sub` on it, sign in         |
| 03 | no user has this `google_sub` or this email           | create a user with a null password hash |

A linked account keeps its password, so both methods work afterward. The verified email condition in rule 02 prevents a takeover through an unverified Google address. Rule 03 sets `name` from the `name` claim, falling back to the email local part.

**Photo import.** When rule 02 or 03 applies and the user has no photo, the service downloads the `picture` claim URL with a five second timeout and processes the bytes through the same photo pipeline as an upload. Any failure logs one line and leaves the user without a photo. A download failure never fails the sign-in.

**Time.** Authlib validates the id token's `exp` against the wall clock. This is the one place `clock.now()` does not apply, and the stub provider sets `exp` and `iat` explicitly relative to the real clock.

**Stub identity provider.** `tests/support/stub_oidc.py` is a small Flask app started by fixtures and by the standalone command in the Test cases section. It serves the discovery document, a JWKS endpoint, an authorize page, a token endpoint that verifies the PKCE challenge, and a fixed PNG at `/picture/<name>.png`. It signs tokens RS256 with an RSA key generated at startup, and its client id and secret are the fake values `stub-client-id` and `stub-client-secret`. The authorize page shows one email field and Approve and Deny buttons. The email's local part prefix selects the scenario.

| id | local part prefix | behavior                                              |
| -- | ----------------- | ----------------------------------------------------- |
| 01 | none              | valid token, `email_verified` true, `picture` present |
| 02 | `unverified`      | `email_verified` false                                |
| 03 | `expired`         | `exp` one hour in the past                            |
| 04 | `badaud`          | `aud` is another client id                            |
| 05 | `badiss`          | `iss` is another issuer                               |
| 06 | `badsig`          | signed with a different key                           |
| 07 | `badnonce`        | `nonce` differs from the request                      |
| 08 | `badstate`        | the redirect carries a different `state`              |

### Authentication components

**Password policy.** Applied at sign-up, and to any future password change. The server checks every rule and reports all unmet rules together.

| id | code                | rule                                                              |
| -- | ------------------- | ----------------------------------------------------------------- |
| 01 | `too_short`         | at least `PASSWORD_MIN_LENGTH` characters, default 12             |
| 02 | `too_long`          | at most 128 characters                                            |
| 03 | `no_lowercase`      | at least one lowercase letter                                     |
| 04 | `no_uppercase`      | at least one uppercase letter                                     |
| 05 | `no_digit`          | at least one digit                                                |
| 06 | `no_symbol`         | at least one character that is not a letter, digit, or whitespace |
| 07 | `contains_identity` | does not contain the email local part or the name without spaces  |

01. rule 07 compares in lowercase and applies only to an email local part or a name of at least four characters.
02. spaces are allowed, so a passphrase can qualify, and count toward length only.
03. a failure answers `400` with `field: "password"`, the message `Password does not meet the requirements.`, and a `rules` array of every unmet code, for example `{"error": "validation_error", "field": "password", "rules": ["too_short", "no_symbol"]}`.

```python
def unmet_rules(password: str, email: str, name: str, min_length: int) -> list[str]: ...
```

**Password hashing.** `werkzeug.security.generate_password_hash` with its default scrypt method and `check_password_hash`. Stored values begin with `scrypt:`. No dependency is added, since Werkzeug ships with Flask.

**Session token and cookie.** The token is `secrets.token_urlsafe(32)`. The database stores its SHA-256 hex digest, so a database read does not yield a usable cookie. The cookie `easymcf_session` carries the token signed with `itsdangerous.URLSafeSerializer(secret_key, salt="easymcf-session")`. Attributes are HttpOnly, `SameSite=Lax`, `Path=/`, `Max-Age` equal to the session lifetime, and `Secure` only when `COOKIE_SECURE=1`. Lifetime is absolute. A session is valid while `clock.now()` is before `expires_at`, with no sliding renewal.

**Secret key.** `SECRET_KEY` when set. Otherwise the app reads `<SECRETS_DIR>/session_key`, or creates it with 32 random bytes and mode `0600` on first start, so a restart keeps users signed in and no key enters the repository.

**Sign-in rate limit.** An in-process table keyed by lowercased email holds failure timestamps read through `clock.now()`. A failure appends, and entries older than `SIGNIN_WINDOW_S` are dropped on every check. With `SIGNIN_MAX_FAILURES=5`, failures one to five answer `401` and the sixth attempt answers `429`, even with the correct password, until the oldest failure ages out. A success clears the key. The process is single, so no shared store is needed.

**Photo pipeline.** Pillow decodes the bytes, which validates that they are an image. A decode failure or a type outside JPEG, PNG, and WebP answers `415`. Bytes beyond `PHOTO_MAX_BYTES` answer `413`, checked on `Content-Length` and again on the read. `Image.MAX_IMAGE_PIXELS` is set to 25 million. The image is center-cropped to a square, resized to 256 by 256, and re-encoded as PNG, which discards metadata and any embedded payload. The content type sent by the client must equal the type Pillow detects, or the answer is `415`.

**Photo storage.** The file is written to `<PHOTO_DIR>/<user_id>/avatar-<sha8>.png`, where `sha8` is the first eight hex characters of the PNG's SHA-256, through a temp file and `os.replace`. Directories are `0700` and files `0600`, following `ARCH-BOT-03`. The previous file is deleted after the new one lands. `user.photo_ref` holds `<user_id>/avatar-<sha8>.png`. `PHOTO_DIR` defaults to `data/photos`, outside `frontend/` and gitignored with `data/`.

**User object.** Returned by signup, signin, `auth/me`, and both photo write endpoints.

```json
{"id": 2, "name": "Sam Second", "email": "second.user@example.test",
 "photo_url": "/api/v1/users/2/photo?v=1a2b3c4d", "auth_methods": ["password", "google"]}
```

`photo_url` is null when no photo exists. `auth_methods` lists `password` when a hash exists and `google` when a subject exists. Neither the hash nor the subject is ever serialized.

### Tenancy layer

**Single declaration.** `easymcf/tenancy.py` holds `SCOPES`, one SQL predicate per table bound to the named parameter `:uid`, and `UNSCOPED = {"role"}`. The generic blueprint and every service read ownership from this module, so no route writes its own filter.

| id | table                                   | predicate over the table's own columns                         |
| -- | --------------------------------------- | -------------------------------------------------------------- |
| 01 | `track`, `cv`, `mcf_session`, `run_log` | `user_id = :uid`                                               |
| 02 | `lead`                                  | `user_id = :uid`                                               |
| 03 | `search_profile`, `search_schedule`     | `track_id IN (SELECT id FROM track WHERE user_id = :uid)`      |
| 04 | `post_track`, `match_score`             | `track_id IN (SELECT id FROM track WHERE user_id = :uid)`      |
| 05 | `lead_note`, `lead_event`, `application`| `lead_id IN (SELECT id FROM lead WHERE user_id = :uid)`        |
| 06 | `post`                                  | linked to the user's tracks through `post_track` or `lead`     |

The `post` predicate is `id IN (SELECT post_id FROM post_track WHERE track_id IN (SELECT id FROM track WHERE user_id = :uid)) OR id IN (SELECT post_id FROM lead WHERE user_id = :uid)`.

**Generic blueprint changes.**

01. `register()` raises at import time for a table that is in neither `SCOPES` nor `UNSCOPED`, so an unscoped resource cannot be added.
02. `_fetch`, `search`, `update`, `delete`, and `bulk_delete` append `AND (predicate)` and bind `uid=g.user_id`. A row outside the predicate is indistinguishable from a missing row and answers `404`, and a search returns only visible rows.
03. `Resource` gains `parents`, a tuple of `(body_field, parent_table)`. On create and batch, each named field must reference a row visible to the caller, or the request answers `404`. Declared parents are `search_profile.track_id` and `search_schedule.track_id` to `track`, `lead.track_id` to `track`, `lead.post_id` to `post`, `lead_note.lead_id` to `lead`, and `track.default_cv_id` and `application.cv_id` to `cv`.
04. `Resource` gains `owned`, a function returning server-set columns. It is applied after schema validation and overrides the body, so `user_id` is absent from the `track` and `cv` create schemas and a client-supplied `user_id` answers `400 not a writable field`. `track` and `cv` set `user_id=g.user_id`, and `lead` sets `user_id` from the owned track.
05. `create_fn` and `update_fn` gain a trailing `uid` argument.

```python
def require_visible(db, uid, table, row_id):
    sql = f"SELECT 1 FROM {table} WHERE id = :id AND ({SCOPES[table]})"
    if db.execute(sql, {"id": row_id, "uid": uid}).fetchone() is None:
        raise RecordNotFound(f"{table} {row_id} not found")
```

**Posts are read-only.** The `post` resource exposes `get` and `search` only, so `POST`, `PUT`, `DELETE`, batch, and bulk delete answer `404` as an unsupported operation. Only the scraper, the manual entry endpoints, and the detail pass write post rows, always on the server. `POST /posts/manual` with a derived id that already exists and is not visible to the caller reuses that row and writes only the caller's `post_track` and `match_score` pairs, answering `201`. When the existing post is visible to the caller it answers `409` as milestone 10 specifies.

**Services.** Every function in `easymcf/services/` that a request or a thread calls takes `uid` and calls `require_visible` for each id it receives. Promotion requires the post visible and the track owned, and writes `lead.user_id`. The scheduler and the run threads take the user id from the track row.

### Data model

Schema version 8. All changes are in `easymcf/db/schema.sql`. Recreate-don't-migrate stays in force per `ARCH-STO-02`.

```sql
CREATE TABLE user (
    id INTEGER PRIMARY KEY,
    name TEXT NOT NULL,
    email TEXT NOT NULL UNIQUE CHECK (email = lower(email)),
    status TEXT NOT NULL CHECK (status IN ('active', 'disabled')),
    password_hash TEXT,
    google_sub TEXT UNIQUE,
    photo_ref TEXT,
    created_at TEXT NOT NULL,
    CHECK (password_hash IS NOT NULL OR google_sub IS NOT NULL)
);

CREATE TABLE auth_session (
    id INTEGER PRIMARY KEY,
    user_id INTEGER NOT NULL REFERENCES user(id) ON DELETE CASCADE,
    token_hash TEXT NOT NULL UNIQUE,
    created_at TEXT NOT NULL,
    expires_at TEXT NOT NULL
);
CREATE INDEX idx_auth_session_user_id ON auth_session(user_id);
```

Changes to existing tables:

01. `cv`: `label UNIQUE` becomes `UNIQUE (user_id, label)`.
02. `session` is renamed `mcf_session`. The `CHECK (id = 1)` is dropped and `user_id` becomes `UNIQUE`. One row exists per user, created at sign-up.
03. `run_log`: adds `user_id INTEGER NOT NULL REFERENCES user(id)`. `ux_run_log_running` becomes `ON run_log(user_id, run_type) WHERE status = 'running'`.
04. `post`: unchanged. `post.id` stays the globally unique identity of a post, shared by every user, and no user owns or edits a post.
05. `lead`: keeps its own `id` as the unique lead identifier and gains `user_id INTEGER NOT NULL REFERENCES user(id)`, so a lead references one user and one post. The `UNIQUE` on `post_id` becomes `UNIQUE (user_id, post_id)`, so each user promotes a post once and two users can each hold a lead on the same post. The columns `title_override` and `company_override` are replaced by the lead's own copies of the post's display fields.

```sql
CREATE TABLE lead (
    id INTEGER PRIMARY KEY,
    user_id INTEGER NOT NULL REFERENCES user(id),
    post_id TEXT NOT NULL REFERENCES post(id),
    track_id INTEGER NOT NULL REFERENCES track(id),
    position_title TEXT NOT NULL,
    company_name TEXT NOT NULL,
    url_ref TEXT CHECK (url_ref IS NULL OR url_ref GLOB 'http://*' OR url_ref GLOB 'https://*'),
    deadline TEXT,
    -- status, stage, close_reason, applied_date, first_attempt_date, last_contact_date,
    -- expected_salary_sgd, created_at, updated_at unchanged
    UNIQUE (user_id, post_id)
);
```

The four display fields are copied from the post at promotion and are the only copy a user sees or edits afterward. `deadline` was already a lead column and keeps milestone 09's maintenance and auto-expiry rules.

A trigger keeps `lead.user_id` equal to the owner of its track, so the ownership shortcut cannot drift.

```sql
CREATE TRIGGER lead_owner_matches_track BEFORE INSERT ON lead
WHEN NEW.user_id != (SELECT user_id FROM track WHERE id = NEW.track_id)
BEGIN SELECT RAISE(ABORT, 'lead.user_id must equal its track owner'); END;
```

The `meta.schema_version` value and the `SCHEMA_VERSION` constant in `easymcf/__init__.py` become 8, and the Schema versions table gains row 08 for this milestone. Ordering assumes milestone 09 (versions 4 to 6) and milestone 10 (version 7) land first, since it edits their tables. If another version lands before this milestone does, the number moves and the table is renumbered.

```python
import re
from werkzeug.security import check_password_hash, generate_password_hash

MAX_LENGTH = 128
DUMMY_HASH = generate_password_hash("dummy-password-for-constant-time")

def unmet_rules(password: str, email: str, name: str, min_length: int) -> list[str]:
    unmet = []
    if len(password) < min_length:                                   unmet.append("too_short")
    if len(password) > MAX_LENGTH:                                   unmet.append("too_long")
    if not any(c.islower() for c in password):                       unmet.append("no_lowercase")
    if not any(c.isupper() for c in password):                       unmet.append("no_uppercase")
    if not any(c.isdigit() for c in password):                       unmet.append("no_digit")
    if not any(not c.isalnum() and not c.isspace() for c in password): unmet.append("no_symbol")
    lowered, local = password.lower(), email.split("@")[0].lower()
    squashed = re.sub(r"\s+", "", name).lower()
    if (len(local) >= 4 and local in lowered) or (len(squashed) >= 4 and squashed in lowered):
        unmet.append("contains_identity")
    return unmet

def hash_password(password: str) -> str:
    return generate_password_hash(password)          # scrypt, "scrypt:" prefix

def verify(stored_hash: str | None, password: str) -> bool:
    ok = check_password_hash(stored_hash or DUMMY_HASH, password)   # one verification in every case
    return ok and stored_hash is not None
```

**13.EL.16** `easymcf/auth/sessions.py`, new. It owns the signing key, the token, the cookie, and the request-to-user lookup.

```python
import hashlib, os, secrets
from datetime import timedelta
from itsdangerous import BadSignature, URLSafeSerializer
from .. import clock

COOKIE = "easymcf_session"

def secret_key(config) -> bytes:
    if os.environ.get("SECRET_KEY"):
        return os.environ["SECRET_KEY"].encode()
    path = os.path.join(config.secrets_dir, "session_key")
    if not os.path.exists(path):
        os.makedirs(config.secrets_dir, mode=0o700, exist_ok=True)
        fd = os.open(path, os.O_WRONLY | os.O_CREAT | os.O_EXCL, 0o600)
        with os.fdopen(fd, "wb") as handle:
            handle.write(secrets.token_bytes(32))
    with open(path, "rb") as handle:
        return handle.read()

def _signer(config):
    return URLSafeSerializer(secret_key(config), salt="easymcf-session")

def _digest(token: str) -> str:
    return hashlib.sha256(token.encode()).hexdigest()

def create(db, config, user_id: int) -> str:
    now = clock.now()
    db.execute("DELETE FROM auth_session WHERE expires_at <= ?", (clock.stamp(now),))
    token = secrets.token_urlsafe(32)
    db.execute("INSERT INTO auth_session (user_id, token_hash, created_at, expires_at) VALUES (?, ?, ?, ?)",
               (user_id, _digest(token), clock.stamp(now), clock.stamp(now + timedelta(hours=config.session_lifetime_h))))
    return _signer(config).dumps(token)

def resolve(db, config, cookie_value: str | None) -> int | None:
    if not cookie_value:
        return None
    try:
        token = _signer(config).loads(cookie_value)
    except BadSignature:
        return None
    row = db.execute(
        "SELECT s.user_id FROM auth_session s JOIN user u ON u.id = s.user_id "
        "WHERE s.token_hash = ? AND s.expires_at > ? AND u.status = 'active'", (_digest(token), clock.stamp())).fetchone()
    return row["user_id"] if row else None

def destroy(db, config, cookie_value: str | None) -> None:
    if not cookie_value:
        return
    try:
        db.execute("DELETE FROM auth_session WHERE token_hash = ?", (_digest(_signer(config).loads(cookie_value)),))
    except BadSignature:
        pass

def set_cookie(response, config, value: str) -> None:
    response.set_cookie(COOKIE, value, max_age=config.session_lifetime_h * 3600, httponly=True,
                        samesite="Lax", path="/", secure=config.cookie_secure)

def clear_cookie(response) -> None:
    response.delete_cookie(COOKIE, path="/")
```

**13.EL.17** `easymcf/auth/ratelimit.py`, new. Time comes from `clock.now()`, so the boundary cases need no sleeping.

```python
import threading
from datetime import timedelta
from .. import clock
from ..errors import TooManyAttempts

_failures: dict[str, list] = {}
_lock = threading.Lock()

def _live(email: str, config) -> list:
    cutoff = clock.now() - timedelta(seconds=config.signin_window_s)
    _failures[email] = [t for t in _failures.get(email, []) if t > cutoff]
    return _failures[email]

def check(email: str, config) -> None:
    with _lock:
        recent = _live(email, config)
        if len(recent) >= config.signin_max_failures:
            wait = int((recent[0] + timedelta(seconds=config.signin_window_s) - clock.now()).total_seconds()) + 1
            raise TooManyAttempts("Too many failed sign-in attempts. Try again later.", retry_after=max(wait, 1))

def record_failure(email: str, config) -> None:
    with _lock:
        _live(email, config).append(clock.now())

def clear(email: str) -> None:
    with _lock:
        _failures.pop(email, None)

def reset() -> None:
    with _lock:
        _failures.clear()
```

```python
def safe_next(value: str | None) -> str:
    return value if value and value.startswith("/") and not value.startswith("//") else "/"

def start(config):
    session.permanent = True
    session["next"] = safe_next(request.args.get("next"))
    return oauth.google.authorize_redirect(config.google_redirect_uri, prompt="select_account")

def _to_signin(code: str):
    session.clear()
    return redirect(f"/signin?error={code}")

def callback(db, config):
    if request.args.get("error"):
        return _to_signin("google_denied")
    try:
        claims = oauth.google.authorize_access_token()["userinfo"]
    except OAuthError:
        return _to_signin("google_invalid")
    except requests.RequestException:
        return _to_signin("google_unavailable")
    if not claims.get("email") or claims.get("email_verified") is not True:
        return _to_signin("google_email_unverified")
    with db:
        user_id = link_or_create(db, config, claims)
        cookie = sessions.create(db, config, user_id)
    target = safe_next(session.pop("next", None))
    session.clear()
    response = redirect(target)
    sessions.set_cookie(response, config, cookie)
    return response

def link_or_create(db, config, claims) -> int:
    sub, email = claims["sub"], claims["email"].lower()
    row = db.execute("SELECT * FROM user WHERE google_sub = ?", (sub,)).fetchone()
    if row:                                                            # rule 01
        return row["id"]
    row = db.execute("SELECT * FROM user WHERE email = ?", (email,)).fetchone()
    if row:                                                            # rule 02, the identity is verified
        db.execute("UPDATE user SET google_sub = ? WHERE id = ?", (sub, row["id"]))
        user_id = row["id"]
    else:                                                              # rule 03
        name = claims.get("name") or email.split("@")[0]
        user_id = db.execute("INSERT INTO user (name, email, status, google_sub, created_at) VALUES (?, ?, 'active', ?, ?)",

    if not db.execute("SELECT photo_ref FROM user WHERE id = ?", (user_id,)).fetchone()["photo_ref"] and claims.get("picture"):
```

```python
import requests
from PIL import Image, ImageOps, UnidentifiedImageError
from ..errors import UnsupportedMedia

Image.MAX_IMAGE_PIXELS = 25_000_000
ALLOWED = {"JPEG": "image/jpeg", "PNG": "image/png", "WEBP": "image/webp"}

def to_avatar(data: bytes, declared: str | None) -> bytes:
    try:
        image = Image.open(io.BytesIO(data))
        detected = image.format
        image.load()
    except (UnidentifiedImageError, Image.DecompressionBombError, OSError):
        raise UnsupportedMedia("The file is not an accepted image.")
    if detected not in ALLOWED or (declared and declared != ALLOWED[detected]):
        raise UnsupportedMedia("Upload a JPEG, PNG, or WebP image.")
    square = ImageOps.fit(ImageOps.exif_transpose(image).convert("RGBA"), (256, 256), Image.LANCZOS)
    out = io.BytesIO()
    square.save(out, "PNG")
    return out.getvalue()

def store(config, user_id: int, png: bytes) -> str:
    ref = f"{user_id}/avatar-{hashlib.sha256(png).hexdigest()[:8]}.png"
    directory = os.path.join(config.photo_dir, str(user_id))
    os.makedirs(directory, mode=0o700, exist_ok=True)
    os.chmod(directory, 0o700)
    fd, tmp = tempfile.mkstemp(dir=directory)
    with os.fdopen(fd, "wb") as handle:
        handle.write(png)
    os.chmod(tmp, 0o600)
    os.replace(tmp, os.path.join(config.photo_dir, ref))
    return ref

    return os.path.join(config.photo_dir, ref)

def replace(db, config, user_id: int, png: bytes) -> None:
    old = db.execute("SELECT photo_ref FROM user WHERE id = ?", (user_id,)).fetchone()["photo_ref"]
    ref = store(config, user_id, png)
    with db:
        db.execute("UPDATE user SET photo_ref = ? WHERE id = ?", (ref, user_id))
    if old and old != ref and os.path.exists(path_of(config, old)):
        os.remove(path_of(config, old))

def remove(db, config, user_id: int) -> None:
    old = db.execute("SELECT photo_ref FROM user WHERE id = ?", (user_id,)).fetchone()["photo_ref"]
    with db:
        db.execute("UPDATE user SET photo_ref = NULL WHERE id = ?", (user_id,))
    if old and os.path.exists(path_of(config, old)):
        os.remove(path_of(config, old))

def import_from_url(db, config, user_id: int, url: str) -> None:
    try:
        response = requests.get(url, timeout=5, stream=True)
        data = response.raw.read(config.photo_max_bytes + 1, decode_content=True)
        if response.status_code == 200 and len(data) <= config.photo_max_bytes:
            replace(db, config, user_id, to_avatar(data, None))
    except Exception:
        pass   # a picture problem never fails a sign-in
```
