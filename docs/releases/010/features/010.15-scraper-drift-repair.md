## 010.15 (pending) scraper drift repair

Detects and repairs breaks in the MyCareersFuture page selectors that the search scraper, the posting detail scraper, and the apply automation depend on. An inspection reads the current markup of each page group, finds broken selectors, repairs the ones a deterministic algorithm can fix, and inventories the rest with the evidence gathered so a person or an agent can finish the repair. An admin-only Scraper Health page shows the last inspection, the open defects with their diagnostics, and a report of past defects and how each was resolved.

## Scope

Build drift detection and repair for the MyCareersFuture markup the scrapers rely on, a persisted repair workflow behind it, and the Scraper Health page that surfaces it. A "drift" is a change in MCF's page markup that stops a selector from resolving or makes it resolve to the wrong content. The prototype's `recommission.py` and the tier 3 smoke protocol in `ARCH-TEST-06` both catch drift only when a person runs them and only report it. This feature makes detection recurring, repairs the simple cases unattended, and keeps a durable record of every case that needs further help. The repair logic is a deterministic algorithm. It fetches a fresh MCF page html, runs pre-determined probes and diagnostics and determines whether to repair or record as a defect for human or ai review. A case the algorithm escalates is logged with the evidence collected, so a person or a coding agent can finish the repair outside the app.

The feature builds on the search scraper and the `MCFBrowser` seam, and extends them in place, reusing the one scheduler thread and browser layer.

Three page groups are in scope. The first two have one fixed reference page the inspection loads on every run. The third, apply workflow, takes its reference page from whichever lead the triggering apply run is processing, per the **triggers and schedule** item below.

| id | page group     | reference page                          | selectors inspected                     |
| -- | -------------- | --------------------------------------- | --------------------------------------- |
| 01 | search results | first page of a canonical search        | card, title, company, date, salary      |
| 02 | post detail    | first open posting on that results page | closed flag, MCF ref, closing date [1]  |
| 03 | apply workflow | the triggering lead's pages [2]         | apply button, CV card, save, submit [3] |

1. also applicants, industry, and description.
2. through the review step, ahead of the final submit. The reference lead is whichever the triggering apply run supplies, see **triggers and schedule** below.
3. also the status text. The submit control is checked for presence only.

The table is a summary. The full selector list per group is settled in Design and comes from the `mycareerfutures` skill and the scraper source code.

In scope:

01. **selector registry.** Every selector the scrapers and the apply automation use moves out of scattered code into one registry keyed by page group and field. The registry is versioned and append only, so a repair always adds a new version and leaves every earlier version intact. The source code reads selectors only through the registry, so a registry update alone changes scraper behavior. Each registry entry also carries what a healthy match looks like, such as the expected element count and the shape of the extracted value, so detection distinguishes a selector that matches zero elements from one that matches the wrong content. Feature 15 owns building the registry and wiring the search, detail, and apply code to read every selector through it, independent of whether features 10 and 11 are implemented yet. A selector already written in feature 10's or 11's code at that point is refactored into the registry. A selector not yet written is defined directly in the registry, so features 10 and 11 build against it from the start.
02. **drift detection.** An inspection loads each reference page through the `MCFBrowser` seam, runs every registered selector against it, and records a result per selector. A selector is broken when it matches zero elements, matches an unexpected number of elements, or extracts a value that fails its item specific validation rule, such as an unparseable date, a posted date outside a plausible range, or a non numeric salary. The live scrapers run this same validation on every real scrape, so a raised exception, the selector throwing outright, and a silent failure, a value that extracts cleanly but fails validation, both count as a drift signal. An inspection separates drift from other causes, such as the site being unreachable, a login wall, a rate limit, or a page with legitimately no results. Those outcomes end the inspection as `blocked` for that page group and raise no defect. Apply workflow pages need the admin's MCF session and report `skipped` when none exists.
03. **deterministic repair.** For each broken selector, the algorithm tries an ordered ladder of candidate strategies, such as a renamed attribute value, a swapped attribute of the same purpose, a match on the label or sample text the field is known to hold, and the same tag and position relative to a stable anchor element. A candidate is accepted only when it verifies against the captured page and matches the entry's healthy shape across all sample elements. What counts as verified differs by field, so Design defines an explicit per-field acceptance table stating the shape and range check each field's candidate output must pass. An accepted candidate is written as a new registry version and the defect is recorded as repaired. Every attempt, accepted or rejected, is recorded with its strategy and evidence.
04. **escalation and defect inventory.** When no strategy verifies, the defect stays open and the algorithm records the initial diagnostics. These cover the failed selector and its last known good version, the failure kind, a sanitized excerpt of the surrounding markup, a ranked list of near miss candidates, a structural diff against the last healthy snapshot when one exists, the page URL, a screenshot reference, and the source locations that read the selector. A repeated detection of the same broken field updates that one open defect, keeping one defect per field. A defect closes only when a later inspection finds the field healthy. A search results or post detail capture is unauthenticated, and is retained under the gitignored `data/` directory for the historical record the **data model update** item describes. An apply workflow capture is authenticated, so it lives only in local runtime storage for the inspection that produced it and is cleared once that inspection ends, repaired or escalated. Only its sanitized excerpt and the other diagnostic fields above persist in the defect record.
05. **triggers and schedule.** The schedule and the manual trigger cover the search results and post detail groups. The apply workflow group carries a higher live-session cost and a lower drift risk than the other two, so its only trigger is a real apply run already walking that lead's pages.
  01. the schedule fires the search results and post detail groups, defaulting to once a day. In production this reads the live MCF site the same way the search by keywords search schedule already does. The automated test suite exercises the schedule against fixtures, and 15.CK.15's live tier case is the human gated check of the production behavior.
  02. a search run requests a search results or post detail inspection when it ends with a raised exception, the selector throwing outright, or a silent failure, a value that extracts cleanly but fails its item specific validation rule, such as an unparseable date or a non numeric salary. An apply run requests an apply workflow inspection on the same two failure kinds, and carries the lead it was processing as that inspection's reference. A debounce limits a run of repeated failures to one inspection per page group.
  03. the admin triggers a search results or post detail inspection manually from the Scraper Health page, and enables, disables, and re-intervals the schedule from the same page.
  One inspection runs at a time, and a trigger that collides with a running inspection is skipped and reported.

Out of scope:

01. Model driven or agent driven repair inside the app. The escalation record is built so an agent can act on it, and the app makes no model calls.
02. Editing selectors by hand from the page. A person or an agent corrects an escalated defect through the registry outside the page, and the next inspection closes the defect once the field is healthy.
03. Automatic re-scraping or re-applying of runs that failed before a repair. A repaired selector applies to the next run.
04. Self healing at scrape time. Repair runs only inside an inspection, and the scrapers use whatever the registry holds.
05. Drift detection for pages outside the three page groups, such as the MCF login flow, profile pages, or the questionnaire steps of an apply.
06. Submitting an application. The inspection verifies the final submit control's presence only.
07. Roles beyond `admin` and `user`, role management screens, any admin surface other than Scraper Health, and email notification of new defects.
08. Cloud deployment, an external scheduler, and any change to the network binding.

## Test strategy

Six verification layers, each following the release-level ids the **test strategy doc** already defines. The layers run in this order, and each checks independently of the layers before it, per `STRAT-TOOL-04`.

01. **self-report, one utility per silo.** Case-config replay through the **api tester** and the **ui tester** against a running instance, per `STRAT-TOOL-01/02`. Each case is a `PASS`, `FAIL`, or `ERROR` verdict. Weakest alone, since a verdict proves a status code or a rendered element, while the registry version a repair actually wrote and a defect's diagnostic evidence are proven by the deeper layers below.
02. **direct inspection.** The **db util** queried against the same database a case just wrote to, per `STRAT-SILO-02`, plus a direct filesystem read of a capture file under `data/` or local runtime storage. This layer proves the registry version history, the defect and repair-attempt rows, the admin role assignment, the schema version, and the capture retention rule the **escalation and defect inventory** item sets, none of which a response body confirms by itself.
03. **oracle.** Hard-coded-expectation pytest calling the detection and repair service functions directly against hand-authored markup mutations of the fixture corpus, mirroring `STRAT-SILO-05`'s service-layer pattern. Each mutation's expected outcome, which selector breaks and what the repaired value should read, is fixed by the test author before the inspection runs, checked against that mutation, independent of the repair algorithm's own report, per `15.CK.03`. This layer owns the ladder strategies, the escalation path, the schedule and debounce arithmetic, and the role matrix for the admin surface, and it carries most of this feature's coverage weight, per `15.CK.18` and the **live tier carries the least weight** strategy rule below.
04. **mock end to end.** Playwright against the real backend and database with MCF replaced by the fixture browser, per `ARCH-TEST-04`. It confirms the Scraper Health page renders, the admin gate holds, and a manual trigger reaches the inspection service through the real UI and API, beyond what the service function alone proves in isolation.
05. **live tier.** A run against the real MCF site, per the **live drift inspection validation** item and `ARCH-TEST-06`, run only after every layer above passes. A healthy live site rarely drifts on any given day, so this layer confirms the reference pages and selectors still resolve against the current markup rather than exercising a repair. The oracle layer above owns detection and repair correctness.
06. **human validation.** Per `STRAT-HUMAN-01/02`, the last step. A person clicks through the Scraper Health page once every automated layer and the live tier are green, following a checklist derived from this tracker's own closure criteria.

Strategy rules applied to this feature:

01. **the mutation is the oracle, independent of the repair's own report.** Per `STRAT-CASE-04`'s named-regression pattern and this feature's own **validation utility extension and drifted fixtures** item, every ladder-strategy case starts from a mutation the test author wrote by hand, and the assertion checks the resulting selector and scraped value against that known mutation.
02. **every attribute in the inventory gets its own mutation case, per `15.CK.18`.** The page groups table and its footnotes name sixteen selectors across the three groups, and each one gets a hand-authored mutation exercising whichever candidate strategy the **deterministic repair** item lists, a renamed attribute value, a swapped attribute, a label or sample text match, or a tag-and-position match against a stable anchor, fits the way that field's markup actually tends to change. At least one mutation per strategy is a hit, and at least one field's mutation matches none of them, exercising escalation and the diagnostics the **escalation and defect inventory** item lists.
03. **no wall clock, no sleep.** Per `STRAT-CASE-06`, the schedule, the debounce window, and `next_run_at` read time through `clock.py::now()`, following the search schedule's own oracle pattern, `10.TC.21` and `10.TC.22`.
04. **the admin surface is exercised as the second user, per `STRAT-CASE-08`.** Every drift endpoint and the Scraper Health page get a non-admin case and an unauthenticated case, alongside the admin happy path, and `13.TC.26`'s tenancy matrix extends to cover the six resources this feature's data model adds.
05. **isolation.** A mutation is applied to a copy of the captured fixture markup at inspection time, and the committed fixture files other silos read stay untouched, so this feature's own tests leave the corpus features 10 and 11 depend on untouched. Every case that writes runs against a freshly reset temp database.
06. **live tier carries the least weight.** A live MCF run rarely drifts on any given day, so the single live-tier case exists to confirm the current site rather than to reach coverage the oracle layer already owns. The sixteen mutation cases and the escalation path above are what this feature's correctness actually rests on.

**time efficient testing**

high value, low latency checks run first, and the full regression suite runs last, once independent failures are isolated and fixed one by one.

make use of time-efficient tests when planning and executing tests and sequence of tests.  Utilize high value, time-efficient tests first, and reserve longer more time-intensive tests in later stages for comprehesive coverage after first exhausting short cycle time high information value testing.

_generic time efficient testing guidelines_

01. run low latency high volume tests such as db inspection and api requests before moving on to more time intensive browser interactive tests and human tests
02. run tests directly related to feature first, and then in later stages expand to more comprehensive tests that include regression testing
03. once failures and exceptions are encountered, 

    - 03.01 first, consolidate and identify independent first-out exceptions
    - 03.02 separate them from cascading failures, then
    - 03.03 one-by-one, run isolated tests narrowly focused on resolving each of these independent issues one-by-one
    - 03.04 only once ALL of these independent issues are resolved run the original complete regression comprehensive test as confirmation or to surface the next independent failure

_specific application to this feature_

01. run the oracle mutation cases and the direct `db_util.py` inspection cases first. Neither needs a browser or a running server, matching `STRAT-SILO-05`'s service-layer pattern, which feature 10's own equivalent, `test_search_pipeline.py`, already showed runs in milliseconds against no live process.
02. run `api_tester.py`/`ui_tester.py` cases against a running dev instance next, narrowed to this feature with `pytest -m backend -k "drift or selector or defect or role"` once the oracle and inspection layers are green, rather than the full backend suite feature 10's logs show growing past 400 cases.
03. run the mock end to end and live tiers last, and only once every layer above passes, since a browser-driven case is the slowest per-case cost this feature has.
04. on a failure, consolidate first-out exceptions, separate them from cascading failures, and resolve them one by one before re-running the full closing command, per `010.10`'s own sequence.
