>Review the guidelines before performing any actions including edits on the document

## 010.15 (pending) scraper drift repair

Detects and repairs breaks in the MyCareersFuture page selectors that the search scraper, the posting detail scraper, and the apply automation depend on. An inspection reads the current markup of each page group, finds broken selectors, repairs the ones a deterministic algorithm can fix, and inventories the rest with the evidence gathered so a person or an agent can finish the repair. An admin-only Scraper Health page shows the last inspection, the open defects with their diagnostics, and a report of past defects and how each was resolved.

## Scope

Build drift detection and repair for the MyCareersFuture markup the scrapers rely on, a persisted repair workflow behind it, and the Scraper Health page that surfaces it. A "drift" is a change in MCF's page markup that stops a selector from resolving or makes it resolve to the wrong content. The prototype's `recommission.py` and the tier 3 smoke protocol in `ARCH-TEST-06` both catch drift only when a person runs them and only report it. This feature makes detection recurring, repairs the simple cases unattended, and keeps a durable record of every case that needs further help. The repair logic is a deterministic algorithm. It fetches a fresh MCF page html, runs pre-determined probes and diagnostics and determines whether to repair or record as a defect for human or ai review. A case the algorithm escalates is logged with the evidence collected, so a person or a coding agent can finish the repair outside the app.

The feature builds on the search scraper and the `MCFBrowser` seam, and extends them in place, reusing the one scheduler thread and browser layer.

Three page groups are in scope. The first two have one fixed reference page the inspection loads on every run. The third, apply workflow, takes its reference page from whichever lead the triggering apply run is processing, per the **triggers and schedule** item below.

| id | page group     | reference page                          | selectors inspected                     |
| -- | -------------- | --------------------------------------- | --------------------------------------- |
| 01 | search results | first page of a canonical search        | card, title, company, date, salary [3]  |
| 02 | post detail    | first open posting on that results page | closed flag, MCF ref, closing date [1]  |
| 03 | apply workflow | the triggering lead's pages [2]         | apply button, CV card, save, submit [4] |

1. also applicants, industry, and description.
2. through the review step, ahead of the final submit. The reference lead is whichever the triggering apply run supplies, see **triggers and schedule** below.
3. also the hit/recommended card marker, since MCF fills a thin result set with recommended cards interleaved among the true hits.
4. also the status text. The submit control is checked for presence only.

The table is a summary. The full selector list per group is settled in Design and comes from the `mycareerfutures` skill and the scraper source code.

In scope:

01. **selector registry.** Every selector the scrapers and the apply automation use moves out of scattered code into one registry keyed by page group and field. The registry is versioned and append only, so a repair always adds a new version and leaves every earlier version intact. The source code reads selectors only through the registry, so a registry update alone changes scraper behavior. Each registry entry also carries what a healthy match looks like, such as the expected element count and the shape of the extracted value, so detection distinguishes a selector that matches zero elements from one that matches the wrong content. Feature 15 owns building the registry and wiring the search, detail, and apply code to read every selector through it, independent of whether features 10 and 11 are implemented yet. A selector already written in feature 10's or 11's code at that point is refactored into the registry. A selector not yet written is defined directly in the registry, so features 10 and 11 build against it from the start.
02. **drift detection.** An inspection loads each reference page through the `MCFBrowser` seam, runs every registered selector against it, and records a result per selector. A selector is broken when it matches zero elements, matches an unexpected number of elements, or extracts a value that fails its item specific validation rule, such as an unparseable date, a posted date outside a plausible range, or a non numeric salary. The live scrapers run this same validation on every real scrape, so a raised exception, the selector throwing outright, and a silent failure, a value that extracts cleanly but fails validation, both count as a drift signal. An inspection separates drift from other causes, such as the site being unreachable, a login wall, a rate limit, or a page with legitimately no results. Those outcomes end the inspection as `blocked` for that page group and raise no defect. Apply workflow pages need the admin's MCF session and report `skipped` when none exists.
03. **deterministic repair.** For each broken selector, the algorithm tries an ordered ladder of candidate strategies, such as a renamed attribute value, a swapped attribute of the same purpose, a match on the label or sample text the field is known to hold, and the same tag and position relative to a stable anchor element. A candidate is accepted only when it verifies against the captured page and matches the entry's healthy shape across all sample elements. What counts as verified differs by field, so Design defines an explicit per-field acceptance table stating the shape and range check each field's candidate output must pass. An accepted candidate is written as a new registry version and the defect is recorded as repaired. Every attempt, accepted or rejected, is recorded with its strategy and evidence.
04. **escalation and defect inventory.** When no strategy verifies, the defect stays open and the algorithm records the initial diagnostics. These cover the failed selector and its last known good version, the failure kind, a sanitized excerpt of the surrounding markup, a ranked list of near miss candidates, a structural diff against the last healthy snapshot when one exists, the page URL, a screenshot reference, and the source locations that read the selector. A repeated detection of the same broken field updates that one open defect, keeping one defect per field. A defect closes only when a later inspection finds the field healthy. A search results or post detail capture is unauthenticated, and is retained under the gitignored `data/` directory for the historical record the **data model update** item describes. An apply workflow capture is authenticated, so it lives only in local runtime storage for the inspection that produced it and is cleared once that inspection ends, repaired or escalated. Only its sanitized excerpt and the other diagnostic fields above persist in the defect record.
05. **triggers and schedule.** The schedule and the manual trigger cover the search results and post detail groups. The apply workflow group carries a higher live-session cost and a lower drift risk than the other two, so its only trigger is a real apply run already walking that lead's pages.
  01. the schedule fires the search results and post detail groups, defaulting to once a day. In production this reads the live MCF site the same way the search by keywords search schedule already does. The automated test suite exercises the schedule against fixtures, and 15.CK.15's live tier case is the human gated check of the production behavior.
  02. a search run requests a search results or post detail inspection when it ends with a raised exception, the selector throwing outright, or a silent failure, a value that extracts cleanly but fails its item specific validation rule, such as an unparseable date or a non numeric salary. An apply run requests an apply workflow inspection on the same two failure kinds, and carries the lead it was processing as that inspection's reference. A debounce limits a run of repeated failures to one inspection per page group.
  03. the admin triggers a search results or post detail inspection manually from the Scraper Health page, and enables, disables, and re-intervals the schedule from the same page.
  One inspection runs at a time, and a trigger that collides with a running inspection is skipped and reported.
06. **data model update.** Add tables and update seed data generator for 
  - selector registry
  - inspections
  - per selector inspection results
  - defects
  - repair attempts
  - drift schedule
  - `user_role` table add `admin` role, assigned by comparing the account's email to the `ADMIN_EMAIL` config value at account creation, and by the seed generator reading the same config value for the seeded admin account. 
  Edit `easymcf/db/schema.sql`, bump `meta.schema_version` to the next value in the **data model** Schema versions table, and extend the seed generator so the seed carries seed data for each resolution method. 
  Recreate-don't-migrate stays in force per `ARCH-STO-02`. 
  Search results and post detail captures are retained as markup files under the gitignored `data/` directory, with the tables holding their references, per the **escalation and defect inventory** item's retention rule. Apply workflow captures stay in local runtime storage only, for the inspection that produced them.
07. **admin role.** Update the `user_role` table to add the `admin` role. Every account has one role, and new accounts default to `user`. Account creation compares the signing up email to the `ADMIN_EMAIL` config value and assigns `admin` on a match, `user` otherwise, for both the password and the Google sign in paths feature 13 defines. `ADMIN_EMAIL` is set in `.env`, and defaults to the seeded initial user's `INITIAL_USER_EMAIL`. The table is named `user_role` because the existing `role` table is the job role a track targets. The Scraper Health page and every endpoint behind it are the only admin only surface. 
08. **backend api.** Admin only endpoints to read the last inspection, the inspection history, the open defects with their diagnostics, and the resolved defect report, to trigger a manual inspection, and to read and update the drift schedule. A non admin caller receives `403` and an unauthenticated caller receives `401`. Endpoints follow the generic shapes of the **api design** wherever a generic shape fits and register any named endpoint in its catalog.
09. **frontend Scraper Health page.** A page reachable only by the admin, with its navigation link shown only to the admin and a route guard that discreetly sends anyone else away redirect to the EasyMCF home landing page. It shows 
  - last inspection result per page group
  - list of open defects in a table with the initial diagnostics visible for each row
  - a control to trigger a search results and post detail inspection
  - schedule settings. 
  Errors and in flight state surface through the existing error surfacing pattern.
10. **resolved defect report.** A report on the same page lists past resolved defects with the page group, field, when it was detected and resolved, the resolution method, and the change made, meaning the old and new selector and the strategy that produced it. A date range filter narrows it.
11. **validation utility extension and drifted fixtures.** Extend `scripts/api_tester.py` and `scripts/ui_tester.py` in place with cases for admin and non admin access to the drift endpoints and page. Add fixture pages that apply known markup mutations to the captured MCF pages, such as a renamed attribute, a removed element, and a restructured container. The mutation is the independent oracle, since the expected repair follows from what was changed, checked independently of the repair code's own output. Existing case fields and the log format stay as they are.
12. **live drift inspection validation.** A live tier case runs one inspection against the real MCF site and confirms the reference pages load, every selector resolves or is reported correctly, and the apply workflow pages are reached with a real session. It follows the human gated pattern of `ARCH-TEST-06`, sits behind the `live` marker, and only the user triggers it. An agent may prepare the case, the command, and the evidence capture.
13. **document updates.** Update the **requirements**, **architecture**, **data model**, **api design**, **user interface**, **workflows**, and the `mycareerfutures` skill so they describe the drift repair feature, the admin role, and the selector registry. The statements that `010` has no roles and no admin console are revised as part of this feature.

Out of scope:

01. Model driven or agent driven repair inside the app. The escalation record is built so an agent can act on it, and the app makes no model calls.
02. Editing selectors by hand from the page. A person or an agent corrects an escalated defect through the registry outside the page, and the next inspection closes the defect once the field is healthy.
03. Automatic re-scraping or re-applying of runs that failed before a repair. A repaired selector applies to the next run.
04. Self healing at scrape time. Repair runs only inside an inspection, and the scrapers use whatever the registry holds.
05. Drift detection for pages outside the three page groups, such as the MCF login flow, profile pages, or the questionnaire steps of an apply.
06. Submitting an application. The inspection verifies the final submit control's presence only.
07. Roles beyond `admin` and `user`, role management screens, any admin surface other than Scraper Health, and email notification of new defects.
08. Cloud deployment, an external scheduler, and any change to the network binding.

## Test strategy

Six verification layers, each following the release-level ids the **test strategy doc** already defines. The layers run in this order, and each checks independently of the layers before it, per `STRAT-TOOL-04`.

01. **self-report, one utility per silo.** Case-config replay through the **api tester** and the **ui tester** against a running instance, per `STRAT-TOOL-01/02`. Each case is a `PASS`, `FAIL`, or `ERROR` verdict. Weakest alone, since a verdict proves a status code or a rendered element, while the registry version a repair actually wrote and a defect's diagnostic evidence are proven by the deeper layers below.
02. **direct inspection.** The **db util** queried against the same database a case just wrote to, per `STRAT-SILO-02`, plus a direct filesystem read of a capture file under `data/` or local runtime storage. This layer proves the registry version history, the defect and repair-attempt rows, the admin role assignment, the schema version, and the capture retention rule the **escalation and defect inventory** item sets, none of which a response body confirms by itself.
03. **oracle.** Hard-coded-expectation pytest calling the detection and repair service functions directly against hand-authored markup mutations of the fixture corpus, mirroring `STRAT-SILO-05`'s service-layer pattern. Each mutation's expected outcome, which selector breaks and what the repaired value should read, is fixed by the test author before the inspection runs, checked against that mutation, independent of the repair algorithm's own report, per `15.CK.03`. This layer owns the ladder strategies, the escalation path, the schedule and debounce arithmetic, and the role matrix for the admin surface, and it carries most of this feature's coverage weight, per `15.CK.18` and the **live tier carries the least weight** strategy rule below.
04. **mock end to end.** Playwright against the real backend and database with MCF replaced by the fixture browser, per `ARCH-TEST-04`. It confirms the Scraper Health page renders, the admin gate holds, and a manual trigger reaches the inspection service through the real UI and API, beyond what the service function alone proves in isolation.
05. **live tier.** A run against the real MCF site, per the **live drift inspection validation** item and `ARCH-TEST-06`, run only after every layer above passes. A healthy live site rarely drifts on any given day, so this layer confirms the reference pages and selectors still resolve against the current markup rather than exercising a repair. The oracle layer above owns detection and repair correctness.
06. **human validation.** Per `STRAT-HUMAN-01/02`, the last step. A person clicks through the Scraper Health page once every automated layer and the live tier are green, following a checklist derived from this tracker's own closure criteria.

Strategy rules applied to this feature:

01. **the mutation is the oracle, independent of the repair's own report.** Per `STRAT-CASE-04`'s named-regression pattern and this feature's own **validation utility extension and drifted fixtures** item, every ladder-strategy case starts from a mutation the test author wrote by hand, and the assertion checks the resulting selector and scraped value against that known mutation.
02. **every attribute in the inventory gets its own mutation case, per `15.CK.18`.** The page groups table and its footnotes name sixteen selectors across the three groups, and each one gets a hand-authored mutation exercising whichever candidate strategy the **deterministic repair** item lists, a renamed attribute value, a swapped attribute, a label or sample text match, or a tag-and-position match against a stable anchor, fits the way that field's markup actually tends to change. At least one mutation per strategy is a hit, and at least one field's mutation matches none of them, exercising escalation and the diagnostics the **escalation and defect inventory** item lists.
03. **no wall clock, no sleep.** Per `STRAT-CASE-06`, the schedule, the debounce window, and `next_run_at` read time through `clock.py::now()`, following the search schedule's own oracle pattern, `10.TC.21` and `10.TC.22`.
04. **the admin surface is exercised as the second user, per `STRAT-CASE-08`.** Every drift endpoint and the Scraper Health page get a non-admin case and an unauthenticated case, alongside the admin happy path, and `13.TC.26`'s tenancy matrix extends to cover the six resources this feature's data model adds.
05. **isolation.** A mutation is applied to a copy of the captured fixture markup at inspection time, and the committed fixture files other silos read stay untouched, so this feature's own tests leave the corpus features 10 and 11 depend on untouched. Every case that writes runs against a freshly reset temp database.
06. **live tier carries the least weight.** A live MCF run rarely drifts on any given day, so the single live-tier case exists to confirm the current site rather than to reach coverage the oracle layer already owns. The sixteen mutation cases and the escalation path above are what this feature's correctness actually rests on.

**time efficient testing**

high value, low latency checks run first, and the full regression suite runs last, once independent failures are isolated and fixed one by one.

make use of time-efficient tests when planning and executing tests and sequence of tests.  Utilize high value, time-efficient tests first, and reserve longer more time-intensive tests in later stages for comprehesive coverage after first exhausting short cycle time high information value testing.

_generic time efficient testing guidelines_

01. run low latency high volume tests such as db inspection and api requests before moving on to more time intensive browser interactive tests and human tests
02. run tests directly related to feature first, and then in later stages expand to more comprehensive tests that include regression testing
03. once failures and exceptions are encountered, 

    - 03.01 first, consolidate and identify independent first-out exceptions
    - 03.02 separate them from cascading failures, then
    - 03.03 one-by-one, run isolated tests narrowly focused on resolving each of these independent issues one-by-one
    - 03.04 only once ALL of these independent issues are resolved run the original complete regression comprehensive test as confirmation or to surface the next independent failure

_specific application to this feature_

01. run the oracle mutation cases and the direct `db_util.py` inspection cases first. Neither needs a browser or a running server, matching `STRAT-SILO-05`'s service-layer pattern, which feature 10's own equivalent, `test_search_pipeline.py`, already showed runs in milliseconds against no live process.
02. run `api_tester.py`/`ui_tester.py` cases against a running dev instance next, narrowed to this feature with `pytest -m backend -k "drift or selector or defect or role"` once the oracle and inspection layers are green, rather than the full backend suite feature 10's logs show growing past 400 cases.
03. run the mock end to end and live tiers last, and only once every layer above passes, since a browser-driven case is the slowest per-case cost this feature has.
04. on a failure, consolidate first-out exceptions, separate them from cascading failures, and resolve them one by one before re-running the full closing command, per `010.10`'s own sequence.

## Design

**TDD:** Every decision below names the `15.TC.*` case from the **Test cases** section that would fail if the decision were built any other way. A design choice with no citation is one the test cases don't yet pin down, and is flagged as an **implementation decision** rather than left silent.

### Workflow

**Inspection run, the one entry point every trigger shares.** `easymcf/services/drift.py::request_inspection(db, browser, trigger_source, page_groups, lead_id=None)` is the single function every trigger calls, mirroring `search.start_run`'s role as the one path every run trigger shares.

01. if `drift_inspection` has a `running` row, log one line naming the trigger that was skipped and return without writing a row, proving `15.TC.04`'s `409` and `15.TC.39`'s tick-collision skip through the same code path.
02. when `trigger_source` is `search_run` or `apply_run`, per `15.CK.07`, check the most recent `drift_inspection` row whose `trigger_source` is `search_run` or `apply_run` and whose `page_groups` overlaps the requested set. If its `started_at` is inside `drift_schedule.debounce_minutes` of `clock.now()`, log the debounce and return. This needs no extra state column, since the history `drift_inspection` already keeps is the oracle `15.TC.38` and `15.TC.39` read directly.
03. otherwise insert a `drift_inspection` row (`status='running'`, `trigger_source`, `lead_id`) and call `run_inspection()` on a background thread, the same one-thread-per-trigger shape `ARCH-RUN-02` already establishes for a search run, returning the new `drift_inspection.id` immediately so the caller can poll it, per `15.TC.03`.

**`run_inspection(db, browser, inspection_id, page_groups, lead_id)`** walks each requested page group in turn.

01. **search_results**: `browser.search_page(keyword, min_salary, page=0)` against the canonical search Design fixes below.
02. **post_detail**: `browser.detail_page(url_ref)` against the first open posting found on that same results page.
03. **apply_workflow**: `browser.apply_flow_pages(url_ref)`, a new `MCFBrowser` method (Architecture below) returning one HTML snapshot per step, `{"apply_button", "cv_select", "save", "review"}`, walked through the review step only, per the **apply workflow** page group's own scope. Runs only when `lead_id` is set or the admin's `mcf_session.status='valid'`; otherwise this page group's own result row is `skipped` and the walk moves on, per `15.TC.26`.

For each page group reached, `_classify_page(page_html_or_exception)` returns `blocked`, `skipped`, or the page content to check, per `15.CK.06`/`15.TC.36`/`15.TC.37`: 

- A `blocked`/`skipped` outcome writes one `drift_inspection_result` row with `field=NULL` and stops that page group. 
- a checkable page proceeds to `_check_selector()` below for every `drift_selector` row current for that page group.

_scenarios_

| id | flag     | scenario                                               | 
| -- | -------- | ------------------------------------------------------ | 
| 01 | blocked  | connection error or non-2xx status                     | 
| 02 | blocked  | login-wall or rate-limit marker in the markup          | 
| 03 | blocked  | results page whose card count is genuinely zero        | 
| 04 | skipped  | no `mcf_session` row for the apply group               | 

**`_check_selector(page_html, selector) -> ('healthy'|'broken', value|None)`** runs `selector.selector_value` against `page_html` with BeautifulSoup, per the **webscraping** skill's defensive-parsing pattern, and checks the resulting element count and extracted value against `selector.healthy_shape` (the **Deterministic repair** section's per-field acceptance table). `healthy` writes a `drift_inspection_result` row (`status='healthy'`); `broken` calls `_attempt_repair()`.

Once every requested page group is walked, `drift_inspection.status` becomes `completed` and `ended_at` is stamped, closing the row `15.TC.03`'s poll waits on.

### Selector registry

**`drift_selector`** is versioned and append only, per `15.CK.01`/`15.TC.11`/`15.TC.12`: exactly one row per `(page_group, field)` carries `is_current = 1`, enforced by `ux_drift_selector_current` (Data model below), and a repair always inserts a new row and leaves every earlier row intact. Every scraper and apply-automation read goes through one function, `easymcf/services/drift.py::current_selector(db, page_group, field) -> Row`, so a registry update alone changes behavior, exactly as `15.CK.01` requires. 

**Seed rows** (Seed data below) are `source='seed'`, `version=1`, `is_current=1`. A repair's row is `source='repaired'`, `version` one past the field's prior current row, and carries `repair_attempt_id` pointing at the `drift_repair_attempt` row that produced it.

### Deterministic repair

**`_attempt_repair(db, inspection_id, page_html, selector) -> ('repaired'|'escalated', new_selector_row|defect_row)`** tries the four strategies below in order, per `15.CK.03`/`15.CK.18`, stopping at the first candidate whose extracted value passes the field's value shape check from the table above. Every attempt, accepted or rejected, writes one `drift_repair_attempt` row (Data model below) before the function moves to the next strategy or returns.

01. **attribute rename** (`15.TC.20/.21/.26/.30/.31/.47`) — the attribute name is unchanged but its value has drifted. The candidate is the sole element under the field's anchor sharing the selector's tag and attribute name; its current value becomes the new selector value.
02. **attribute swap** (`15.TC.22/.27/.32`) — a different attribute now carries the same purpose. The candidate is an element under the anchor, of a plausible tag, whose value under any of `data-testid`, `data-cy`, `id`, or `class` equals the field's last known good value; the new selector records the new attribute name with that same value.
03. **label or sample text match** (`15.TC.24/.25/.34`) — every attribute is gone, but the field's own text still matches a known pattern (an exact prior label, a `$`-prefixed token, the literal text `"Closed"`). The candidate is the element under the anchor whose text matches that pattern, and the new selector is expressed as that element's tag plus its position relative to the anchor, since only the field's text survives to lock onto.
04. **tag and position against the anchor** (`15.TC.23/.28/.33`) — the field's own markup changed past every rule above, but its position relative to the anchor is unchanged. The candidate is whatever element now sits at the selector's recorded child-index or sibling-offset from the anchor, and the new selector adopts that element's current tag and attributes.

A field whose mutation matches none of the four, `15.TC.29`'s `industry_classification` and `15.TC.35`'s `submit`, exhausts the ladder with every attempt rejected and calls `_escalate()` below.

### Escalation and defect inventory

**`_escalate(db, inspection_id, page_group, field, page_html, selector, attempts) -> defect_row`**, called once every strategy above is exhausted, per `15.CK.04`. It opens a `drift_defect` row, or updates the one already open for that `(page_group, field)` per `ux_drift_defect_open_field`'s partial unique index, so a repeated failure never creates a second, per `15.TC.14`. The diagnostics written match `15.TC.13` field for field:

01. **failed selector and last known good version** — `selector.id`, its `selector_value`, and `version`.
02. **failure kind** — `zero_match`, `unexpected_count`, or `shape_mismatch`, from `_check_selector()`'s own classification.
03. **sanitized excerpt** — the anchor's outer HTML, truncated to a size cap Design fixes at 4 KiB, with every attribute value matching a session-cookie or bearer-token pattern replaced by `[redacted]` before it is ever written, satisfying `15.CK.13`/`15.TC.16`.
04. **near miss candidates** — every rejected candidate from every strategy above, ranked by how much of the field's value shape check each one passed.
05. **structural diff** — a shallow tag/attribute diff against the anchor's markup from the field's last healthy inspection, or `NULL` when none exists yet.
06. **page URL and screenshot reference** — the reference page's own URL, and, for `search_results`/`post_detail`, a file path under `data/drift/` a Playwright screenshot is written to; for `apply_workflow` this reference is dropped once the inspection ends, per the capture-retention rule below.
07. **source locations** — the file and line of every place `current_selector()` is called for that `(page_group, field)`, read once at startup from a small static map in `easymcf/services/drift.py` rather than by inspecting the call stack at failure time.

**Capture retention** (`15.CK.17`/`15.TC.17`): a `search_results`/`post_detail` page capture is unauthenticated and is written to `data/drift/<inspection_id>/<page_group>.html`, retained under the gitignored `data/` directory as the historical record `15.CK.02`'s baseline case and later audits read. An `apply_workflow` capture is authenticated and is written only to a path under the OS temp directory for the running inspection, deleted in a `finally` block once `run_inspection()` ends, whether the field repaired or escalated; only the sanitized excerpt already written into `drift_defect` survives.

A defect closes only when a later inspection finds the field `healthy` (`_check_selector()` returns `healthy` for that `(page_group, field)`), setting `status='resolved'`, `resolved_inspection_id`, `resolved_at`, and `resolution_method`. `resolution_method` is `'repaired'` when that same inspection's `_attempt_repair()` produced the fix and `'manual'` when the current `drift_selector` row for that field was written by neither `_attempt_repair()` nor the seed, satisfying `15.CK.05`'s "a repaired defect and a defect fixed by hand outside the app both show correctly."

### Triggers and schedule

**Schedule.** `drift_schedule` is a single row (`id=1`), a global 1:1 counterpart to `search_schedule`'s per-track shape, read and advanced by the same `next_run_after()` pure function `easymcf/services/scheduler.py` already exports, per `15.TC.38`/`15.TC.39`. `easymcf/services/scheduler.py::tick(db, now)` gains one call after its existing `search_schedule` loop: when `drift_schedule.schedule_enabled` and it is due, it calls `request_inspection(db, browser, 'scheduled', ('search_results', 'post_detail'))` and advances `next_run_at` exactly as a search schedule's row does; a `RunInFlight`-equivalent collision, `request_inspection`'s own running-row check, is caught, logged, and leaves `next_run_at` untouched, per `15.TC.39`. This is the one change to `tick()`, and `run_forever()` needs none, since a bad drift tick is caught by the same per-tick `except Exception` guard that protects a bad search tick today.

**Failure triggers.** `easymcf/services/search.py`'s run loop and the eventual apply-run loop (feature 11, whichever exists at build time) each call `request_inspection()` once at the point they already classify a raised exception or a silent shape-validation failure against a scraped field, per `15.CK.07`. A search-run failure requests `('search_results', 'post_detail')`; an apply-run failure requests `('apply_workflow',)` with that run's `lead_id`.

**Manual trigger.** `POST /api/v1/drift/inspections` (API endpoints below) calls `request_inspection(db, browser, 'manual', ('search_results', 'post_detail'))`, admin only, per `15.TC.03`/`15.TC.04`. The apply group has no manual trigger, per the Scope's **triggers and schedule** item; the admin page's run now control only ever starts the two scheduled groups.

### Admin role and access gate

**`user_role`** is a two-row catalog, `1='admin'`, `2='user'` (Data model below), joined from `user.user_role_id`. `easymcf/auth/roles.py::role_id_for_email(config, email) -> int` returns the admin row's id when `email.lower() == config.admin_email.lower()` and the user row's id otherwise; `accounts.signup()` and `google.py`'s account-creation branch both call it once, at the row's own `INSERT`, so the role is always server-assigned and set the same way on both sign-up paths, per `15.TC.29`/`15.TC.40`. `is_admin(db, uid) -> bool` reads `user.user_role_id` joined to `user_role.name = 'admin'`.

**Gate.** A new blueprint, `easymcf/api/drift_routes.py` (`url_prefix="/api/v1"`), registers its own `before_request`, run after `auth_routes.install_guard`'s existing hook has already set `g.user_id` or raised `401`: `if not is_admin(get_db(), g.user_id): raise Forbidden("admin only")`. This answers `15.TC.01`'s `403` for a signed-in non-admin and relies on the existing global guard for `15.TC.02`'s `401`, needing no change to `install_guard` itself since only this one blueprint's routes are admin-restricted.

**`auth/me`** gains one field, `role`, `"admin"` or `"user"`, read the same join `is_admin()` uses, so the frontend gate (Frontend page UI below) needs no separate endpoint.

### Data model

Schema version 11. Six new tables and one column on `user`, all in `easymcf/db/schema.sql`. Recreate-don't-migrate stays in force per `ARCH-STO-02`.

```sql
CREATE TABLE user_role (
    id INTEGER PRIMARY KEY,
    name TEXT NOT NULL UNIQUE CHECK (name IN ('admin', 'user'))
);
INSERT INTO user_role (id, name) VALUES (1, 'admin'), (2, 'user');
-- user gains: user_role_id INTEGER NOT NULL REFERENCES user_role(id) DEFAULT 2

CREATE TABLE drift_selector (
    id INTEGER PRIMARY KEY,
    page_group TEXT NOT NULL CHECK (page_group IN ('search_results', 'post_detail', 'apply_workflow')),
    field TEXT NOT NULL,
    version INTEGER NOT NULL,
    selector_value TEXT NOT NULL,
    healthy_shape TEXT NOT NULL,
    is_current INTEGER NOT NULL DEFAULT 1 CHECK (is_current IN (0, 1)),
    source TEXT NOT NULL CHECK (source IN ('seed', 'repaired')),
    repair_attempt_id INTEGER REFERENCES drift_repair_attempt(id),
    created_at TEXT NOT NULL
);
CREATE UNIQUE INDEX ux_drift_selector_current ON drift_selector(page_group, field) WHERE is_current = 1;

CREATE TABLE drift_inspection (
    id INTEGER PRIMARY KEY,
    trigger_source TEXT NOT NULL CHECK (trigger_source IN ('scheduled', 'manual', 'search_run', 'apply_run')),
    page_groups TEXT NOT NULL,
    lead_id INTEGER REFERENCES lead(id),
    started_at TEXT NOT NULL,
    ended_at TEXT,
    status TEXT NOT NULL CHECK (status IN ('running', 'completed', 'failed'))
);
CREATE UNIQUE INDEX ux_drift_inspection_running ON drift_inspection(status) WHERE status = 'running';

CREATE TABLE drift_inspection_result (
    id INTEGER PRIMARY KEY,
    inspection_id INTEGER NOT NULL REFERENCES drift_inspection(id),
    page_group TEXT NOT NULL,
    field TEXT,
    status TEXT NOT NULL CHECK (status IN ('healthy', 'repaired', 'escalated', 'blocked', 'skipped')),
    selector_id INTEGER REFERENCES drift_selector(id),
    defect_id INTEGER REFERENCES drift_defect(id),
    CHECK ((field IS NULL AND status IN ('blocked', 'skipped'))
        OR (field IS NOT NULL AND status IN ('healthy', 'repaired', 'escalated')))
);

CREATE TABLE drift_defect (
    id INTEGER PRIMARY KEY,
    page_group TEXT NOT NULL,
    field TEXT NOT NULL,
    status TEXT NOT NULL CHECK (status IN ('open', 'resolved')),
    last_known_good_selector_id INTEGER NOT NULL REFERENCES drift_selector(id),
    failure_kind TEXT NOT NULL CHECK (failure_kind IN ('zero_match', 'unexpected_count', 'shape_mismatch')),
    markup_excerpt TEXT NOT NULL,
    near_miss_candidates TEXT NOT NULL,
    structural_diff TEXT,
    page_url TEXT NOT NULL,
    screenshot_ref TEXT,
    source_locations TEXT NOT NULL,
    opened_inspection_id INTEGER NOT NULL REFERENCES drift_inspection(id),
    resolved_inspection_id INTEGER REFERENCES drift_inspection(id),
    resolution_method TEXT CHECK (resolution_method IN ('repaired', 'manual')),
    resolved_selector_id INTEGER REFERENCES drift_selector(id),
    opened_at TEXT NOT NULL,
    resolved_at TEXT
);
CREATE UNIQUE INDEX ux_drift_defect_open_field ON drift_defect(page_group, field) WHERE status = 'open';

CREATE TABLE drift_repair_attempt (
    id INTEGER PRIMARY KEY,
    inspection_id INTEGER NOT NULL REFERENCES drift_inspection(id),
    page_group TEXT NOT NULL,
    field TEXT NOT NULL,
    strategy TEXT NOT NULL CHECK (strategy IN ('attribute_rename', 'attribute_swap', 'label_match', 'tag_position')),
    candidate_selector_value TEXT NOT NULL,
    verified INTEGER NOT NULL CHECK (verified IN (0, 1)),
    evidence TEXT NOT NULL,
    created_at TEXT NOT NULL
);

CREATE TABLE drift_schedule (
    id INTEGER PRIMARY KEY CHECK (id = 1),
    schedule_enabled INTEGER NOT NULL DEFAULT 0 CHECK (schedule_enabled IN (0, 1)),
    schedule_interval_hours INTEGER NOT NULL DEFAULT 24 CHECK (schedule_interval_hours > 0),
    next_run_at TEXT,
    debounce_minutes INTEGER NOT NULL DEFAULT 30 CHECK (debounce_minutes > 0)
);
INSERT INTO drift_schedule (id) VALUES (1);
```

`page_groups` on `drift_inspection` is a JSON array, `["search_results", "post_detail"]` or `["apply_workflow"]`, read by `request_inspection()`'s own debounce check rather than a join table, since an inspection touches at most two groups together and they are always the same pair. `drift_schedule.schedule_enabled` seeds `0`, matching `search_schedule`'s own opt-in default, so a fresh install starts with the schedule off, per the **unattended live access** design decision the Scope already resolved. `meta.schema_version` and `SCHEMA_VERSION` in `easymcf/__init__.py` become 11, and the **data model** document's Schema versions table gains row 11 in task `15.04`.

None of the six new tables carries a `user_id` column and none is added to `easymcf/tenancy.py::SCOPES`; they join `UNSCOPED` alongside `role`, since drift affects the shared scraping capability rather than any one user's data. The admin gate above governs access entirely through role.

### API endpoints

Named endpoints, admin only, all under `/api/v1/drift`. `drift_selector`, `drift_inspection`, `drift_inspection_result`, `drift_defect`, and `drift_repair_attempt` are otherwise read through the generic `API-CAT-01` shape, `get`/`search` verbs only, since every write to them happens only inside `run_inspection()`.

| id       | method and path                     | success              | failures            |
| -------- | ----------------------------------- | -------------------- | ------------------- |
| DRIFT-01 | `POST /api/v1/drift/inspections`    | `202` id, `running`  | `401`, `403`, `409` |
| DRIFT-02 | `GET /api/v1/drift_inspection/{id}` | `200` inspection row | `401`, `403`, `404` |
| DRIFT-03 | `GET /api/v1/drift_defect/search`   | `200` defect rows    | `401`, `403`        |
| DRIFT-04 | `GET /api/v1/drift/resolved`        | `200` resolved rows  | `401`, `403`        |
| DRIFT-05 | `GET /api/v1/drift_schedule/1`      | `200` schedule row   | `401`, `403`        |
| DRIFT-06 | `PUT /api/v1/drift_schedule/1`      | `200` schedule row   | `400`, `401`, `403` |

01. **DRIFT-01** answers `202` per `15.TC.03`, the same asynchronous shape `API-EP-04` uses, and `409` per `15.TC.04` when `request_inspection()` finds a running row.
02. **DRIFT-02** is what `15.TC.03`'s `poll` field targets, `status` moving from `running` to `completed`.
03. **DRIFT-03** accepts `status=open` and a `page_group`/`field` filter through the generic column check; the Scraper Health page's open defects table calls it with `status=open`.
04. **DRIFT-04** is a named endpoint rather than a generic `search`, since "resolved, joined to its opened/resolved inspections, filtered by a date range" spans two tables, per the **API design**'s `API-CAT-03` category. It accepts `from`/`to` query dates.
05. **DRIFT-05/06** are the plain generic shape on the single-row `drift_schedule` table; `06` rejects `schedule_interval_hours < 1` with `400`, per `15.TC.05`.
06. every route in this table sits behind the admin gate (Admin role and access gate above), so a non-admin gets `403` and an unauthenticated caller gets `401` on all six, per `15.TC.01`/`15.TC.02`.
