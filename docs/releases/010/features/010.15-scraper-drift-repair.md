# Scraper Drift Repair - Feature tracker
>Review the guidelines before performing any actions including edits on the document

## 010.15 (open) scraper drift repair

Detects and repairs breaks in the MyCareersFuture page selectors that the search scraper, the posting detail scraper, and the apply automation depend on. An inspection reads the current markup of each page group, finds selectors that no longer resolve, repairs the ones a deterministic algorithm can fix, and inventories the rest with the evidence gathered so a person or an agent can finish the repair. An admin-only Scraper Health page shows the last inspection, the open defects with their diagnostics, and a report of past defects and how each was resolved.

## Scope

Build drift detection and repair for the MyCareersFuture markup the scrapers rely on, a persisted repair workflow behind it, and the Scraper Health page that surfaces it. Drift is a change in MCF's page markup that stops a selector from resolving or makes it resolve to the wrong content. The prototype's `recommission.py` and the tier 3 smoke protocol in `ARCH-TEST-06` both catch drift only when a person runs them and only report it. This feature makes detection recurring, repairs the simple cases without a person, and keeps a durable record of every case it could not repair. The repair logic is a deterministic algorithm. It fetches a fresh MCF page html, runs pre-determined probes and diagnostics and determines whether to repair or record as a defect for human or ai review.  Cases the algorithm cannot resolve are escalated, which means logged with the evidence collected so a person or a coding agent can finish the repair outside the app.

The feature builds on the search scraper, `MCFBrowser`. It extends them in place. It does not add a second scheduler thread, a second browser layer, or a parallel scraper.

Three page groups are in scope. Each has a reference page the inspection loads and a set of selectors it checks.

| id | page group     | reference page                             | selectors inspected                     |
| -- | -------------- | ------------------------------------------ | --------------------------------------- |
| 01 | search results | first results page of a canonical search   | card, title, company, date, salary      |
| 02 | post detail    | first open posting on that results page    | closed flag, MCF ref, closing date [1]  |
| 03 | apply workflow | apply pages of that posting, not submitted | apply button, CV card, save, submit [2] |

1. also applicants, industry, and description.
2. also the status text. The submit control is checked for presence and never clicked.

The table is a summary. The full selector list per group is settled in Design and comes from the `mycareerfutures` skill and the scraper source code.

In scope:

01. **selector registry.** Every selector the scrapers and the apply automation use moves out of scattered code into one registry keyed by page group and field. The registry is versioned and append only, so a repair adds a new version and never edits an old one. The source code reads selectors only through the registry, so a repair takes effect without a source edit. Each registry entry also carries what a healthy match looks like, such as the expected element count and the shape of the extracted value, so detection can tell a selector that matches nothing from one that matches the wrong thing.
02. **drift detection.** An inspection loads each reference page through the `MCFBrowser` seam, runs every registered selector against it, and records a result per selector. A selector is broken when it matches nothing, matches an unexpected number of elements, or extracts a value that fails its shape check. An inspection separates drift from causes that are not drift, such as the site being unreachable, a login wall, a rate limit, or a page with legitimately no results. Those outcomes end the inspection as `blocked` for that page group and raise no defect. Apply workflow pages need the admin's MCF session and report `skipped` when none exists.
03. **deterministic repair.** For each broken selector, the algorithm tries an ordered ladder of candidate strategies, such as a renamed attribute value, a swapped attribute of the same purpose, a match on the label or sample text the field is known to hold, and the same tag and position relative to a stable anchor element. A candidate is accepted only when it verifies against the captured page and matches the entry's healthy shape across all sample elements. An accepted candidate is written as a new registry version and the defect is recorded as repaired. Every attempt, accepted or rejected, is recorded with its strategy and evidence.
04. **escalation and defect inventory.** When no strategy verifies, the defect stays open and the algorithm records the initial diagnostics. These cover the failed selector and its last known good version, the failure kind, a sanitized excerpt of the surrounding markup, a ranked list of near miss candidates, a structural diff against the last healthy snapshot when one exists, the page URL, a screenshot reference, and the source locations that read the selector. A repeated detection of the same broken field updates the one open defect and does not create a second. A defect closes only when a later inspection finds the field healthy.
05. **triggers and schedule.** An inspection starts three ways. 
  01. fired from a schedule, defaulting to once a day
  02. search run or an apply run that ends with a selector miss or an unexpected empty result requests one, with a debounce so a failing run cannot start a loop of inspections
  03. admin user can also trigger one manually from the Scraper Health page. The admin can enable or disable the schedule and change its interval from that page. 
  One inspection runs at a time, and a trigger that collides with a running inspection is skipped and reported.
06. **data model update.** Add tables and update seed data generator for 
  - selector registry
  - inspections
  - per selector inspection results
  - defects
  - repair attempts
  - drift schedule
  - `user_role` table add `admin` role. 
  Edit `easymcf/db/schema.sql`, bump `meta.schema_version` to the next value in the **data model** Schema versions table, and extend the seed generator so the seed carries seed data for each resolution method. 
  Recreate-don't-migrate stays in force per `ARCH-STO-02`. 
  Large captured markup lives in files under the gitignored `data/` directory and the tables hold their references.
07. **admin role.** Update the `user_role` table to add the `admin` role. Every account has one role, and new accounts default to `user`. The account with the email `yayfalafels@gmail.com` is the one admin. The table is named `user_role` because the existing `role` table is the job role a track targets. The Scraper Health page and every endpoint behind it are the only admin only surface. 
08. **backend api.** Admin only endpoints to read the last inspection, the inspection history, the open defects with their diagnostics, and the resolved defect report, to trigger a manual inspection, and to read and update the drift schedule. A non admin caller receives `403` and an unauthenticated caller receives `401`. Endpoints follow the generic shapes of the **api design** wherever a generic shape fits and register any named endpoint in its catalog.
09. **frontend Scraper Health page.** A page reachable only by the admin, with its navigation link shown only to the admin and a route guard that discreetly sends anyone else away redirect to the EasyMCF home landing page. It shows 
  - last inspection result per page group
  - list of open defects in a table with the initial diagnostics visible for each row
  - a control to trigger an inspection 
  - schedule settings. 
  Errors and in flight state surface through the existing error surfacing pattern.
10. **resolved defect report.** A report on the same page lists past resolved defects with the page group, field, when it was detected and resolved, the resolution method, and the change made, meaning the old and new selector and the strategy that produced it. A date range filter narrows it.
11. **validation utility extension and drifted fixtures.** Extend `scripts/api_tester.py` and `scripts/ui_tester.py` in place with cases for admin and non admin access to the drift endpoints and page. Add fixture pages that apply known markup mutations to the captured MCF pages, such as a renamed attribute, a removed element, and a restructured container. The mutation is the independent oracle, since the expected repair follows from what was changed and never from the repair code's own output. Existing case fields and the log format stay as they are.
12. **live drift inspection validation.** A live tier case runs one inspection against the real MCF site and confirms the reference pages load, every selector resolves or is reported correctly, and the apply workflow pages are reached with a real session. It follows the human gated pattern of `ARCH-TEST-06`, sits behind the `live` marker, and is never run by an agent on its own initiative. An agent may prepare the case, the command, and the evidence capture.
13. **document updates.** Update the **requirements**, **architecture**, **data model**, **api design**, **user interface**, **workflows**, and the `mycareerfutures` skill so they describe the drift repair feature, the admin role, and the selector registry. The statements that `010` has no roles and no admin console are revised as part of this feature.

Out of scope:

01. Model driven or agent driven repair inside the app. The escalation record is built so an agent can act on it, and the app makes no model calls.
02. Editing selectors by hand from the page. A person or an agent corrects an escalated defect through the registry outside the page, and the next inspection closes the defect once the field is healthy.
03. Automatic re-scraping or re-applying of runs that failed before a repair. A repaired selector applies to the next run.
04. Self healing at scrape time. Repair runs only inside an inspection, and the scrapers use whatever the registry holds.
05. Drift detection for pages outside the three page groups, such as the MCF login flow, profile pages, or the questionnaire steps of an apply.
06. Submitting an application. The inspection never clicks the final submit control and only checks that it exists.
07. Roles beyond `admin` and `user`, role management screens, any admin surface other than Scraper Health, and email notification of new defects.
08. Cloud deployment, an external scheduler, and any change to the network binding.

Decisions to settle in Design before implementation:

01. **selector ownership.** Features 10 and 11 are still pending, so their scrapers can read the registry from the start. Design decides whether feature 15 owns the registry and the refactor of any selector code already written, or whether features 10 and 11 are amended to build against the registry interface first.
02. **unattended live access.** The project instructions forbid live site requests in an automated context, and the scheduled inspection reads the real MCF site. The search schedule of feature 10 already sets the precedent that the running app does this on the user's behalf. Design records the scheduled inspection as a deviation, keeps the schedule off in the seed, keeps `MCF_MODE=fixture` as the default so a fresh install never reaches the live site, and states that agents never trigger a live inspection.
03. **apply workflow reach.** Clicking through apply steps may create draft state on MCF. Design decides how far the inspection walks, and which steps it reports as not inspected when reaching them would change state on MCF.
04. **admin assignment.** Feature 13 has no email verification, so a password sign up with the admin email must not receive the admin role. Design decides between assigning the role only through the seed and a verified Google sign in, and how a fresh database gets its admin.
05. **snapshot privacy.** Captured markup from the apply pages is authenticated. Design defines what is stripped before it is stored and shown, which covers cookies, tokens, and personal text, and the size cap on stored excerpts.
06. **candidate acceptance rules.** The verification a candidate must pass before it is written, the confidence threshold if scores are used, and a limit on how many selectors one inspection may rewrite before it stops and escalates instead, so a broken page cannot cause a mass rewrite.
07. **trigger debounce.** The minimum gap between failure triggered inspections and what counts as a scrape failure worth inspecting.

**closure**

- **15.CK.01** every selector used by the search, detail, and apply code is read from the registry. Changing a registry version changes scraper behavior with no source edit.
- **15.CK.02** an inspection against unmodified fixture pages reports every selector healthy and records a completed inspection with no defects.
- **15.CK.03** for each mutation of the fixture pages that a strategy in the ladder is designed to handle, the inspection repairs the selector, writes a new registry version, records the attempt, and the scraper then parses the mutated page correctly. The result matches the known mutation and not the repair code's own report.
- **15.CK.04** for a mutation no strategy can handle, the inspection leaves the selector unchanged, opens one defect, and records the initial diagnostics with every field named in scope item 04. A second inspection of the same page updates that defect and creates no new one.
- **15.CK.05** a defect closes only through a later inspection that finds the field healthy, and its record shows the resolution method and the change made. A repaired defect and a defect fixed by hand outside the app both show correctly in the resolved report.
- **15.CK.06** blocked causes, such as an unreachable site, a login wall, or a page with no results, end the page group as `blocked` and open no defect. A missing MCF session reports the apply group as `skipped`.
- **15.CK.07** a scheduled inspection fires when due, defaulting to a daily interval. A failed search run or apply run requests one, and a burst of failures yields one inspection inside the debounce window. A manual trigger during a running inspection returns a conflict.
- **15.CK.08** the schedule can be enabled, disabled, and changed from the page, and `next_run_at` follows the new interval.
- **15.CK.09** `user_role` holds only `admin` and `user`, `yayfalafels@gmail.com` is the only admin, every other account is `user`, and no API request can change a role.
- **15.CK.10** the Scraper Health page and its endpoints reject a non admin with `403` and an unauthenticated caller with `401`. The navigation link is absent for a non admin and the route redirects them away.
- **15.CK.11** the page shows the last inspection per page group, the open defects table with the initial diagnostics on each row, the run now control, the schedule settings, and the resolved defect report with its date filter, and every figure matches the database.
- **15.CK.12** `schema.sql`, `meta.schema_version`, and the **data model** document agree. `scripts/resetdb.py --seed` loads cleanly and a version mismatch refuses startup with the `ARCH-STO-03` message.
- **15.CK.13** no cookie, token, or personal text appears in stored snapshots, the database, or the logs.
- **15.CK.14** the closing commands of features 07 to 13 still pass against this feature's changes, with any existing case updated only for the registry or the role column.
- **15.CK.15** with every fixture case passing, a user triggered live inspection reports the real pages correctly per 15.CK.02 and no secret from the run appears in the repository, the database, or the logs. An agent never runs this case on its own initiative.
- **15.CK.16** the release documents named in scope item 13 describe the feature and agree with the implementation.
