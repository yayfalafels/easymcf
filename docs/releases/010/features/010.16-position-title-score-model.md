# Position Title Score Model - Feature tracker
>Review the guidelines before performing any actions including edits on the document

## 010.16 (open) position title score model development

Builds the scoring model milestone 10's search run calls at persist time (`title_keyword_v1`, REQ-SRCH-09): the token-overlap scoring method itself, the small role-agnostic reference tables that support title cleaning (`rank_tag`, `junk_tag`, `keep_tag`), and the developer-curated, git-tracked keyword library organized by `role` that the method scores against. Trains and evaluates that library from the historical corpus already committed under `reference/` (one user's own scraped-title and applied-role history, `jobsearch`-era mining), and packages the result as versioned JSON config, one file per role, loaded into the `role` catalog and its keyword library at seed/build time. `010.10` only calls the resulting pure function against tables this milestone populates; this milestone owns the method, the library's content, and the evaluation that proves it performs.

This split exists because the two were tangled in `010.10`'s original design: a runtime feature (call a scoring function during a search run) and an offline model-development effort (curate, train, and evaluate what that function scores against) were one Scope section. They have different lifecycles — this milestone's output is versioned config that changes on its own schedule, not on every search-run code change — and different owners in practice: one is service-layer implementation, the other is closer to data curation and evaluation.

## Scope

In scope:

- **research — scoring methodology**: select a role-generalized, brief, dependency-free, polynomial-time scoring approach. See Algorithms below for the chosen method and the alternatives considered and preserved for a later release.
- **role library JSON schema and content** (REQ-SRCH-09): one git-tracked JSON file per role under `reference/roles/`, each holding that role's keyword phrases and scores plus optional synonyms, replacing `keyword_tag.csv`'s hand-picked groups and `title_tag.csv`'s personal bigram-frequency table as the runtime library's source. A small manifest lists the roles available, which becomes the seed for the `role` catalog table.
- **curation/training from the historical corpus**: `reference/title_tags.csv`, `keyword_tags.csv`, `junk_tags.csv`, `rank_tags.csv`, and `keep_tags.csv` stop being loaded directly as runtime lookup tables and become this milestone's *training input* — the historical record of one user's own scraped/applied titles, mined for a starting keyword set per role. Gaps a role's historical data doesn't cover are filled by hand-authored keyword lists researched for that role, using the same brevity constraint (a short phrase list, not a mined frequency table).
- **evaluation**: a held-out slice of the historical corpus (titles with a known good/bad role match) scores the chosen method's precision, committed as a short report alongside the library so `020` or a later revision has a baseline to beat.
- **role becomes a closed, developer-managed catalog**: only this milestone's seed loader writes `role` rows, from the git-tracked JSON. The current data model already models `role` as a shared catalog (`010-data-model.md`, `role` table) and `track.role_id` as a plain FK, but the **api design**'s `role` entry is still `CAT-01` generic (full user CRUD) — this milestone changes that classification to read-only and updates `010-api.md` accordingly. A user picks an existing role when creating a track/search profile; they cannot create, edit, or delete a `role` row, since there would be no way for a user-created role to get a keyword library.
- **seed loader integration**: `scripts/gen_test_data.py` reads the role JSON library instead of `title_tag`/`keyword_tag` CSVs directly, and continues to load `rank_tag`, `junk_tag`, and `keep_tag` from their existing (global, role-agnostic) CSVs unchanged.
- **cross-cutting documentation**: this milestone is the one that changes `010-api.md`'s `role` classification and `010-data-model.md`'s keyword-library table shapes, both flagged for architect/product-manager review since they touch an existing requirement's (REQ-SRCH-01) assumption that search configuration is entirely user-editable.

Out of scope:

- the runtime scoring service itself — `score_title`, `TagLibrary`, and the `post_track`/`match_score` write path stay `010.10`'s. This milestone hands `010.10` a populated set of tables and a documented formula; `010.10` calls it.
- `track`/`search_profile` CRUD, the Tracks/Search Profiles screens, and the role picker control — `010.10`/frontend. This milestone only makes `role` itself read-only; the picklist UI that lists available roles is `010.10`'s to build.
- any change to `rank_tag`'s semantics — it stays a single global seniority table shared by every role, not per-role.
- NLP/semantic scoring in production — a release-wide exclusion (**requirements** Out of scope). Semantic similarity is documented here only as a rejected alternative for `010`, with the reasoning kept so a later release can pick it up deliberately.
- letting a user create, edit, or delete a `role` row through the API — explicitly refused, see Scope above.

- **16.CK.03** an evaluation report, committed alongside the library, shows the chosen method's precision against a held-out slice of the historical corpus, per role and overall.

## Design

### Algorithms

**Chosen method — declared-keyword overlap.** A pure function of a post title, a track's role, and the role's keyword library, in the range 0 to 1, computed as a net count of matched signals normalized the same way `010.10`'s formula already does (`net / (net + 1)` for a positive net count, `0` otherwise). Three signals contribute, each phrase or tag counting once regardless of repetition:

01. every keyword phrase in the track's role's library that appears in the cleaned title as adjacent words
02. every phrase in the track's own `search_profile.keywords` that appears in the cleaned title
03. a seniority modifier from the single global `rank_tag` table

This is a token/phrase-overlap measure — a weighted, role-scoped variant of a Jaccard-style set intersection — computed with plain string containment checks, $O(\text{title words} \times \text{role phrases})$, no external library.

**Alternatives considered, preserved for a later release:**

- **plain Jaccard coefficient** over the cleaned title's word set and the role's keyword set, $\lvert A \cap B\rvert / \lvert A \cup B\rvert$, with no per-phrase weighting. Simpler than the chosen method and equally cheap, but loses the ability to score one phrase as a stronger signal than another (a fully unweighted alternative — the chosen method's weighted-count formula subsumes it as the un-weighted case). Not chosen because the historical corpus's title_tag/keyword_tag scores show real signal-strength variation worth keeping.
- **live TF-IDF / cosine similarity** computed from term frequencies in the `post` table itself (the shared, growing corpus across all users), rather than from a hand-curated library. Generalizes automatically to any role without curation, but needs a maintained term-frequency cache and drifts as the corpus grows — more moving parts and less predictable than this release wants for its first scoring method.
- **semantic/embedding similarity** (e.g. sentence embeddings + cosine distance). The most generalizable option, matching titles by meaning rather than exact phrase, but requires an embedding model dependency, which the release-wide NLP/semantic exclusion and this repo's "no complex NLP library" constraint both rule out for `010`. Recorded here so `020` can evaluate it deliberately against this milestone's own evaluation report as a baseline.

### Role library schema

```json
{
  "role": "Data Scientist",
  "description": "generic data science / ML individual-contributor roles",
  "keywords": [
    {"phrase": "data scientist", "score": 1},
    {"phrase": "machine learning", "score": 1},
    {"phrase": "data science", "score": 1}
  ],
  "synonyms": ["ml engineer", "applied scientist"],
  "meta": {"trained_from": "reference/title_tags.csv, reference/keyword_tags.csv", "sample_size": 0, "precision": 0.0}
}
```

`reference/roles/index.json` lists `{id, name, file}` for every role, seeding the `role` table's `id`/`name` in file order for byte-stable regeneration. `keywords[].score` follows the existing `-1`/`0`/`1` convention (off-target/neutral/on-target). `synonyms` are phrases that count as a keyword match without their own score, folded into signal 01 at 1 each.

### Data model

Reduces `010.10`'s original five-table keyword-library proposal to a role-keyed library plus the three tables that stay role-agnostic:

01. `role_keyword`: `role_id INTEGER REFERENCES role(id)`, `phrase TEXT NOT NULL`, `score INTEGER NOT NULL CHECK (score IN (-1, 0, 1))`, `PRIMARY KEY (role_id, phrase)` — the per-role library, loaded from `reference/roles/*.json`.
02. `junk_tag`, `rank_tag`, `keep_tag` keep the shapes `010.10` already specified, unchanged, still CSV-seeded since they hold no personal data and no per-role variation.
03. `role` keeps its existing shape (`010-data-model.md`); this milestone only changes who is allowed to write to it (nobody, at the API layer — only the seed loader).

### Seed data

`scripts/gen_test_data.py` gains a role-library loader that reads `reference/roles/index.json` and each listed role file, in manifest order, emitting one `role` insert and one `role_keyword` insert per keyword/synonym, byte-stable across regenerations. `_map_junk_tag`, `_map_rank_tag`, and `_map_keep_tag` stay as `010.10` specified them, reading their existing CSVs directly.
