## Scope

Add a **MCF** nav destination that runs the Singpass login MCF already presents, inside a local browser session easyMCF owns, and hands the resulting QR code and Singpass app-launch link to the signed-in user so they can approve the login from their own phone. The same browser that requested the login completes MCF's normal callback, and the resulting authenticated MCF session becomes the `mcf_session` row apply automation already reads.

- all steps other than the user's own Singpass approval can be executed by an autonomous claude ai agent with access to terminal using re-runnable idempotent scripts, and any check against the real `mycareersfuture.gov.sg` or Singpass origin stays human-gated per `ARCH-TEST-06` and `CLAUDE.md`'s boundary against unattended live-site access

In scope:

01. **connection attempt.** The user selects Connect MCF from the MCF nav page while signed in. The backend creates an attempt owned by that user and launches an isolated local Chromium context through Playwright. A repeated click while an attempt is already active reuses that same attempt.
02. **login navigation.** The runner opens `https://www.mycareersfuture.gov.sg/`, selects Login, follows the popup's Login with Singpass option, and follows the resulting redirect until Singpass displays a usable QR for the pending transaction. The runner keeps the same browser context for the rest of the attempt.
03. **QR and link handoff.** The runner extracts the actual Singpass app-launch URL when the page reliably exposes it, and decodes the displayed QR image otherwise. It validates the extracted destination against the known Singpass host and login path before showing it, using only the reference MCF's own page provides. The frontend shows the QR image, and on a device where a tappable link makes sense, the Open Singpass link, to the requesting user's own session only.
04. **phone approval.** The user scans the QR or taps the link and completes Singpass authentication, including any biometric or other challenge, in their own Singpass app. This step is always a human action performed on the user's own device, regardless of whether an agent is driving the rest of the attempt.
05. **callback verification.** The runner waits for the originating browser's own page to complete MCF's normal callback. It relies on MCF's and Singpass's own documented callback and page behavior to detect completion, leaving callback handling and authorization code redemption to MCF as the relying party. It confirms a stable authenticated MCF page before treating the attempt as connected.
06. **account confirmation.** The runner reads the account-identifying information MCF's authenticated page exposes. A first connection requires the user's explicit confirmation of the displayed account before it becomes usable. A later attempt compares against the previously confirmed identifier where MCF exposes a reliable one, and an unexpected account change is blocked and surfaced to the user for resolution.
07. **session record.** A verified and confirmed attempt exports the browser context's own authenticated storage state and writes it to `mcf_session`, the same `.secrets/mcf_session_<user_id>.json` file and `cookie_ref` column `ARCH-BOT-03` already defines for the manual upload flow, and the same `status` vocabulary the **data model** already defines. This is now the way that row and file get populated, automatically, in place of the user's own manual cookie export and upload.
08. **attempt lifecycle.** The attempt carries its own state, `starting`, `awaiting_approval`, `verifying`, `account_confirmation_required`, `connected`, `expired`, `cancelled`, `failed`, `interaction_required`, `reauthentication_required`, distinct from a search run or apply run's own state. If the Singpass page regenerates its QR, the frontend's image and link update together for the same attempt. A refresh retires the superseded browser context, so only the current attempt's approval can complete the active connection.
09. **ownership.** Every attempt, its QR, its link, and its status are authorized against the signed-in user per REQ-AUTH-06, and each browser context serves exactly one user.
10. **disconnect.** The user can disconnect a connected or in-progress attempt. Disconnect cancels pending login work, deletes easyMCF's retained session material for that user, and stops the owned browser. This action is scoped to easyMCF's own retained state, and any other session MCF or Singpass holds independently stays under their own management.
11. **execution mode.** The runner is a background thread inside the existing local Flask process, holding one headless Chromium context through Playwright for the duration of one active attempt. The thread writes each state transition to the attempt's own row, so the status endpoint reads that row directly. Every Playwright wait carries its own timeout, so a stuck attempt reaches `failed` or `interaction_required` instead of leaving the thread blocked. The browser context itself closes once the attempt reaches `connected` or any other terminal state, its authenticated storage state already exported per item 07 by that point, so apply automation opens its own fresh context from that saved state when a run actually needs one, rather than a browser sitting open and idle between the two.
12. **document updates.** The **api design**, **data model**, **workflows**, and **requirements** documents are updated at the design stage, task 17.02, to describe the connection-attempt lifecycle and endpoints, and to replace REQ-APPLY-06's manual export-and-upload description with this feature's handoff as the way the existing `mcf_session` row is populated.

Out of scope:

01. Cloud or AWS-hosted browser execution, ECS or Fargate tasks, and any container orchestration. Cloud deployment stays out of scope for `010` per `CLAUDE.md`.
02. A remote desktop viewer, video or screen streaming, keyboard forwarding, or any VNC-style component. The headless QR-only flow needs none of them.
03. Embedding the live MCF website in an `<iframe>`, webview, proxy frame, or any other in-app browser surface.
04. Automating the Singpass authentication step itself. Biometric verification and app approval stay the user's own manual action, consistent with REQ-APPLY-06's exclusion of automating the login or MFA itself.
05. Cloud or encrypted-object-storage persistence of browser state. Local persistence reuses the existing `.secrets/mcf_session_<user_id>.json` mechanism and `cookie_ref` column `ARCH-BOT-03` already defines, described under Design, not a new storage mechanism of its own.
06. Any additional identity challenge beyond the reported QR-and-approval flow. An unsupported step reports `interaction_required` and stops there.
07. Live-site validation run unattended or by an agent on its own initiative. Any check against the real `mycareersfuture.gov.sg` or Singpass origin is human-gated per `ARCH-TEST-06` and `CLAUDE.md`'s boundary.
08. Multi-user cloud scaling of the browser runner. `010` runs one local backend process, and that same process serves each user's attempt directly.

**closure**

- **17.CK.01** clicking **MCF** in the nav opens an easyMCF-owned page reflecting the signed-in user's own connection state, and a repeated click always reuses that same active attempt for that user
- **17.CK.02** the runner reaches the real Singpass QR page for a login it started, and extracts a validated app-launch URL or QR image using the exact reference MCF's page provides
- **17.CK.03** the page shows the current QR image, and where available a tappable Open Singpass link, scoped to the requesting user's own session only
- **17.CK.04** the user's phone approval of the QR or link results in an authenticated MCF session in the same browser context that requested it
- **17.CK.05** the authenticated account is presented to the user and requires explicit confirmation before the connection is usable, and an account change on a later attempt is blocked and surfaced for the user to resolve
- **17.CK.06** the connection is marked ready only after authenticated-session verification and account confirmation both succeed, and the `mcf_session` row apply automation reads reflects that state
- **17.CK.07** expiry, rejection, and cancellation each reach a safe terminal state that leaves the `mcf_session` row unchanged, and a fresh attempt is available afterward
- **17.CK.08** every attempt, QR, link, and browser-runner request is authorized against its owning user, and a request from a different user returns not found
- **17.CK.09** disconnect stops the owned browser and deletes easyMCF's retained session material for that user
- **17.CK.10** the feature's added surface is limited to the session coordinator, the browser runner, the QR and link handoff, and account confirmation, matching the components named in scope

## Design Probes

these probe tasks settled two open design decisions, both closed against real live runs:

| id        | probe                                  |
| --------- | -------------------------------------- |
| 17.PB.01  | Singpass redirect URL extraction       |
| 17.PB.02  | MCF account-identifying fields         |

01. **Singpass redirect URL extraction.** Headless Chromium, launched with `channel="chromium"`, reaches the real Singpass QR page on its own, no bot-detection block observed. The page does not expose the app-launch URL as literal text anywhere in the DOM or the network trace. It renders the QR as an inline `<svg id="ndi-qr-canvas">`, decoded directly from that element with `cv2.QRCodeDetector`. MCF's own redirect into Singpass, `id.singpass.gov.sg/fapi/auth?client_id=...&request_uri=...`, is captured in the network trace but confirmed single-use, `PX-E0013 invalid_request_uri` when a second browser tried it after the first had already fetched it, so it stays diagnostic evidence rather than a handoff link. The decoded QR value is the one the runner hands to the user.
02. **MCF account-identifying fields.** The dashboard's own text exposes only a display name, `Hello <name>,`, not fit alone for scope item 06's account-confirmation check. Clicking the account-menu trigger, `<button data-testid="initial-circle-container">`, reveals the actual identifier directly underneath the name: the account's email address, present both in the opened menu and again on the profile page reached through its **Profile** link. The profile page also exposes extensive account content beyond identity, work history, skills, expected salary, and the uploaded resume's filename, none of it needed for account confirmation but confirming the depth of detail sitting behind that one menu click. `EASYMCF_ACCOUNT_EMAIL` matched against the extracted MCF email, and the probe's own interactive confirmation prompt, a live rehearsal of scope item 06's UX, completed end to end against a real Singpass login.

**probe prerequisites**

01. verify the local live-automation environment. `env/bin/python`'s Playwright already launches headless Chromium, confirmed locally with `playwright.chromium.launch(headless=True)` against version 151.0.7922.34, so task 17.14 can start directly against that already-installed Chromium.
02. design both probes as one script, reusing the `HEADLESS` and `MCF_MODE` env vars `easymcf/config.py` already defines, and follows `scripts/check_gcp_oauth.py`'s pattern of a small, git-tracked, rerunnable script rather than a pytest case, since the expected result is what the probe is discovering rather than a fixed assertion to check against. It captures a screenshot and the full page HTML at each navigation step under `.dev/logs/`, so a human can review what the runner actually saw without re-running the live site. It stops at extraction and observation, and leaves the Singpass approval itself, per out-of-scope item 04, to the human running task 17.13.
03. both probes need a human to trigger the run, per `CLAUDE.md`'s boundary against unattended live-site access. **Probe 17.PB.01** completes once the runner reaches the QR page. **Probe 17.PB.02** additionally needs the user's own real Singpass approval on their phone, the same manual action **Workflow 8** already asks for, so both probes are typically run together in one sitting to avoid a second live login.

### Probe script design

`scripts/probe_mcf_singpass.py` is the single git-tracked, rerunnable script both probes ran against, `scripts/check_gcp_oauth.py`'s pattern of a small standalone check rather than a pytest case, since the point was discovering unknown behavior, not asserting a known one. The file's own docstrings and comments are the source of truth for exact behavior; this section records the findings and reusable patterns worth carrying into the real implementation, not a restatement of the code.

**flow, as it actually ended up working**

01. reach `https://www.mycareersfuture.gov.sg/`, wait for its own client-rendered app to settle (`_wait_for_render()`), locate Login through `LOGIN_LOCATORS`'s ordered, explicit-priority candidates, since the real markup was unknown ahead of running this.
02. follow the click through to Singpass, launched with `channel="chromium"` rather than Playwright's headless default.
03. wait for the QR to render (`_wait_for_qr_render()`), decode it directly from the matched DOM element (`QR_ELEMENT_LOCATORS`, `_decode_qr_element()`), and hand it to the user both as a popup image (`_save_qr_popup()` / `_open_image_popup()`) and a decoded link, refreshing both on `QR_REFRESH_INTERVAL_MS` rather than one static capture.
04. once MCF's callback returns this same browser, wait for render again, print the dashboard's own text, then click the account-menu trigger (`ACCOUNT_MENU_TRIGGER`) and follow any revealed profile link (`PROFILE_LINK_LOCATORS`), scanning everything captured with `_find_email()`.
05. compare the found email against `EASYMCF_ACCOUNT_EMAIL` and rehearse the actual confirm/reject prompt with a real `input()`, not a simulated one.

**findings and patterns for the real implementation**

- **client-rendered pages lie about being ready.** Hit three times independently, MCF's home page, Singpass's QR page, and MCF's own post-approval page, all still show a loading skeleton at `domcontentloaded`. Every navigation this script makes is followed by a `networkidle` wait before reading anything (`_wait_for_render()`, folded into `_wait_for_qr_render()` too). The real browser runner needs the same discipline everywhere it navigates, not only at the two spots this probe happened to hit it.
- **an explicit-priority locator list beats a combined CSS selector.** `QR_ELEMENT_LOCATORS` exists because `"canvas, img[src^='data:image']"` matched two unrelated decorative icons before it ever found the real QR, DOM order deciding which alternative wins. `LOGIN_LOCATORS` and `SINGPASS_OPTION_LOCATORS` already used the safer pattern; `_first_match()` is the one shared implementation:
  ```python
  QR_ELEMENT_LOCATORS = [
      ("id=ndi-qr-canvas", lambda pg: pg.locator("#ndi-qr-canvas")),
      ("data-testid=ndi-qr-canvas", lambda pg: pg.locator("[data-testid='ndi-qr-canvas']")),
      ("canvas", lambda pg: pg.locator("canvas")),
      ("svg[role=img]", lambda pg: pg.locator("svg[role='img']")),
      ("img[data:image]", lambda pg: pg.locator("img[src^='data:image']")),
  ]
  ```
- **the real Singpass QR is an inline `<svg id="ndi-qr-canvas">`**, confirmed against a live page, never a `<canvas>` or a raster `data:` image. `_decode_qr_element()` still works for either fallback shape, since Playwright's element `.screenshot()` renders whatever is on screen regardless of element type.
- **`cv2.QRCodeDetector` fails a small, borderless QR regardless of source**, confirmed against a freshly `cv2`-generated one before ever touching Singpass. `_decode_qr_element()` upscales with nearest-neighbor interpolation and pads a white quiet zone before decoding.
- **MCF's own redirect into Singpass is single-use**, `id.singpass.gov.sg/fapi/auth?client_id=...&request_uri=...`, confirmed by `PX-E0013 invalid_request_uri` when a second browser opened it after the first had already fetched it. Capturing it without the original browser consuming it was tried four ways, a compiled regex matcher, a Python predicate, routing every request and filtering in Python, `service_workers="block"`, and none of them caught it: a confirmed Chromium/Playwright cross-origin renderer-swap limitation, not a bug in this script, so the on-page QR stays the only mechanism that actually works for handoff.
- **the dashboard alone shows only a display name.** The account-menu trigger, `<button data-testid="initial-circle-container">`, reveals the account's actual email directly underneath it, and its **Profile** link exposes far more account detail again, work history, skills, expected salary, resume filename. The real account-confirmation step needs to look there, not just read the landing page.
- **`stdout` is fully buffered once redirected to a file**, not line-buffered the way a terminal is, so a long-running, human-monitored script needs `sys.stdout.reconfigure(line_buffering=True)` or its progress, including a link the human is waiting to act on, never appears until the process exits.
- **`explorer.exe` from WSL2 opens a file in the OS's own viewer** when given a `wslpath -w`-converted path, but its own exit code is not a reliable success signal, a documented WSL interop quirk.
- **static analysis is cheap insurance against a live run that costs a real login.** `pyflakes`, added to `.dev/dev-env`'s `pyproject.toml`, caught a `NameError` on an undefined constant and, separately, an edit that had silently swallowed an `elif` branch, both before they could waste another real Singpass approval.

Evidence lands under `.dev/logs/<ts>-17.PB-probe/`, one screenshot, one HTML dump, and one visible-text dump per step, plus a `findings.json` summarizing what each step found and a `network.jsonl` of every captured request and response. The script never submits, applies, or clicks anything outside the Login-to-Singpass-and-back path, and it only ever writes what the rendered page shows, never a cookie or session value, to its own evidence files. Those same captured HTML dumps, the MCF home page, the Singpass QR page, the account menu, and the profile page, are the natural seed for a fixture corpus the real implementation's automated tests can run against instead of the live sites, the same role `ARCH-TEST-04`'s canned MCF HTML already plays for search and apply.

## Test Strategy

Seven layers, following the **test strategy doc**'s own `STRAT-*` framework and running in the same order `STRAT-TOOL-04` already establishes for every other functional milestone: each layer checks independently of the layers before it, so a claim at one layer gets a second, independent confirmation.

01. **self-report.** Case-config replay through the **api tester** and the **ui tester**, `STRAT-TOOL-01/02`, against a running instance, once task 17.02 names the actual connection-attempt endpoints. `tests/backend/cases/mcf_connection.json` and `tests/frontend/checks/mcf_connection_ui.json` extend the existing directories, the same replay mechanism every other milestone already uses.
02. **direct inspection.** `scripts/db_util.py` against `mcf_session` and whatever attempt/session-registry table task 17.02 adds, `STRAT-SILO-02`, confirming a write actually persisted, the `status` transition, the confirmed account identifier, independent of what the API response claimed.
03. **oracle.** hard-coded-expectation pytest calling the session-coordinator and attempt-lifecycle service directly, `STRAT-SILO-05`'s pattern for search and apply's own service layer, covering the full attempt state machine, every state in scope item 08's vocabulary and every legal transition between them, against a fixture browser.
04. **automation silo, a Singpass fixture seam.** `ARCH-BOT-02`'s `MCFBrowser` deliberately kept Singpass outside its own seam, because automating login was out of scope under the old design. This feature's whole point is bringing that flow into an automated seam, so it needs the equivalent split: a `fixture.py`/`live.py` pair task 17.02 names, gated by the same `MCF_MODE` `ARCH-RUN-08` already defines. The fixture corpus, `tests/fixtures/singpass/`, seeds directly from this tracker's own probe evidence, `.dev/logs/*-17.PB-probe/qr-singpass-qr.html`, `qr-account-menu.html`, and `qr-account-profile.html`, real markup this tracker's own probe runs already proved accurate. Route-intercepted per `ARCH-TEST-04`'s existing pattern, this lets extraction, decoding, and account-comparison logic run deterministically against a fixed reference, never a real rotating QR, per `STRAT-CASE-06`.
05. **mock end to end.** Playwright against the real backend and the same Singpass fixture corpus, `ARCH-TEST-04/09`'s existing pattern, confirming the frontend's QR image, its Open Singpass link, and its status indicator wire together correctly across the whole flow.
06. **live tier.** human-gated exactly as `ARCH-TEST-06` and this feature's own probes already were: a real Singpass approval and a real MCF account, triggered only by the user's own explicit action, never by an agent's initiative. This is the same live check the probes already performed, run again here as this feature's own closing validation.
07. **human validation.** `STRAT-HUMAN-01/02`, the last step, once every layer above passes: does the printed QR actually look right, does the nav entry read correctly, does the account-confirmation wording make sense to someone who isn't the person who wrote it.

Strategy rules specific to this feature:

01. **the probe's own findings become permanent regression cases**, `STRAT-CASE-04`. A render-wait must precede every read of MCF or Singpass page state: a fixture case captures a page mid-loading-skeleton and asserts the runner waits for it to settle before reading it. QR-element selection uses the explicit-priority locator list: a fixture case deliberately places a decorative icon ahead of the real QR element in DOM order and asserts the runner still picks the right one. The MCF-to-Singpass redirect capture stays a documented out-of-scope boundary, confirmed unworkable by the probe, so it needs no case of its own beyond that boundary itself.
02. **state-machine coverage**, `STRAT-CASE-02`. Every state in scope item 08's vocabulary, `starting` through `reauthentication_required`, needs a reachable fixture scenario and its legal transitions enumerated, the same treatment the lead status/stage machine already gets.
03. **ownership**, `STRAT-SILO-08` and `STRAT-CASE-08`. Every attempt, its QR, its link, and its status endpoint gets the tenancy-matrix treatment against a second seeded user, generated from the resource registry the same way milestone 13's own regression case already is, so a new resource added later fails until it is scoped.
04. **determinism**, `STRAT-CASE-06`. Singpass's real QR rotation, its bot-detection timing, and any wall-clock dependency are removed entirely from every tier but the live one; only a human-triggered live run ever sees a real, time-limited QR.

## Design

### Session coordinator and browser runner

The connection-attempt workflow runs entirely inside the existing local Flask backend process, using a background thread, the same choice `ARCH-RUN-02` already made for search and apply runs. This keeps the runner inside the same process as the rest of the backend, sharing its existing SQLite connection pattern directly. Each thread holds one headless Chromium context through Playwright, `channel="chromium"` per **17.PB.01**'s finding, scoped to one active attempt, and closes it once that attempt reaches a terminal state or is disconnected.

**attempt flow**, informed directly by the probe's own findings:

01. `POST /api/v1/mcf_attempt/start` creates the row (`starting`) and starts the thread, or returns the existing row if one is already in flight for that user, matching scope item 01's reuse requirement.
02. the thread opens `https://www.mycareersfuture.gov.sg/`, waits for the page's own render to settle before reading anything, the client-rendered-app finding **17.PB.01** hit twice, clicks Login, and follows it to Singpass, moving the row to `awaiting_approval` once a QR is visible.
03. it locates the QR through the explicit-priority locator list, `#ndi-qr-canvas` first, the same fix **17.PB.01** needed after a decorative icon matched ahead of the real QR under a combined CSS selector, and decodes it directly from that element's own bitmap.
04. it waits for the page's own navigation back to an `mycareersfuture.gov.sg` host, moving the row to `verifying`, then waits for that page's own render to settle again before reading it, the same finding a second and third time.
05. it clicks the account-menu trigger, `[data-testid="initial-circle-container"]`, since **17.PB.02** found the dashboard's own text exposes only a display name; the account holder's email sits directly underneath that click. The row moves to `account_confirmation_required` with the found email attached.
06. once the user confirms through the frontend, the row moves to `connected`, the browser exports its own authenticated storage state to `.secrets/mcf_session_<user_id>.json`, and the coordinator writes the existing `mcf_session` row, `status='valid'` and `cookie_ref` pointing to that file, the same fields apply automation already reads. Its own browser context then closes, having already handed off what it captured. A rejection, an unconfirmed mismatch, or a timeout at any step moves the row to `failed` or `interaction_required` instead, leaving `mcf_session` unchanged, per closure item 17.CK.07.

the QR value and the found email, while unconfirmed, live only in an in-memory registry the coordinator keeps, keyed by attempt id, the same short-lived, sensitive handling the reference spec's own notes call for. Only the confirmed outcome persists to disk: the account email once the user accepts it, and the exported storage state once the attempt reaches `connected`, both written to `mcf_session` itself, defined below.

**deviation** - `ARCH-NET-03`'s outbound allow list currently names only the MCF origin. This feature adds the Singpass origin the runner actually redirects to, `app.singpass.gov.sg` and any host observed alongside it, the same way milestone 13 added the Google endpoints for OAuth.

### Expiry and reauthentication

The attempt's own browser context closes once it reaches `connected`, its authenticated storage state already exported to `mcf_session.cookie_ref` by that point per scope item 07. Apply automation opens its own fresh context from that saved file and restores the cookies into it each time a run actually needs one. This is also what keeps a connected session intact across a backend restart: the file survives one, an in-memory-only browser would not have.

MCF's own session can still lapse on its own side at any later point, restored or not. The detection this feature relies on is the same one `REQ-APPLY-06` already establishes: an apply run that opens its restored context and lands on MCF's login page instead of the page it expected writes `mcf_session.status='expired'` and moves the owning attempt row to `reauthentication_required`, the vocabulary value scope item 08 already names for exactly this case. This reuses an existing trigger, one check with one place to get its timing right.

The frontend reads this the same way it reads every other state: `GET .../search` already polls `mcf_attempt` and `mcf_session` together for the status page and badge, so the very next poll after either one flips shows `reauthentication_required` directly. That state renders with the Connect MCF action available again, the same control a never-connected user sees, since `reauthentication_required` sits outside `ux_mcf_attempt_active` alongside `connected`, `expired`, `cancelled`, and `failed`, so starting a fresh attempt is always available once it's reached.

`ARCH-BOT-02`'s `MCFBrowser` deliberately kept Singpass outside its own seam, since automating login was out of scope under the design this feature replaces.

`easymcf/automation/singpass_browser.py` gives Singpass the same fixture/live split `MCFBrowser` already has, `fixture.py` and `live.py` behind one interface, gated by the same `MCF_MODE` `ARCH-RUN-08` already defines. **`mcf_attempt`**, new table.

### API endpoints

| `POST /api/v1/mcf_attempt/start`        | named       | create or return the caller's in-flight attempt      |

### 17.06 session coordinator and attempt lifecycle

**17.EL.09** `easymcf/services/mcf_connection.py`, new. The coordinator owns the state machine and the in-memory registry the **Session coordinator and browser runner** design section describes. It never runs Playwright itself; `singpass_browser.py` does, behind the `SingpassBrowser` interface 17.07 builds.

```python
"""REQ-APPLY-06 — the mcf_attempt coordinator (ARCH-BOT-02's SingpassBrowser seam)."""

from __future__ import annotations

import threading

from .. import clock
from ..automation.singpass_browser import get_browser
from ..errors import Conflict, RecordNotFound

ACTIVE_STATUSES = ("starting", "awaiting_approval", "verifying", "account_confirmation_required")
_REGISTRY: dict[int, dict] = {}  # attempt_id -> {"qr_bytes": ..., "found_email": ...}
_LOCK = threading.Lock()


def get_qr_bytes(attempt_id: int) -> bytes | None:
    with _LOCK:
        entry = _REGISTRY.get(attempt_id)
    return entry["qr_bytes"] if entry else None


def start_attempt(db, uid: int) -> dict:
    existing = db.execute(
        "SELECT * FROM mcf_attempt WHERE user_id = ? AND status IN (?,?,?,?)",
        (uid, *ACTIVE_STATUSES),
    ).fetchone()
    if existing:
        return dict(existing)
    now = clock.now().isoformat()
    with db:
        cur = db.execute(
            "INSERT INTO mcf_attempt (user_id, status, created_at, updated_at) VALUES (?, 'starting', ?, ?)",
            (uid, now, now),
        )
        attempt_id = cur.lastrowid
    threading.Thread(target=_run_attempt, args=(db, attempt_id, uid), daemon=True).start()
    return dict(db.execute("SELECT * FROM mcf_attempt WHERE id = ?", (attempt_id,)).fetchone())


def _set_status(db, attempt_id: int, status: str, **fields) -> None:
    cols = ", ".join(f"{k} = ?" for k in fields) + ", " if fields else ""
    with db:
        db.execute(
            f"UPDATE mcf_attempt SET status = ?, {cols}updated_at = ? WHERE id = ?",
            (status, *fields.values(), clock.now().isoformat(), attempt_id),
        )


def _run_attempt(db, attempt_id: int, uid: int) -> None:
    browser = get_browser()
    try:
        browser.open_qr_login()
        qr_bytes = browser.decode_qr()
        with _LOCK:
            _REGISTRY[attempt_id] = {"qr_bytes": qr_bytes, "found_email": None}
        _set_status(db, attempt_id, "awaiting_approval")
        browser.wait_for_authenticated()  # blocks until MCF's own redirect lands
        _set_status(db, attempt_id, "verifying")
        email = browser.read_account_email()
        with _LOCK:
            _REGISTRY[attempt_id]["found_email"] = email
        _set_status(db, attempt_id, "account_confirmation_required", account_email=email)
    except Exception as exc:  # noqa: BLE001 — every failure mode lands in error_code, not a crashed thread
        _set_status(db, attempt_id, "failed", error_code=type(exc).__name__)
        browser.close()


def confirm(db, uid: int, attempt_id: int, accept: bool) -> dict:
    row = db.execute("SELECT * FROM mcf_attempt WHERE id = ? AND user_id = ?", (attempt_id, uid)).fetchone()
    if row is None:
        raise RecordNotFound("attempt not found", field="id")
    if row["status"] != "account_confirmation_required":
        raise Conflict("attempt is not awaiting confirmation")
    browser = get_browser()
    if not accept:
        browser.close()
        _set_status(db, attempt_id, "cancelled")
        return dict(db.execute("SELECT * FROM mcf_attempt WHERE id = ?", (attempt_id,)).fetchone())
    cookie_ref = browser.export_storage_state(uid)
    browser.close()
    now = clock.now().isoformat()
    with db:
        db.execute(
            "INSERT INTO mcf_session (user_id, status, uploaded_at, cookie_ref, confirmed_account_email, confirmed_at) "
            "VALUES (?, 'valid', ?, ?, ?, ?) "
            "ON CONFLICT(user_id) DO UPDATE SET status='valid', uploaded_at=excluded.uploaded_at, "
            "cookie_ref=excluded.cookie_ref, confirmed_account_email=excluded.confirmed_account_email, confirmed_at=excluded.confirmed_at",
            (uid, now, cookie_ref, row["account_email"], now),
        )
    _set_status(db, attempt_id, "connected")
    with _LOCK:
        _REGISTRY.pop(attempt_id, None)
    return dict(db.execute("SELECT * FROM mcf_attempt WHERE id = ?", (attempt_id,)).fetchone())
```
