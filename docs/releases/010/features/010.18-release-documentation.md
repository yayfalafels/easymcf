## 010.18 (open) release documentation

Publishes release `010`, version `0.1.0`, on GitHub. The publication has four parts: the release tagged `010`, a GitHub Pages site built with Material for MkDocs, the as-built design and API documentation, and the three demo videos. The site holds a user guide, a developer guide, and a design section. Everything on it describes the app as built through feature 11 apply automation. The user guide teaches a job seeker to run a search, work the lead pipeline, and apply in batches in live mode. The developer guide takes a developer from a clean machine to a running, debuggable local instance. The design section is the release design docs, revised to match the source code. The three unbuilt milestones, 14, 15, and 16, move to release `020`, so `010` closes when this milestone closes.

## Test strategy

The test strategy stays narrow and covers the MkDocs toolchain and its publication path only. It confirms three things. 

01. The MkDocs dependencies install into `.dev/dev-env` from the **dev-env manifest**
02. site prerequisites are in place, so `mkdocs build --strict` produces exactly the published page set with the videos
03. The GitHub Pages workflow deploys that same site from `main`. 
04. the seed identity codegen fills the seed from `.env`, falls back to public values, and leaves no real identity in a tracked file.

Five verification layers, run in this order. Each layer checks independently of the layers before it.

01. **self-report.** The exit code and log of `mkdocs build --strict`, and the conclusion of the workflow run reported by `gh run view`. Weakest alone. A strict build only fails on warnings, and MkDocs reports a link to an excluded page as an info message, so a green build can still publish a broken link or the wrong page set.
02. **direct inspection.** The installed packages in `.dev/dev-env`, the parsed `mkdocs.yml` and workflow YAML, the file tree of the local `site/` build, the tree of a `gh-pages` branch, and the repository Pages settings read through `gh api`. This layer proves what is installed, configured, and built, without trusting the build's own verdict.
03. **oracle.** Expected values derived by a separate route from the code under test. The expected page set is the published page list decided in task 18.03 and recorded in Design, compared against the `site/` tree and the deployed `sitemap.xml`. The expected video bytes are the `sha256` of the source files. The expected dependency set is the output of `mkdocs get-deps`, compared against the **dev-env manifest**.
04. **black-box.** HTTP requests from outside, first against `mkdocs serve` on `127.0.0.1`, then against the deployed Pages URL. This layer proves each page and video is served with the right status and content type, and that the deployed site matches the local build.
05. **human validation.** A person opens the deployed site in a desktop browser, confirms the navigation tabs, search, and code-copy buttons work, and plays each video inline. This layer also covers the one-time repository settings change to set the Pages source to GitHub Actions.

Strategy rules applied to this feature:

01. **strict is necessary but not sufficient.** `mkdocs.yml` sets the `validation` options for omitted files, absolute links, unrecognized links, and anchors to `warn`, so `--strict` fails on them. `scripts/build_docs.sh` also fails on a link to an excluded page, which no `validation` option raises. The page set is still checked against the oracle list in layer 03, since strict mode cannot catch a page that is in `nav` but should not be published.
02. **a negative case proves each gate.** The strict gate is shown to fail on a planted broken link and on a planted unlisted page, and the excluded-link gate is shown to fail on a planted link to an excluded page. Both run in a scratch copy of `docs/`, so the repo tree is never modified.
03. **no push from a test.** Every case that exercises the workflow before merge, or exercises `mkdocs gh-deploy`, runs against a scratch clone and a local bare remote. 
04. **same toolchain locally and in CI.** The workflow installs from the same **dev-env manifest** and runs the same `mkdocs build --strict` command as the local build, so a local pass predicts a CI pass.
05. **the fallback shares the Pages site.** `mkdocs gh-deploy` pushes to a `gh-pages` branch, while the workflow publishes through the Pages artifact flow. The Pages source can only be one of the two at a time, so publishing through the fallback also means switching the Pages source to the `gh-pages` branch. The Design section's manual fallback documents that switch, and 18.TC.22 checks the fallback's output without switching.
06. **the codegen is tested apart from the seed it renders.** The codegen oracle cases render small template files written by the test into a temp directory, with expected output typed into the test. They never read `seed/` or `.env`, so a change to the seed data cannot mask a codegen defect. The reset cases then confirm the rendered identity lands in the database.

## Design

01. **published design set.** The site's design section is `docs/design/`, one page per baseline design doc, named without the release prefix. `scripts/sync_design_docs.py` generates it from the current release's `docs/releases/<release>/design/` docs, and `scripts/build_docs.sh` fails when it is stale. The release docs are the authoring source during a release and freeze when the release closes. Material's per-page table of contents gives navigation within each page.
02. **URL scheme.** `use_directory_urls: false`. A page `docs/a/b.md` is served at `a/b.html`, so a raw HTML path such as a `<video src>` is written relative to the source file and resolves the same on the site, on GitHub, and in the editor.
03. **links out of the site.** A published page links to an unpublished doc or to a repo file outside `docs/` with an absolute GitHub URL on `main`. Do not use relative links.
04. **one build command.** `scripts/build_docs.sh` wraps the strict build and adds the excluded-link gate that strict mode lacks. The local build, the developer guide, and the workflow all run it.
05. **toolchain pins.** `mkdocs==1.6.*`, `mkdocs-material==9.7.*`, and `pymdown-extensions==10.*` in the **dev-env manifest**. MkDocs 2.0 removes the plugin and theme system Material depends on.
06. **pull request check.** The deploy job runs only on `main`. A pull request into `main` runs the build job alone, which checks the site and the workflow before the merge, per 18.IS.09.
07. **seed identity codegen.** The tracked seed holds placeholders, and the seed is rendered from `.env` at the moment it is applied. The rendered output goes only to untracked paths. Each file type uses the placeholder form that suits it. The codegen is validated by its own oracle tests and by scratch resets, in task 18.18.

### Design probe

One probe, 18.PB.01, built a scratch site under the session scratchpad with `mkdocs 1.6.1` and `mkdocs-material 9.7.7` installed into `.dev/dev-env` on Python 3.14. It mirrored this repo's layout: a published design doc linking to an excluded requirements doc, an excluded feature tracker, and `README.md` at the repo root.

01. **exclusion is per file.** An `exclude_docs` block that excludes `/*` and re-includes single files with `!` publishes exactly the re-included files. A re-include inside an excluded folder works, since MkDocs matches each file path on its own.
02. **links to excluded pages pass strict mode.** MkDocs reports a link to an excluded page at `INFO` level, as `contains a link to '...' which is excluded from the built site`. No `validation` option raises it to a warning, so `--strict` passes and the site ships a 404 link. `scripts/build_docs.sh` fails on that log line.
03. **links outside `docs/` fail strict mode.** A relative link to `../../../../README.md` is a `WARNING` and aborts a strict build.
04. **unlisted pages fail strict mode.** With `validation.omitted_files: warn`, a page that is neither in `nav` nor excluded is a `WARNING` and aborts a strict build.
05. **raw HTML paths are left as written.** A `<video src="../assets/video/a.mp4">` in `user-guide/search.md` is emitted unchanged, and resolves correctly only with `use_directory_urls: false`.
06. **`mkdocs get-deps` lists `mkdocs`, `mkdocs-material`, and `pymdown-extensions`** for the theme and extensions below.
07. **Material 9.7 prints a MkDocs 2.0 notice** on every build. Setting `NO_MKDOCS_2_WARNING=1` suppresses it. The notice holds no `WARNING` token and does not affect strict mode.

### Link rules

Every published page follows these rules. The sync script applies them to the `docs/design/` pages.

01. a link between two published pages is a relative `.md` link, which MkDocs checks and rewrites.
02. a link from a published page to an unpublished doc or to any repo file outside `docs/` is an absolute URL, `https://github.com/yayfalafels/easymcf/blob/main/<repo path>`, or `tree/main/<repo path>` for a folder. This covers the requirements, prototype, test strategy, roadmap, issues, trackers, skills, `README.md`, `.env.example`, and source files.
03. a raw HTML `src` or `href` is written relative to the source file, which the `use_directory_urls: false` setting keeps valid on the site.
04. unpublished docs, including the release design docs, keep their relative links, since they are read on GitHub.

02. each page is the source text with two changes. A line after the H1 title reads `Release <release> design. Source: [<source path>](<GitHub blob URL>).` Each relative link is rewritten.

### Build command

`scripts/build_docs.sh`, git-tracked and executable, is the single build entry point for developers and CI.

01. it reads `MKDOCS`, defaulting to `.dev/dev-env/bin/mkdocs`, and `PYTHON`, defaulting to `.dev/dev-env/bin/python`. The workflow sets `MKDOCS=mkdocs` and `PYTHON=python`.
02. it runs `"$PYTHON" scripts/sync_design_docs.py --check` and fails on a non-zero exit.
03. it exports `NO_MKDOCS_2_WARNING=1` and runs `"$MKDOCS" build --strict --clean` from the repo root.
04. it tees the build output to `$LOGS_DIR/<timestamp>-18.05-docs-build.log`, per the implementation guide's log naming, with `LOGS_DIR` defaulting to `.dev/logs` and created if missing.
05. it fails when the build exits non-zero, when the log holds a `WARNING` line, or when the log holds `excluded from the built site`. It prints each offending line.
06. it ends with one `[PASS] docs build` or `[FAIL] docs build: <reason>` line and exits 0 or 1 to match.

| id | file type                   | form                                                                 |

01. **seed SQL form.** A `{{NAME}}` token sits inside the quoted string literal, so each file is valid SQL syntax. The upper-case email token fails the `user.email` lowercase check, so an unrendered seed file is rejected at load, per 18.IS.01. 02. **`.env.example` form.** `easymcf/config.py` already treats a value starting with `%%` as unset, and `values_from_env()` does the same.

**components**

01. **generator.** `scripts/gen_test_data.py` writes the `{{INITIAL_USER_NAME}}` and `{{INITIAL_USER_EMAIL}}` tokens for user 1's `name` and `email`, for user 1's `mcf_session.confirmed_account_email`, and for user 1's `mcf_attempt.account_email`. `seed/` is regenerated with the **test data** doc's `--mode seed --out seed/ --rand-seed 42` command. _18.IS.01 (closed) generator load check rejects the email token_

**problem description**

After 18.EL.01 set user 1's identity to the `{{...}}` tokens, regenerating the seed failed. The generator's own `validate()` step loads the generated SQL into a fresh schema, and the `user` insert was rejected. Expected: the seed files are written with the tokens in place.

**exception**

```log
sqlite3.IntegrityError: CHECK constraint failed: email = lower(email)
...
RuntimeError: seed validation failed in user: CHECK constraint failed: email = lower(email)
```

**triggering actions**

01. edit `ACCOUNTS[0]` in `scripts/gen_test_data.py` to `"name": "{{INITIAL_USER_NAME}}", "email": "{{INITIAL_USER_EMAIL}}"`.
02. run `env/bin/python scripts/gen_test_data.py --mode seed --out seed/ --rand-seed 42 --anchor 2026-09-21`.

**cause**

The `user.email` column carries `CHECK (email = lower(email))`, and the token `{{INITIAL_USER_EMAIL}}` is upper case. The generator's `validate()` loaded the unrendered SQL, so the check rejected it. The fix in step 03 renders the tokens with the public defaults before `validate()` loads them, and the regenerated seed then passed. The Design section's statement that an unrendered seed file still loads was wrong for the same reason, and is corrected in step 04.

| 18.IS.01.02 | 02  | closed | inspect `sql_value()` quoting of the token             |
| 18.IS.01.03 | 03  | closed | render tokens with public defaults inside `validate()` |
| 18.IS.01.04 | 04  | closed | correct the Design statement on unrendered seed files  |

**diagnostic details**

01. (closed) an in-memory table with `CHECK (email = lower(email))` rejected `{{INITIAL_USER_EMAIL}}` with the same `CHECK constraint failed` message and accepted `{{initial_user_email}}`. This reproduced the exception outside the generator and supported the casing hypothesis.
