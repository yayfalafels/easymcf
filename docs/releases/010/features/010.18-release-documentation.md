## 010.18 (open) release documentation

Publishes release `010` on GitHub. The publication has three parts: the tagged release, a GitHub Pages site built with MkDocs, and the three demo videos. The site holds a user guide and a developer guide. Both describe the app as built through feature 11 apply automation. The user guide teaches a job seeker to run a search, work the lead pipeline, and apply in batches. The developer guide takes a developer from a clean machine to a running, debuggable local instance. Scraper drift repair, milestone 15, and performance dashboard reports, milestone 14, are not built, and the guides leave them out.

## Scope

Write, build, and publish the release `010` documentation site. Publish the release itself on the **github repo**. The as-built scope the guides describe is every closed milestone through feature 11 in the **milestones** table: 07 local dev env, 08 schema and seed data, 12 validation utilities, 09 job leads tracking, 13 oauth login, 17 MCF website session, 10 search by keywords, and 11 apply automation. The guides describe the app as it behaves today. Where a design doc and the running app disagree, the running app is the source of truth for the guide, and the difference is logged as an issue.

In scope:

01. **mkdocs site.** An MkDocs project with a site configuration, navigation, and a home page. The home page states what Easy MCF does, who it is for, the current version `0.1.0`, and links to both guides and the demo videos. MkDocs and its theme are dev tooling. They are declared in the **dev-env manifest** and run through `.dev/dev-env`, per the **project boundaries** two-venv rule. `mkdocs build --strict` passes with no warnings.
02. **user guide.** Task-oriented pages for a job seeker using the running app. The guide covers
    1. signing up and signing in with email and password or with Google, the user menu, the profile photo, and signing out.
    2. connecting an MCF session through the global MCF connection pop-up and the Singpass QR approval, reading session status, and reconnecting after the session expires.
    3. creating tracks and search profiles, setting keywords, the default CV, and a search schedule.
    4. running a search, reading run progress, and browsing posts with their match scores.
    5. the lead pipeline on the Leads page. It covers stages, promotion from posts, batch moves, the Lead Detail panel, notes, deadlines and auto-expiry, close reasons, and offers.
    6. managing CV labels on the CVs page and how the label matches the resume stored on MCF.
    7. the apply queue on the Applications page. It covers CV overrides, dropping a lead, running an apply batch, each apply outcome and its next action, and manually repairing a lead that needs a questionnaire.
    8. the Automation page Runs tab for search and apply run history and error detail.
    9. fixture mode and live mode, what each one does, and a prominent warning that live mode with `APPLY_LIVE_SUBMIT=1` submits real job applications on MCF.
03. **developer guide.** Minimal setup to install, run, and debug the app locally. The guide covers
    1. supported platform, Linux or Windows with WSL2, and prerequisites: Python 3.11 or later with `venv`, git, and the Chromium system libraries Playwright needs.
    2. cloning the repo and creating the `env` virtual environment at the repo root.
    3. installing dependencies from the **ops-env manifest** and installing the Playwright Chromium binary, including the one-time `--with-deps` fallback.
    4. configuration through `.env` copied from `.env.example`, with every variable explained, and the `.secrets/` directory.
    5. optional Google sign-in. It covers registering an OAuth client in a Google Cloud project, the loopback redirect URI, and where the client id and client secret file go. Email and password sign-in works without this step.
    6. creating and seeding the database with `scripts/resetdb.py --seed`, and the seeded test accounts and their sign-in credentials.
    7. starting, restarting, and stopping the app with `python -m easymcf` and `scripts/restart.sh`, and confirming it with the health endpoint and the browser.
    8. running the automated test suite with `scripts/envcheck.py` and `pytest`, and the meaning of the `backend`, `frontend`, `e2e`, and `live` markers.
    9. debugging. It covers headed browser runs with `HEADLESS=0`, where logs are written, inspecting the database directly with `scripts/db_util.py`, pinning the clock with `FIXED_NOW`, and the common failure modes with their fixes, such as a Chromium launch error, a busy port, and a schema version mismatch.
    10. a short orientation to the repo layout and the architecture: the Flask backend, the SQLite store, the vendored AngularJS frontend served from the same origin, and the Playwright automation behind the `MCFBrowser` seam. It links to the release design docs on GitHub for depth.
04. **demo videos.** The three recordings in the **demo videos** folder: `20260926-easymcf-login-auth-search.mp4`, `20260926-easymcf-search.mp4`, and `20260926-easymcf-batch-apply.mp4`. Each video plays inline on the site, on the home page and on the user guide page for the workflow it shows, with a one-line caption. The videos are tracked in git so the site build is reproducible.
05. **release notes and readme.** Update the **release notes** to describe the as-built `0.1.0` feature set and link to the site. Update the **readme** with a one-paragraph description, the site link, and a quick start that points to the developer guide.
06. **pre-publish review.** Before anything is pushed, `scripts/check_no_secrets.py` passes on the release branch, and no `.env`, `.secrets/`, cookie export, `test-data/`, or database file is tracked. A person watches each demo video and confirms it shows no personal data that should stay private, such as a real name, NRIC, email, phone number, or Singpass details.
07. **github release.** Merge the release branch into `main`, tag `v0.1.0`, and create a GitHub release. The release body carries the release notes and links to the site and the videos.
08. **github pages.** Publish the built site to GitHub Pages for the **github repo** and set the site URL as the repository homepage.
09. **move pending features to 020.** Move scraper drift repair, milestone 15, performance dashboard reports, milestone 14, and position title score model, milestone 16, out of release `010` and into the scope of release `020`. Move their three trackers from the **010 features folder** to the **020 features folder**. Remove their rows from the **milestones** table and add them to the **020 milestones** table with their current status. Update every link to the moved trackers, including those in the **job leads tracker** and the **search tracker**. After the move, the **milestones** table lists only closed milestones plus this one, so `010` closes when this milestone closes.
10. **as-built accuracy.** Every command in the developer guide runs as written on a clean clone. Every screen, control, and label the user guide names exists in the running app under the same name.

Out of scope:

01. Implementing scraper drift repair, performance dashboard reports, or the position title score model. Scope item 09 only moves their trackers to `020`, leaving their content unchanged beyond ids and links. The guides do not mention them as features. The release notes may list them as planned for `020`.
02. Setup for running or testing with an autonomous AI agent. That covers the Claude Code skills and subagents, `CLAUDE.md`, the agent validation loop, and the `api_tester.py` and `ui_tester.py` case-replay workflow.
03. Publishing the requirements, architecture, and design documents on the site. The developer guide links to them in the repo.
04. Auto-generated API reference and code-level docstring documentation.
05. A GitHub Actions workflow or any other CI/CD pipeline, per the **project boundaries** release rule. The site is built and deployed from a local machine.
06. A custom domain, analytics, search tuning, versioned documentation, and translations.
07. Re-recording or editing the demo videos. The existing compressed recordings are published as they are.
08. Any change to application behavior. A defect found while writing the guides is logged as an issue and fixed under its owning milestone, and the guide describes the fixed behavior once it lands.

Decisions to settle in Design before implementation:

01. **deploy method.** CI/CD is out of scope, so the site is deployed locally. The recommendation is `mkdocs gh-deploy`, which builds the site and pushes it to a `gh-pages` branch. The alternative is a GitHub Actions Pages workflow, which this release excludes.
02. **site source location.** `docs/` already holds the release design docs. Design picks a separate MkDocs `docs_dir` so the design docs stay out of the published site, and names where the site configuration lives.
03. **video placement.** The recommendation is to move the videos into the site source directory and embed them with an HTML5 `video` element. The alternative is attaching them to the GitHub release as assets and linking them from the site. Design also decides whether `assets/video/` stays as a folder in the repo.
04. **theme and extensions.** The recommendation is Material for MkDocs, for its navigation, search, admonitions for the live-mode warning, and code-copy buttons.
05. **screenshots.** Whether the user guide includes screenshots captured from a seeded fixture-mode instance. Any capture uses seed data only.
06. **moved feature ids.** Whether the moved trackers keep their `010.14`, `010.15`, and `010.16` ids or are renumbered into the `020` sequence, and how the **020 milestones** table records milestone 16's `drop` status.
07. **branch and tag flow.** How `features/010-poc-local-dev` reaches `main`, either as a pull request or as a direct merge, and whether the tag is `v0.1.0` or `010`.
