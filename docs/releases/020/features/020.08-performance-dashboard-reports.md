# Performance Dashboard Reports - Feature tracker
>Review the guidelines before performing any actions including edits on the document

## 010.14 (pending) performance dashboard reports

Adds a Dashboard page that reports on the user's job search performance from the data easymcf already records. It translates the Google Sheets dashboard the **sheets report specification** describes into easymcf's own data model and terms. The page shows recent application activity, the live pipeline, conversion funnels across time, role and source breakdowns, timing diagnostics, and a forecast of interviews and offers. Every figure is computed from the local SQLite database and reconciles to the underlying lead records.

## Scope

Build a Dashboard page, a Report Settings page, and the read-only report endpoint behind them. The **sheets report specification** describes the reports in business terms and warns that its terminology and implementation differ from easymcf. This feature keeps its report logic and reporting principles and re-expresses every report against the tables the **data model** defines. Reports are computed by queries at request time over `lead`, `lead_event`, `post`, `track`, `role`, and `search_profile`. No warehouse, ETL job, or export to Google Sheets is introduced. The release requirements exclude dashboards, and this feature narrows that exclusion to warehouse and BI pipelines. In-app reports over the local database are in scope.

Every report shows the data of the signed-in user only. Ownership is resolved through `track.user_id`, and the reports rely on the sign-in and per-user scoping that feature 13 delivers.

Three rules govern how a lead is counted, and every report follows them.

01. **cohort by application date.** The reporting window is a filter on leads whose application date falls inside it. Every other event date on those leads is part of that cohort, even when it falls outside the window. A lead applied in December whose offer arrives in February counts in the December cohort. Event based reports are the one exception and select by the event's own date.
02. **furthest stage reached.** How far a lead progressed is read from its `lead_event` history and never from `lead.stage`, since closing a lead overwrites its stage. A lead counts as having reached a stage when an event entered that stage or any later one. The state of the lead, open or closed, and its close reason do not change what it reached. A lead closed as rejected after an interview and one still open at the interview stage both count as reaching the interview. The close reason of rejected, where the company declined, and the close reason of withdrawn, where the user declined, are not distinguished.
03. **application and interview dates.** The application date is the date of the first event entering `APPLIED`. The interview date is the date of the first event entering `INTERVIEW`. Callback and offer dates follow the same pattern.

The concept mapping below shows how each concept in the **sheets report specification** maps to easymcf.

| id | sheet concept       | easymcf source                                                             |
| -- | ------------------- | -------------------------------------------------------------------------- |
| 01 | opportunity         | one `lead`, unique per `post`, so distinct counts are distinct `lead.id`   |
| 02 | application date    | date of the first stage event entering `APPLIED`                           |
| 03 | stage event         | `lead_event` rows of type `stage_change` with `occurred_at`                |
| 04 | current status      | furthest stage reached from events, plus `lead.status` for open or closed  |
| 05 | stage hierarchy     | `APPLIED` < `CALLBACK` < `INTERVIEW` < `OFFER`, adjacent steps only        |
| 06 | role category       | `role.name` through `track.role_id`, with Unclassified for a missing role  |
| 07 | track               | `track`, which already combines role and seniority                         |
| 08 | lead source         | `post.source` and `post.src_method`, since MCF is the only channel in 010  |
| 09 | employment type     | `search_profile.employment_type` through the lead's track                  |
| 10 | compensation        | `post.salary_high`, with null preserved as unknown                         |
| 11 | open versus closed  | `lead.status` of `OPEN` or `CLOSED`                                        |

In scope:

01. **data model and seed data update.** The structured `stage_from` and `stage_to` columns on `lead_event` already exist (schema version 5, milestone 09) and every event writes them, so this milestone adds no stage columns. If events recorded before the columns existed remain, a parser reads the free text `detail` of those stage change events and derives the same two values, so older events are usable. Add a `report_setting` table owned by the user through `user_id`, holding the report parameters listed in scope item 10 with defaults from the **sheets report specification** section 15. Record both changes in the **data model** Schema versions table, bump `meta.schema_version`, and extend `scripts/gen_test_data.py` to seed several months of leads with application, callback, interview, offer, and close events across more than one role. Recreate-don't-migrate stays in force per `ARCH-STO-02`.
02. **backend cohort derivation.** A reporting service derives one row per lead with the semantic fields the **sheets report specification** section 3.2 lists, translated to easymcf names. The row holds the application date, application week and year, role, track, source, employment type, open or closed state, furthest stage reached, the callback, interview, and offer dates, cumulative reached stage flags, and maturity flags for each time bounded measure. Every report reads this one derivation so definitions cannot drift between reports. A lead with no event entering `APPLIED` is excluded from funnel counts and counted separately as never applied.
03. **backend filters.** Every report accepts the same filter set. The set is an application date range or year, role, track, source, employment type, furthest stage reached, and open versus closed. A report that intentionally uses a different population says so in its response.
04. **backend recent activity reports.** The weekly funnel matrix by application cohort with role rows and a totals row, the application mix by role, the mature 14 day callback rate, and the mature 28 day interview rate. Callbacks and interviews are attributed to the week of application. Immature applications are excluded from the mature window denominators. The current partial week is marked.
05. **backend current pipeline reports.** Open applications awaiting callback, open callbacks awaiting interview, open interviews, and total active leads, grouped by role and employment type with median salary where present. A pipeline depth comparison of open callbacks and interviews by role. The pipeline position of an open lead is its furthest stage reached.
06. **backend historical reports.** The annual funnel summary with all five stage conversion rates, the annual funnel by role, the annual funnel by source, and the annual maximum and median offer amount (`offer.amount_sgd`, milestone 09) of leads that reached the offer stage. The current year is labeled as an incomplete cohort.
07. **backend composition reports.** Applications by furthest stage reached per year, with open and closed leads shown separately and closed leads broken down by close reason. Applications by source per year, the three weekly distributions by stage, source, and track, and responses by track and application week.
08. **backend timing diagnostics.** Callback and interview event counts by event week, and the callback day of week profile. These are event based and are labeled apart from the cohort based reports.
09. **backend forecast.** Expected interviews over a configurable horizon, the probability of at least one interview, the offer probability distribution from active interviews using a Poisson binomial calculation, and the application plan scenario table. Every forecast shows its model date, input counts, assumed rates, and manual overrides. A scenario is withheld when a required parameter is missing. The **data model** records no interview rounds, so the stage based offer probability is a single configurable value for the `INTERVIEW` stage.
10. **backend report settings.** The recent weekly window, callback and interview maturity windows, forecast horizon, week start, small sample warning threshold, stage offer probability, and reporting timezone are stored in `report_setting` and exposed as a generic resource under the **api design**. Reports read them at request time and read the current time through `clock.py::now()`. A request may override a setting for one call without changing the stored value.
11. **backend report endpoint.** One read only named endpoint added to the **api design** named endpoint index. Its JSON request body names the reports wanted and the filters to apply, so the page loads all six sections in one call and any single report can be requested alone. The response is keyed by report id. Each report returns counts, denominators, and rates together. An empty denominator returns null, never zero and never an error. The endpoint requires a signed-in user.
12. **frontend Dashboard page.** A Dashboard entry in the navigation and one page with six sections in the order the **sheets report specification** section 5 defines. Charts follow the **dataviz** skill, use color blind safe palettes, and never carry meaning by color alone. Each chart has an accessible data table, shows the count, denominator, and rate, and the empty state shows an em dash. Selecting a role, source, track, year, or week cross filters the related visuals. Drilling from an aggregate opens the contributing leads in the Leads page. The global filter bar sits above the sections. The page prints legibly without tooltips.
13. **frontend Report Settings page.** A page reached from the Dashboard where the user views and edits the stored report parameters, including the stage offer probability, and resets them to defaults. Validation errors surface through the **user interface** design's cross cutting error surfacing pattern.
14. **download as csv.** Each report on the Dashboard can be downloaded as a CSV file that matches its displayed figures under the applied filters.
15. **validation utility extension.** Extend `scripts/api_tester.py` and `scripts/ui_tester.py` in place with report cases. Extend `scripts/db_util.py` with independent aggregate queries that serve as the oracle. Existing case file fields and the log format stay as they are.
16. **document updates.** Update the **requirements**, **architecture**, **api design**, **user interface**, **workflows**, and **data model** documents so they describe the Dashboard and the Report Settings page. Revise the dashboard exclusion in the **requirements** and add REQ identifiers for the reports.

Out of scope:

01. Export to Google Sheets, sync with the existing sheet, and import of historical sheet data.
02. A warehouse, ETL pipeline, scheduled report jobs, materialized aggregate tables, and any BI platform.
03. Lead source channels beyond what the data model records. Referral, recruiter, outreach, and direct channels need a new lead field and a taxonomy, and are deferred. Composite source rollups are deferred with them.
04. Compensation normalization across currencies and pay periods. The dashboard reports `post.salary_high` as recorded.
05. Prospect value and the target versus alternative compensation comparison from the **sheets report specification** section 8.3.
06. Survival or lag models for late responses. Immature cohorts are excluded or shown as provisional.
07. A user defined strategic track grouping independent of the existing `track` table.
08. Editing any lead or event record from the Dashboard. Every report is read only.
09. Cross user comparison. Reports show one user's data.

**closure**

- **14.CK.01** the Dashboard page shows all six sections against seed data and each section's figures reconcile to an independently computed oracle.
- **14.CK.02** a lead is counted in the cohort of its application date, and its callback, interview, and offer dates count toward that cohort even when they fall outside the reporting window.
- **14.CK.03** the furthest stage reached is derived from `lead_event` history. A lead closed after an interview and a lead still open at the interview stage both count as reaching the interview, and changing a lead's close reason does not change any funnel count.
- **14.CK.04** annual application totals equal the distinct applied lead count for the same filtered population, and for every cohort offers do not exceed interviews, callbacks, or applications after cumulative stage derivation.
- **14.CK.05** role, source, and track subtotals reconcile to totals, weekly cohorts reconcile to the period total, and stage distributions reconcile to applications.
- **14.CK.06** mature 14 day and 28 day rates exclude immature applications from their denominators, and a zero denominator returns an empty value shown as an em dash, never a divide by zero.
- **14.CK.07** event week charts reconcile to `lead_event` rows and cohort week charts reconcile to `lead` rows, and the page labels which is which.
- **14.CK.08** forecast probabilities stay between 0 and 1, exact offer probabilities sum to 1 within rounding tolerance, expected offers equal the sum of individual prospect probabilities, and every forecast shows its inputs and assumptions.
- **14.CK.09** a user can edit a report setting on the Report Settings page and the next report load reflects it. A per call override changes one response and leaves the stored value unchanged.
- **14.CK.10** one request to the report endpoint returns any requested subset of reports, and a request naming an unknown report is rejected with a descriptive error.
- **14.CK.11** two seeded users each see only their own figures, and an unauthenticated request returns `401`.
- **14.CK.12** applying the same filters to the Leads drill down reproduces every displayed aggregate, and each CSV download matches the figures the page displays.
- **14.CK.13** `schema.sql`, `meta.schema_version`, and the **data model** document agree, `scripts/resetdb.py --seed` loads cleanly, stage events recorded as free text parse to the same stages as structured events, and a version mismatch refuses startup with the `ARCH-STO-03` message.
- **14.CK.14** `scripts/api_tester.py` and `scripts/ui_tester.py` replay report cases, and the validation utilities' own self test cases still pass unchanged.
- **14.CK.15** milestone 07's, 08's, 09's, 10's, 11's, and 12's own closing commands still pass against this feature's changes.
- **14.CK.16** the release documents named in scope item 16 describe the Dashboard and agree with the implementation.
